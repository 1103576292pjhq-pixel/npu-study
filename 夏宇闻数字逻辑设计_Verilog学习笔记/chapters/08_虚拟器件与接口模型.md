# 08 虚拟器件与接口模型：把外部世界搬进仿真

## 本章知识全景图

大型数字系统不可能只验证核心 RTL 本身。真实芯片周围还有存储器、总线、ADC、UART、CPU、DMA、外部协议和各种时序限制；虚拟器件和接口模型的作用，是在仿真里给 DUT 一个足够像真实世界的环境。

| 学习块 | 核心问题 | 工程判断 |
|---|---|---|
| 虚拟器件/IP | 预先设计好的模块能不能复用 | 可综合 IP 和仿真模型必须分清 |
| 虚拟接口模型 | 外部器件怎样在仿真中出现 | 只要接口行为准确，不一定可综合 |
| AD7886 行为模型 | 怎样按数据手册写一个 ADC 数字接口 | 时序参数、三态数据、忙信号、错误提示缺一不可 |
| USART 8251A 模型 | 复杂串行接口行为怎样组织 | 用任务、事件、状态寄存器和时序检查描述环境 |
| 8085A 行为模型 | 处理器模型怎样驱动外部总线 | 取指、读写、等待、保持、中断都可建成 BFM |
| 现代验证映射 | 这些例子今天对应什么 | BFM、VIP、UVM agent、cocotb driver/monitor、assertion |

最短路径：先区分“要综合进芯片的 RTL”和“只在仿真里模拟外部世界的模型”，再学习 AD7886 这种小模型的写法，最后从 8251A 和 8085A 看到复杂行为模型怎样拆成任务、事件和自检查。

## 1. 虚拟器件、软核、硬核和接口模型不是一回事

本章的第一条边界是：同样叫“模型”，有的会变成硬件，有的只服务仿真。

| 名称 | 典型形态 | 是否可综合 | 用途 |
|---|---|---|---|
| 软核 IP | RTL 级 Verilog/VHDL/SystemVerilog | 通常可综合 | 作为设计的一部分复用，例如 UART、FIFO、CPU 核 |
| 硬核 IP | 工艺或器件中已经实现好的模块 | 不由 RTL 综合生成 | PLL、SerDes、DDR PHY、厂商嵌入式处理器等 |
| 虚拟器件 | 用 HDL 描述的常用芯片模型 | 可能可综合，也可能只是行为级 | 复用成熟功能或模拟外部器件 |
| 虚拟接口模型 | 系统级行为模型、总线模型、外设模型 | 常常不可综合 | 替代外部芯片，验证 DUT 的接口行为 |
| BFM/VIP | driver、monitor、checker、scoreboard 组合 | 通常不可综合 | 主动发事务、检查协议、覆盖边界场景 |

一句话判断：如果它要放进 FPGA/ASIC 的最终网表，就必须符合可综合 RTL 规则；如果它只是 testbench 里的“外部世界”，就可以使用延迟、事件等待、文件读写、显示任务和随机化。

本章列出的早期供应商和联系方式只适合作为历史背景。今天选择 IP 或 VIP 时，应看厂商/开源项目的维护状态、协议版本、许可证、验证覆盖、仿真器支持和综合目标，不应把早期表格当成当前采购信息。

## 2. 虚拟接口模型解决的是 DUT 边界问题

一个 DUT 只能在环境里暴露真实问题。没有外部模型时，很多接口 bug 不会出现：

| 没有模型时看不到的问题 | 虚拟模型需要提供的能力 |
|---|---|
| DUT 请求太快，外设来不及响应 | 时序限制和 busy/ready 行为 |
| DUT 写信号太窄 | 脉宽检查和警告 |
| DUT 读数据时机错 | 数据有效窗口和高阻态 |
| DUT 没有处理错误状态 | 错误注入、帧错误、奇偶校验错误 |
| 总线被多方驱动 | 三态控制和冲突暴露 |
| 程序/数据输入不可控 | 从文件读入确定的测试数据 |

验证环境的基本边界可以画成：

```text
       stimulus / driver
              |
              v
       +--------------+       external bus/protocol       +----------------+
       |     DUT      | <-------------------------------> | virtual model  |
       +--------------+                                   +----------------+
              |                                                     |
              v                                                     v
          monitor -------------------------------------------> checker
```

虚拟模型不是“帮 DUT 通过测试”的宽松替身，而是“尽量像真实外设一样挑错”的仿真部件。它既要输出正确响应，也要在 DUT 违反手册时主动报错。

## 3. AD7886 模型：用数据手册写一个小型 BFM

AD7886 是一个 8 位三态数据输出的模数转换器。教学模型只保留数字接口的一部分：启动转换输入、忙信号输出和 8 位数据总线输出，并假设片选和读信号始终有效。

| 信号或对象 | 作用 | 建模要点 |
|---|---|---|
| `nconvst` | 低有效转换启动脉冲 | 检测下降沿和上升沿，检查脉宽 |
| `nbusy` | 转换忙标志 | 转换开始后拉低，转换完成后拉高 |
| `data` | 8 位三态数据总线 | 转换期间高阻，数据有效时驱动 |
| `data_mem` | 仿真数据存储 | 用 `$readmemh` 从文件装入样本 |
| `tconv` | 转换时间 | 决定 busy 低电平持续多久 |
| `t5/t8/t9/t12` | 数据手册时序参数 | 控制 busy、数据建立、总线释放、采样保持 |

这个模型的行为可以写成一条时间线：

```text
nconvst 下降沿
  -> 计算/更新本次时序参数
  -> t5 后 nbusy 拉低
  -> t9 后关闭 data 三态输出

nconvst 上升沿
  -> tconv 后 nbusy 拉高
  -> tconv - t8 后把 data_mem[i] 放入 databuf
  -> 打开 data 三态输出
```

代码中有三类 Verilog 构造值得学习：

| 构造 | 在模型中的作用 | 为什么不可当作普通可综合 RTL |
|---|---|---|
| `#t5`、`#tconv` | 直接表达器件延迟 | 综合器不会把任意仿真延迟变成硬件 |
| `fork ... join` | 并行安排 busy 和总线动作 | 属于仿真行为组织方式 |
| `$readmemh` | 从文件加载转换结果 | 可用于仿真存储初始化，综合语义依工具和场景受限 |
| `$display` | 输出错误提示 | 只属于仿真可观察性 |
| `$random` | 制造转换时间扰动 | 不代表硬件随机源 |
| 三态 `8'bzz` | 模拟外部数据总线释放 | 顶层 I/O 可用，片内实现需谨慎 |

AD7886 模型最有价值的不是“能吐出数据”，而是能抓两类错误：

| 检查 | 触发条件 | 暴露的 DUT 问题 |
|---|---|---|
| 启动请求太快 | busy 刚结束后 `t12` 内又请求转换 | 采样保持时间不够，DUT 没等外设恢复 |
| `nconvst` 脉宽不合格 | 负脉冲太窄或太宽 | 控制 FSM 没按器件手册产生启动脉冲 |

写虚拟接口模型的一般步骤：

1. 从数据手册抽取端口、有效电平、数据宽度和三态关系。
2. 把关键时序参数写成可读的 `parameter` 或内部变量。
3. 用事件边沿描述外设状态变化，而不是凭感觉给固定输出。
4. 给输入协议加检查，错误时输出具体原因。
5. 用文件或任务提供可控数据，便于构造边界测试。
6. 明确标注哪些行为被简化，避免把教学模型误当完整器件模型。

## 4. 精确虚拟模型比普通 testbench 更难

普通 testbench 可以只服务一个实验；虚拟器件模型要在很多场景里替代真实芯片。它的质量要求更高：

| 质量维度 | 低质量模型的表现 | 合格模型的表现 |
|---|---|---|
| 接口完整性 | 只连了几个常用信号 | 端口、有效电平、三态和状态输出清楚 |
| 时序准确性 | 延迟随手写 | 参数来自手册，边界可检查 |
| 错误检测 | DUT 错了也沉默 | 脉宽、保持、恢复、非法模式能报警 |
| 可控输入 | 只能输出固定数据 | 可从文件、任务、随机或事务输入数据 |
| 可定位性 | 只说结果错 | 能指出哪类协议或时序违例 |
| 边界说明 | 看起来像完整芯片 | 明确哪些功能未建模 |

ASIC 投片前的仿真模型尤其不能马虎。真实外设不会因为模型没写某个约束就自动变宽容；模型漏掉的时序检查，可能会把接口 bug 留到板级或硅后才暴露。

## 5. USART 8251A：复杂接口模型要拆成任务、事件和状态

USART 8251A 模型比 AD7886 复杂得多，因为它同时包含 CPU 并行总线接口、发送器、接收器、同步/异步模式、错误状态和时序检查。

可以把它拆成五个层次：

| 层次 | 典型对象 | 作用 |
|---|---|---|
| 端口和总线 | `dbus`、`read_`、`write_`、`chipsel_`、`comdat_` | 模拟 CPU 读写 8251A 的并行接口 |
| 状态寄存器 | `status`、`command`、`modreg`、`rxrdy/txrdy/txe` | 保存模式、命令、发送接收状态 |
| 时序检查 | 读脉宽、写脉宽、地址保持、数据保持、复位脉宽 | DUT 违反接口时输出提示 |
| 发送路径 | `tdata_out`、`tdata_hold`、`txd`、`txc_` | 按波特率发 start/data/parity/stop 或 sync 字符 |
| 接收路径 | `receivebuf`、`rdata`、`rcd`、`rxc_` | 接收同步/异步串行数据，检查奇偶、帧错、溢出 |

模型中大量使用 `task`：

| 任务类型 | 例子 | 设计意图 |
|---|---|---|
| 错误报告任务 | frame error、parity error、overrun error | 把错误置位和打印集中管理 |
| 地址/脉宽监视任务 | read/write address watch | 在读写周期内并行监视控制信号是否稳定 |
| 发送任务片段 | 发送保持数据、空闲发送、同步字符发送 | 把串行输出流程拆成可读阶段 |
| 接收任务片段 | 同步接收、异步接收、奇偶校验、标记接收完成 | 把协议细节从主控制流里拆出 |

还使用事件来组织复杂流程：

```text
reset event -> 初始化寄存器和状态
tx end event -> 判断发送保持数据还是进入空闲
start receiver event -> 按同步/异步模式启动接收
sync hunt event -> 在比特流中寻找同步字
break detect event -> 检测异步接收线长时间为低
```

这些写法非常适合行为模型，但不要误读成可综合控制器模板。`wait`、`event`、`fork/join`、`#delay`、`$display` 和无限 `forever` 行为过程，都是验证环境常用结构，不应混入要综合的 RTL 数据通路。

## 6. 8085A 行为模型：处理器也可以作为外部总线模型

Intel 8085A 行为模型展示了另一种虚拟接口：不是模拟一个简单外设，而是模拟一个能主动取指、读写存储器、响应中断和驱动总线的处理器。

它的结构可以按处理器行为拆开：

| 组成 | 典型信号或变量 | 作用 |
|---|---|---|
| 寄存器组 | `pc/sp/acc/regb/.../ir` | 保存处理器状态 |
| 总线驱动 | `ad/a/readout/writeout/iomout` | 模拟地址、数据和控制总线 |
| 内部时钟事件 | `ec1/ec2` | 把外部时钟拆成处理器内部节拍 |
| 复位序列 | `reset_sequence` | 设置 PC、寄存器、中断和总线控制 |
| 取指执行 | `execute_instructions` | 发地址、读指令、译码、执行 |
| 存储器/I/O 任务 | `memread/memwrite/ioread/iowrite` | 用任务表达总线周期 |
| 等待/保持/中断 | `ready_hold/holdit/checkint/interrupt` | 处理外部 ready、hold 和中断请求 |

一个处理器 BFM 的核心价值是主动生成总线事务：

```text
取指周期：PC -> 地址总线，read 有效，采样 AD 总线为指令
存储器读：目标地址 -> 地址总线，read 有效，等待 ready，采样数据
存储器写：地址和数据建立，write 有效，等待 ready，释放总线
I/O 读写：使用 I/O 选择信号和端口地址完成外设访问
```

这类模型适合验证外设或总线接口：DUT 可以作为 8085A 的外围电路，被处理器模型发起读写事务。如果 DUT 对 ready、hold、中断、读写时序处理错误，模型能在仿真中把问题暴露出来。

## 7. 现代验证中这些模型对应 BFM、VIP 和 cocotb/UVM 组件

本章虽然使用较早期的 Verilog 行为模型，但思想今天仍然有效。

| 本章概念 | 现代对应 | 说明 |
|---|---|---|
| 虚拟接口模型 | Bus Functional Model | 按协议驱动和响应接口信号 |
| 商业虚拟接口 | Verification IP | 带 driver、monitor、checker、功能覆盖率的验证组件 |
| AD7886 模型 | 外设响应模型 | 模拟 ready/busy/data 和时序限制 |
| 8251A 模型 | 协议级外设 VIP 雏形 | 发送、接收、错误注入、状态寄存器 |
| 8085A 模型 | CPU/总线 master BFM | 主动产生读写和中断相关事务 |
| `$display` 警告 | assertion/checker | 今天可用 SVA、UVM report、scoreboard 更系统地报错 |
| `$readmemh` 数据文件 | stimulus vectors / memory image | 用可控输入构造回归测试 |

在 cocotb 或 UVM 中，通常会把一个模型拆成：

| 组件 | 作用 |
|---|---|
| driver | 把事务转换成引脚波形 |
| monitor | 从引脚波形还原事务 |
| sequencer/sequence | 产生正常、随机和边界事务 |
| scoreboard | 比较 DUT 输出和期望结果 |
| checker/assertion | 检查协议时序、握手、互斥和非法状态 |
| 功能覆盖率 | 记录哪些模式、边界、错误场景被测过 |

所以不要把“行为模型”理解成随便写一段模拟代码。高质量行为模型本质上是验证资产。

## 8. 常见误用和判断规则

| 误用 | 为什么错 | 判断规则 |
|---|---|---|
| 把虚拟接口模型拿去综合 | 模型里可能有延迟、事件、文件读写和无限等待 | 看到 `#`、`wait`、`event`、`fork/join`、`$display`，默认属于仿真环境 |
| 模型只给正确响应，不检查错误 | DUT 违反协议时可能也通过 | 模型至少要检查关键脉宽、保持、恢复和非法请求 |
| 只按理想时序建模 | 真实外设有延迟和有效窗口 | 数据有效、busy、ready、高阻释放必须有时序关系 |
| 没有边界说明 | 读者以为教学模型等同完整器件 | 明确哪些信号、模式、模拟特性被省略 |
| 把历史供应商表当当前资料 | 供应商、协议版本和 IP 形态会变化 | 当前选型必须查官方资料和维护状态 |
| 模型过于宽松 | 接口 bug 被吞掉 | 模型要像真实外设一样不配合错误时序 |
| 模型过于复杂但无检查 | 代码很长，验证价值仍低 | 长模型必须能定位失败原因 |

最实用的自问句：

```text
这个模块是在描述我要造的硬件，还是在描述硬件周围的世界？
如果 DUT 把请求发早一拍、晚一拍、窄一拍，这个模型会不会报错？
```

## 9. 和 AI+IC 验证的连接

AI 芯片设计里，虚拟器件和接口模型是日常工具，不是附加知识。

| AI+IC 场景 | 需要的模型 | 检查重点 |
|---|---|---|
| NPU 读写 SRAM | SRAM 行为模型或 memory BFM | 地址、写使能、读延迟、数据一致性 |
| NPU 通过 AXI 访问 DDR/HBM | AXI master/slave VIP | valid/ready、burst、ID、响应、乱序 |
| 卷积控制器读取输入流 | ADC/streaming BFM | sample valid、backpressure、采样间隔 |
| 指令流控制 NPU | 命令寄存器 BFM 或 CPU BFM | 配置顺序、启动、完成、中断 |
| 算子验证 | golden model + memory image | 输出 tensor 与参考模型一致 |
| 片上网络/NoC | router/link BFM | 流控、拥塞、死锁、包顺序 |

一个 NPU 小项目的最小验证环境可以这样搭：

```text
Python/文件生成输入激活和权重
  -> memory model 提供数据
  -> DUT 执行卷积或矩阵乘
  -> monitor 收集输出
  -> golden model 计算期望结果
  -> scoreboard 比较
  -> assertion 检查握手、地址范围和状态机不死锁
```

这条链路和本章 AD7886/8251A/8085A 的思想一致：真实硬件还没在板子上出现，仿真环境先把它会遇到的外部世界搬进来。

## 10. 自测题

1. 虚拟器件、软核 IP、虚拟接口模型三者的主要区别是什么？
2. 为什么虚拟接口模型通常不需要可综合？
3. AD7886 模型中 `nconvst`、`nbusy`、`data` 分别模拟了什么？
4. `$readmemh` 在 ADC 模型中解决了什么验证问题？
5. 为什么 AD7886 模型要检查启动脉冲宽度和相邻转换间隔？
6. 8251A 模型为什么需要错误报告任务和时序监视任务？
7. 8085A 行为模型为什么适合用来验证外设或总线接口？
8. 看到一个 Verilog 模块里有 `#delay`、`event`、`wait`，你应该先判断它属于哪一层？
9. BFM、VIP、driver、monitor、scoreboard 分别承担什么角色？
10. 在 NPU SRAM 控制器验证中，虚拟 SRAM 模型至少要检查哪些行为？

答案检查口径：

- 能明确区分 DUT、仿真环境和可综合 IP。
- 能按数据手册信号和时序重建一个小型外设行为模型。
- 能解释行为模型为什么要主动报错，而不是只返回理想数据。
- 能把本章早期 Verilog 行为模型映射到现代 BFM/VIP/cocotb/UVM 验证结构。
- 能为 AI+IC 小模块设计一个最小但可定位失败的仿真环境。
