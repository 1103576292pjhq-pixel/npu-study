# 任务103：综合的基本概念

## 本章知识全景图

逻辑综合解决的是一个硬件工程问题：RTL 代码已经能仿真，但它还不是芯片上真实存在的门、电路和时序路径；综合把 `RTL + 工艺库 + 约束` 转成后端可以继续布局布线的门级网表。

| 知识块 | 你要回答的问题 | 直接结论 |
|---|---|---|
| 广义综合与狭义综合 | “综合”到底覆盖多大范围 | 广义是 idea/spec 到真实器件；本课默认讲狭义逻辑综合，即 RTL 到 gate-level netlist |
| 综合在 IC flow 中的位置 | 综合前后分别由谁交付 | 前端交付 RTL、约束和验证证据；综合输出 gate-level netlist、报告和后端入口数据 |
| DC top-level flow | 一次综合脚本为什么不是只打一条 `compile` | 工具必须先读库和设计，再读约束，之后综合、分析 QoR，最后写出设计数据 |
| 三类 transformation | RTL 为什么能变成具体工艺门 | `translation` 变成 GTECH，`mapping` 绑定 target library，`optimization` 按时序/DRC/面积功耗改结构 |
| 约束与 QoR | 为什么无约束网表不等于可交付网表 | 约束定义目标，QoR 判断结果；没有目标，综合只是在生成某种可实现结构 |
| DC 三种接口 | GUI、shell、batch 分别什么时候用 | GUI 用来看结构，interactive shell 用来试命令和 debug，batch 用来正式可复现交付 |
| Tcl 与 UNIX-like 命令 | 为什么综合工程离不开脚本 | DC flow 本质是 Tcl 控制的 EDA 自动化流程，脚本决定可重复性和可审计性 |

最短学习路径：先把综合放回数字 IC 设计流，确认它的输入输出；再把 `compile` 拆成 translation、mapping、optimization；最后用 Tcl/batch 把流程固化成可重复脚本。

看图要点：红笔把 idea、spec、RTL、真实芯片分开，入口问题不是“工具多强”，而是“当前这门课里的 synthesis 只覆盖哪一段交付链”。

## 1. 广义综合是“想法到芯片”，狭义综合是“RTL 到门级网表”

本课里的综合不是把需求文档自动变成芯片；Design Compiler 这一段主要做狭义逻辑综合。

两个层级要分开：

| 层级 | 输入 | 输出 | 边界 |
|---|---|---|---|
| 广义 synthesis | idea、spec、architecture、算法需求 | 可制造、可测试、可工作的 real device | 覆盖完整设计流，包含架构、RTL、验证、综合、后端、制造测试 |
| 狭义 logic synthesis | RTL、technology library、constraints | gate-level netlist、timing/area/power/DRC reports | 只把逻辑描述转成门级实现，不直接做 placement/routing |

初学者最容易错在把“综合”理解成“工具替你做设计”。工具不能决定你的微架构、流水线边界、状态机协议或 CDC 策略；它只在你给定 RTL 行为、工艺库能力和约束目标后，尝试生成一个等价且满足目标的门级结构。

对 AI+IC 学习来说，这个边界很关键。NPU 里的 MAC 阵列、DMA、buffer controller、NoC 接口，必须先由工程师写出可综合 RTL；综合工具不会凭空替你推导这些体系结构。

## 2. 综合位于 RTL 验证之后、APR 之前，是前后端交付分界点

综合之前，核心问题是“行为是否正确”；综合之后，核心问题开始变成“这个行为能否在工艺、时序、面积、功耗约束下落到硬件”。

看图要点：IC flow 的重点不是背流程名，而是看清每个阶段把什么交给下一个阶段。

![综合在 IC flow 中的位置](<./screenshots/任务103_综合的基本概念/task103_dense_0600s_00h10m00s.png>)

| 阶段 | 主要对象 | 成功信号 | 失败信号 |
|---|---|---|---|
| Idea/spec | 功能目标、接口需求、性能指标 | 需求可拆成模块、接口、约束 | 需求无法转成明确输入输出或时序目标 |
| Functional description | 流程图、算法描述、文本规格 | 算法链路和状态变化清楚 | 只讲功能愿望，没有可实现结构 |
| RTL design | Verilog/SystemVerilog/VHDL | 模块层次、端口、时钟复位、状态机清楚 | 不可综合写法、隐式 latch、跨时钟不安全 |
| RTL simulation and verification | testbench、断言、波形、覆盖率 | 功能行为匹配 spec | 只跑 happy path，未覆盖边界和异常 |
| Logic synthesis | RTL、library、SDC | gate-level netlist，timing/area/power/DRC reports | 找不到库/模块，时序违例，DRC 违例 |
| Physical implementation/APR | netlist、约束、工艺物理数据 | placement/routing 完成，物理时序收敛 | 拥塞、hold/setup 违例、物理 DRC |
| Tape out/Post-silicon/DFT | GDS、测试结构、测试向量 | 可制造、可测试、芯片回片可验证 | 可测性差、硅后行为与仿真不一致 |

因此，RTL 工程师不能只追求“仿真能过”。如果代码写法让综合器难以推断触发器、MUX、RAM、clock gating 或握手逻辑，后面会在综合和 APR 阶段付出代价。

## 3. DC top-level flow 是五步，每一步都有可检查结果

一次最小综合 flow 可以压成五个动作：读入设计和库，施加约束，综合，分析结果，写出交付物。

看图要点：这张 top-level flow 图把 `target library`、constraints、QoR、gate-level netlist 串成证据链，说明综合不是一条 `compile` 命令，而是每一步都要留下可检查结果。

![Top-level synthesis flow](<./screenshots/任务103_综合的基本概念/task103_dense_1080s_00h18m00s.png>)

```text
1. Load library and design
2. Apply timing constraints and design rules constraints
3. Synthesize the design
4. Analyze the results
5. Write out the design data
```

这五步不是形式流程，而是逐步把“设计对象”和“目标条件”放进工具：

| 步骤 | 输入 | 工具内部发生什么 | 你要检查什么 |
|---|---|---|---|
| Load library and design | `.v/.sv`、`.db/.lib`、必要 IP/宏单元 | DC 建立 design objects 和 library objects | top 是否正确、子模块是否全读入、库是否存在 |
| Apply constraints | SDC、设计规则、时钟/IO/负载 | 工具知道优化目标和边界 | clock 是否创建、input/output delay 是否合理、DRC 约束是否生效 |
| Synthesize | RTL、库、约束 | 进行 translation、mapping、optimization | 是否报 unresolved reference、unsupported construct、timing impossible |
| Analyze | timing/area/power/constraint reports | 评估 QoR | WNS/TNS、area、power、max fanout/transition/capacitance |
| Write out | mapped netlist、DDC、SDC、reports | 把内存中的结果落盘 | 输出文件是否存在、是否是 mapped gate-level netlist |

综合工程的基本态度是“每一步都留下证据”。只看到 `compile_ultra` 跑完，不等于设计可交付；必须看报告，确认它是否满足约束。

## 4. `compile` 不是一个黑盒按钮，而是三类 transformation

`compile` 的核心链路是 translation -> gate mapping -> logic optimization。把这三步分开，才能理解为什么同一份 RTL 在不同库、不同约束下会产生不同网表。

看图要点：这张转换总图要按三段读，先让 RTL 变成工具可处理的通用逻辑，再按约束重写，最后才落到目标库标准单元。

![Synthesis transformations 总图](<./screenshots/任务103_综合的基本概念/task103_dense_1440s_00h24m00s.png>)

| transformation | 解决的问题 | 输入 | 输出 | 关键误区 |
|---|---|---|---|---|
| Translation | 先把 RTL 变成工具内部能处理的通用逻辑 | Verilog/VHDL RTL | GTECH/generic netlist | 以为 translation 已经绑定具体工艺 |
| Gate mapping | 把通用逻辑映射到目标工艺库的标准单元 | GTECH + target library | mapped netlist | 以为 mapping 后一定满足时序和 DRC |
| Logic optimization | 在逻辑等价前提下修 timing、DRC、area、power | mapped netlist + constraints | optimized mapped netlist | 以为优化只会“变快”，不会引入面积/功耗权衡 |

这也是为什么改一条约束、换一个工艺库、调整一个 RTL 写法，最后网表可能发生明显变化。综合不是单纯翻译语言，而是在目标库和约束空间里寻找实现。

可以把综合看成把架构草图变成符合材料和施工规范的施工图：translation 是把草图翻成工地能读的通用图纸，mapping 是从材料库里选具体砖瓦梁柱，optimization 是在不改房屋功能的前提下调整梁柱粗细、支撑位置和走线长度。这个比喻的边界也要记住：施工队不能替你决定这栋楼该有几层，综合器也不能替你决定 NPU 的流水线级数、buffer 切分或总线协议。

## 5. Translation 生成 GTECH：它是工艺无关的中间网表

Translation 的任务是把 RTL 写法统一成工具内部表示；这个阶段重点是“看懂 RTL”，不是“选 40nm 还是 55nm 的某个 cell”。

看图要点：这张图只证明 translation 得到的是 generic technology netlist，还没有目标库 cell 属性。

![Translation 到 GTECH netlist](<./screenshots/任务103_综合的基本概念/task103_dense_1800s_00h30m00s.png>)

可以把这一阶段看成两件事：

1. 识别 RTL 语义：组合逻辑、寄存器、MUX、case、if/else、加法器、比较器、状态机等。
2. 转成通用结构：用 GTECH/SEQGEN 等内部对象表达这些逻辑，暂时不绑定某个制造厂库的具体标准单元。

Translation 失败通常说明 RTL 入口有问题，而不是时序优化问题。常见失败信号包括：

- 语法或 elaboration 错误。
- top module 不正确。
- 子模块没有读入，层次无法展开。
- 使用不可综合语句，或综合器无法推断目标硬件。
- 时钟、复位、赋值风格导致 latch 或不期望的寄存器推断。

在 NPU/数字前端项目里，translation 阶段会暴露很多“仿真写法”和“综合写法”的差异。例如 testbench 里可以用 `#10` 延迟控制时间，RTL 可综合逻辑不能靠这种延迟生成硬件。

## 6. Gate mapping 绑定 target library：通用逻辑变成真实标准单元

Mapping 的关键动作是“把通用网表中的逻辑节点，替换成 target library 里真实存在的 cell”。

看图要点：mapping 图的主角是 GTECH 到标准单元的身份变化，generic 逻辑从这一刻开始被 target library 约束。

![Gate mapping 到标准单元](<./screenshots/任务103_综合的基本概念/task103_dense_1920s_00h32m00s.png>)

Mapping 后，网表会从抽象逻辑变成类似下面的结构：

```verilog
NAND2_X1 U17 (.A(n3), .B(n5), .ZN(n8));
DFFR_X2  U21 (.D(next_state[0]), .CK(clk), .RN(rst_n), .Q(state[0]));
BUF_X4   U33 (.A(req), .Z(req_buf));
```

这些名字不是 RTL 工程师随便定义的模块，而是工艺库里的标准单元。每个 cell 有面积、引脚、电容、延迟、功耗、驱动能力和可用 corner。工具选择哪一个 cell，取决于 target library 里有什么，以及约束要求什么。

Mapping 成功只说明“能用这个库里的 cell 表达逻辑”。它不保证：

- setup/hold 已经满足。
- fanout、transition、capacitance 都满足。
- 面积和功耗达到目标。
- 结构适合后端布局布线。

所以 mapped netlist 还需要 optimization。

## 7. Logic optimization 是在多目标约束下改结构

Optimization 不是把电路“随便优化得更好”，而是在保持逻辑等价的前提下，围绕 timing、DRC、area、power 做取舍。

看图要点：这张图不要只背 max-fanout、max-transition 等名字，而要看清这些约束决定综合器允许把逻辑改到什么程度。

![Logic optimization 约束目标](<./screenshots/任务103_综合的基本概念/task103_dense_2280s_00h38m00s.png>)

常见优化动作可以这样理解：

| 动作 | 触发原因 | 结果 | 代价 |
|---|---|---|---|
| cell sizing | 某条路径太慢，需要更强驱动 | 把 `X1` 换成 `X2/X4` 等更大单元 | 面积和功耗上升 |
| buffer insertion | 长线或大负载导致 transition/fanout 违例 | 插入 buffer 分担负载 | 增加级数和面积 |
| load splitting | 一个驱动端挂太多负载 | 分裂成多支负载树 | 结构变复杂 |
| logic restructuring | 原逻辑结构不利于时序 | 重新组织等价逻辑 | 可能改变网表形状，增加验证难度 |
| leakage/area recovery | 时序有余量时降低面积或漏电 | 用小单元或低漏电单元替换 | 可能吃掉时序余量 |

一个典型判断口径是：如果 setup 违例，工具可能加大驱动或重构逻辑；如果 max transition 违例，工具可能插 buffer；如果 max fanout 违例，工具可能把负载分组；如果面积过高，工具可能在不破坏时序的前提下回收大 cell。

因此，综合报告不能只看一个数字。时序、面积、功耗、DRC 是联动的：把时序修好可能牺牲面积；压面积可能让 critical path 变慢；压漏电可能影响性能库选择。

优化也有边界。若只是单个高 fanout 控制信号导致 transition 违例，综合器可以复制驱动或插 buffer；若是一条 MAC 数据通路在一个周期里塞进过多乘加和 mux，工具可能已经把 cell 放大到极限仍然负 slack，这时问题就不再是“换一个更猛的 compile option”，而是要回 RTL 改 pipeline、切状态、重分配时钟周期。

## 8. 约束定义目标，QoR 证明结果

约束文件不是综合流程的附属品，而是告诉工具“什么叫合格结果”的合同。

常见约束可以按问题分类：

| 约束类型 | 回答的问题 | 缺失后果 |
|---|---|---|
| `create_clock` / clock period | 芯片要跑多快 | 工具不知道 setup 目标，路径优化失去方向 |
| input/output delay | 外部模块给本模块留下多少时序预算 | IO 路径可能在系统级不收敛 |
| load / driving cell | 外部负载和输入驱动能力是什么 | 输出 transition、输入 arrival 估计失真 |
| max fanout | 一个驱动端最多挂多少负载 | 可能产生难以布线或 transition 过慢的网 |
| max transition | 信号边沿允许多慢 | 慢边沿会放大延迟、功耗和可靠性风险 |
| max capacitance | 输出端允许看到多大电容 | 过大负载会破坏 cell timing model 假设 |
| max area / leakage | 面积或漏电预算 | 工具可能过度用大单元换速度 |

QoR 是 Quality of Results，常用报告包括：

- `report_timing`：看 critical path、WNS/TNS、setup/hold。
- `report_area`：看组合逻辑、寄存器、层次面积。
- `report_power`：看 dynamic/leakage 估计。
- `report_constraint -all_violators`：集中看违反约束的对象。
- `check_design` / `check_timing`：看设计和约束是否存在基础问题。

合格的综合不是“生成了 `.v` 文件”，而是“生成的网表在当前约束和库模型下有可解释的 QoR 结果，并且违例被确认或修掉”。

一个最小复现闭环是：`check_timing` 先证明约束完整，`report_timing` 找到最差路径，`report_constraint -all_violators` 集中列出仍未满足的规则。若 `report_timing` 没有目标 clock、路径被报 unconstrained，或者 violators 里 max transition/max fanout 大面积残留，就不能把 mapped netlist 当成合格交付。

## 9. GUI、interactive shell、batch 是三个不同工作姿势

DC 的三种入口对应三个阶段：先看懂、再调试、最后自动化。

看图要点：三种接口图要分工阅读，GUI 建立结构画面，interactive shell 用来试命令和定位，batch 才是正式可复现入口。

![Design Compiler 三种接口](<./screenshots/任务103_综合的基本概念/task103_dense_2520s_00h42m00s.png>)

| 入口 | 典型命令 | 最适合 | 不适合 |
|---|---|---|---|
| Design Vision GUI | `design_vision -topographical_mode` | 看层次、schematic、cell、路径和属性，适合初学建立画面感 | 正式批量回归和稳定交付 |
| DC Shell interactive | `dc_shell -topographical_mode` | 单步试 Tcl 命令、查对象属性、定位报错 | 每次从头手敲完整 flow |
| Batch mode | `dc_shell -topo -f run.tcl | tee DC.log` | 正式综合、可重复运行、保留日志和结果 | 初次探索时反馈不如交互模式直接 |

工程上不应该只会 GUI。GUI 能帮你理解层次，但真正交付需要脚本；脚本能被版本管理、复跑、比较报告，也能在服务器上无人值守运行。

## 10. DC flow 本质是 Tcl：读懂脚本才能读懂综合

综合脚本里的命令不是“工具界面操作记录”，而是 Tcl 程序。掌握基础语法后，DC flow 会从一串神秘命令变成可维护工程文件。

看图要点：Tcl 规则图的价值在于把综合 flow 从“手工操作”变成“可审计程序”，尤其是续行、注释、`source` 和命令缩写边界。

![Tcl 脚本规则](<./screenshots/任务103_综合的基本概念/task103_dense_2760s_00h46m00s.png>)

| 规则 | 含义 | 例子 |
|---|---|---|
| `\` | 当前命令未结束，下一行继续 | `create_clock ... \` 后接下一行参数 |
| `#` | 注释，后面内容不执行 | `# read RTL files` |
| `;` | 同一行写多个命令 | `pwd; history` |
| `source file.tcl` | 读取并执行另一个 Tcl 文件 | `source constraints.tcl` |
| 命令缩写 | 只有唯一匹配时才可缩写 | `get_attr` 若不歧义才可短写 |

一个更接近工程的骨架如下：

```tcl
set_app_var search_path ". ./rtl ./libs ./cons"
set_app_var target_library "ss40_wc.db"
set_app_var link_library "* ss40_wc.db"

read_verilog ./rtl/top.v

```

这段脚本包含了本课的主要概念：设计数据、库数据、约束、link、compile、report、write out。

## 11. UNIX-like DC shell 命令是调试工具，不是综合核心

交互模式下常用的 `pwd`、`cd`、`ls`、`history`、`!!`、`!5`、`!report`、`sh`，目标是提高定位效率。

看图要点：DC shell 常用命令图只负责调试效率，不能把它误读成综合核心流程。

![DC shell 常用命令](<./screenshots/任务103_综合的基本概念/task103_dense_2880s_00h48m00s.png>)

| 命令 | 用途 |
|---|---|
| `pwd` | 看当前工作目录，确认相对路径从哪里开始 |
| `cd` | 切换目录 |
| `ls` | 查看当前目录文件 |
| `history` | 查看已经执行过的命令 |
| `!!` | 重复上一条命令 |
| `!5` | 执行历史记录中第 5 条命令 |
| `!report` | 执行最近一条以 `report` 开头的命令 |

## 12. 本课在数字前端/NPU 学习中的位置

这节课是从 RTL 编码转入 EDA flow 的入口。前面写状态机、FIFO、总线、CDC 时，重点是功能正确；从综合开始，代码还要面对工艺库、时序、面积、功耗和工具可解释性。

在 NPU 或 AI 加速器项目中，下面这些问题都会回到本课：

- 一个多级 MAC pipeline 是否能在目标频率下收敛。
- SRAM wrapper、寄存器堆、乘加器 IP 是否能被 link library 正确解析。
- 大 fanout 控制信号是否需要复制寄存器或插 buffer。
- 宽数据通路是否因为组合链太长导致 setup 违例。
- RTL 中的不可综合写法是否在 translation 阶段就失败。
- 约束是否真实描述了系统时钟、IO 边界和模块环境。

真正的数字前端交付不是“我写完 RTL 了”，而是“我的 RTL 能被综合，综合报告可解释，违例有闭环，后端能接着做”。

## 本章收束与检查

- 广义综合覆盖 idea/spec 到真实器件；本课重点是狭义逻辑综合。
- 狭义逻辑综合的输入是 RTL、technology library、constraints，输出是 gate-level netlist 和 QoR reports。
- 综合位于 RTL 仿真验证之后、APR 之前，是前端进入后端的关键交付点。
- DC top-level flow 是 load -> constrain -> synthesize -> analyze -> write out。
- `compile` 内部可以拆成 translation、gate mapping、logic optimization。
- GTECH/generic netlist 不绑定具体工艺；mapped netlist 才使用 target library 标准单元。
- Optimization 必须同时考虑 timing、DRC、area、power，不是单目标“变快”。
- GUI 用来看结构，interactive shell 用来 debug，batch 用来正式交付。
- Tcl 是综合自动化的控制语言；不会读脚本，就很难稳定维护综合 flow。

## 自测题

1. 狭义逻辑综合的输入和输出是什么？  
   答：输入是 RTL、technology library、constraints；输出是 gate-level netlist、DDC/中间数据库、timing/area/power/constraint 等报告。核心交付是后端能继续使用的门级网表和可解释 QoR。

2. Translation 和 gate mapping 的根本差别是什么？  
   答：translation 把 RTL 转成工具内部的 generic/GTECH 表示，不绑定具体工艺；gate mapping 把 generic 逻辑映射成 target library 里真实存在的标准单元。

3. 为什么 mapping 后还要 optimization？  
   答：mapping 只说明逻辑能被目标库表达，不保证满足 setup/hold、max fanout、max transition、max capacitance、面积或功耗目标。optimization 在逻辑等价前提下调整 cell、buffer 和结构来满足这些约束。

4. 没有 timing constraints 的综合结果为什么不能直接交付？  
   答：工具不知道目标时钟、IO 边界和负载，无法判断路径该优化到什么程度。结果可能有网表文件，但不代表能在系统目标频率下工作。

5. `dc_shell -topo -f run.tcl | tee DC.log` 为什么适合正式 flow？  
   答：它用 batch 方式执行完整脚本，并把输出保存到 log，便于复现、比较和追踪错误；比手工点 GUI 或逐条输入命令更适合工程交付。

6. `sh cp a.tcl backup/` 里的 `sh` 做什么？  
   答：让 DC shell 调用操作系统 shell 执行 `cp`。不加 `sh` 时，DC shell 可能把 `cp` 当成 DC/Tcl 命令解析而失败。

7. 如果一个 RTL 模块仿真通过但综合 translation 失败，优先怀疑什么？  
   答：优先怀疑不可综合语句、模块层次未读入、top 设置错误、时钟复位/赋值风格不规范，或某些仿真专用写法进入了 RTL。

8. AI 加速器里的大 fanout `valid` 控制信号为什么会成为综合问题？  
   答：它可能违反 max fanout、max capacitance 或 max transition。综合器可能插 buffer、复制逻辑或调整结构；RTL 工程师也可能需要从架构上分区控制，不能只靠工具兜底。

## 练习与检查动作

拿一个简单寄存器或小 FSM，写出一份最小综合脚本骨架，至少包含：

```tcl
read_verilog
set_app_var target_library
set_app_var link_library
current_design
link
source constraints.tcl
check_timing
compile_ultra
report_timing
report_area
write -format verilog
```

检查标准：

- 能说清每条命令属于 load、constrain、synthesize、analyze、write out 中哪一步。
- 能解释 target library 和 link library 的职责差异。
- 能指出如果缺少 clock constraint，`report_timing` 的意义会变弱。
- 能在报告中找到至少一个 timing 或 constraint 检查入口。
