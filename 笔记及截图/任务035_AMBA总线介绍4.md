# 任务35：AMBA总线介绍4

## 本章知识全景图

这一讲把 AHB 从“传输信号和 burst 地址”推进到“总线系统如何决定谁被访问、谁必须响应、谁拿到总线”。如果任务32-34解决的是一次 AHB 传输怎么跑起来，那么任务35解决的是系统级的三个问题：地址怎么译码成 `HSELx`，slave 如何用 `HREADY/HRESP/HRDATA` 给出确定响应，多个 master 如何由 arbiter 分配总线。

| 层级 | 核心概念 | 本章要形成的判断 | 连接到前端交付 |
|---|---|---|---|
| 地址空间 | `HADDR`、地址窗口、1KB 最小粒度 | 一个地址必须命中某个 slave 或 default slave | memory map、地址译码 RTL、非法地址测试 |
| 从设备选择 | decoder、`HSELx` | `HSELx` 是 decoder 输出，不是 master 直接指定 | AHB interconnect、slave select、默认分支 |
| 从设备响应 | `HRDATA`、`HREADY`、`HRESP` | slave 被选中后不能沉默，必须完成、等待或报错 | 波形验收、错误响应、wait state |
| 异常响应 | `ERROR`、`RETRY`、`SPLIT` | 非 OKAY 响应会打断流水，所以需要两周期语义 | master 状态机、arbiter 策略、异常 testcase |
| 数据与字节 | `HWDATA`、`HRDATA`、`HSIZE`、endianness | AHB 内部读写数据分开，byte lane 由大小端规则解释 | byte enable、寄存器访问、8/16/32-bit 访问 |
| 仲裁 | `HBUSREQx`、`HGRANTx`、`HMASTER`、`HLOCKx`、`HSPLITx` | `HGRANT` 只是许可，`HREADY` 为高时 master 才真正接管 | 多 master SoC、DMA/CPU 争用、锁定传输 |

最短学习路径：

```text
memory map
  -> address decoder
  -> HSELx 选中一个 slave
  -> slave 用 HREADY/HRESP/HRDATA 响应
  -> 非 OKAY 响应影响 master 下一步
  -> arbiter 决定多个 master 谁能继续用总线
```

## 1. `HSELx` 是地址译码的结果，不是 master 的愿望

AHB master 发出地址和控制信息，但它不直接指定“我要访问 slave 2”。真正把地址翻译成 slave 选择信号的是 decoder：输入是 `HADDR`，输出是一组 `HSELx`。

![HSEL 与地址译码](<./screenshots/任务035_AMBA总线介绍4/task35_00_hselect_decoder_00m50s.jpg>)

视觉核验/看图要点/漏看后果：00:50-01:05，这张图的教学职责是把“地址进入 decoder，再产生唯一 `HSELx`”定住。先看 `HADDR` 进入译码器，而不是 master 直接连到某个 slave；再看 decoder 输出一组互斥 select。漏看这一点，后面很容易把 memory map、slave select 和 master “点名访问”混成一件事。`x` 表示有多个 slave 编号，不表示低有效；低有效通常才用 `n`，如 `HRESETn`。

工程里可以把 decoder 想成 memory map 的硬件化版本。文档里写：

```text
0x0000_0000 - 0x0000_EFFF  -> SRAM
0x0002_0000 - 0x0003_FFFF  -> Flash
其他地址                     -> default slave
```

RTL 里就要变成互斥的地址范围判断：

```systemverilog
always_comb begin
    hsel_sram    = 1'b0;
    hsel_flash   = 1'b0;
    hsel_default = 1'b0;

    if (haddr inside {[32'h0000_0000:32'h0000_EFFF]}) begin
        hsel_sram = 1'b1;
    end else if (haddr inside {[32'h0002_0000:32'h0003_FFFF]}) begin
        hsel_flash = 1'b1;
    end else begin
        hsel_default = 1'b1;
    end
end
```

这段伪代码的重点不是语法，而是三个约束：

- 地址窗口不能重叠，否则一个地址可能同时选中多个 slave。
- 地址窗口不能留下无响应空洞，否则 master 可能等不到确定响应。
- 默认分支必须存在，否则非法地址会变成系统级“没人回答”。

一个准确的比喻是：decoder 像硬件版“路由表”，`HADDR` 像包头，`HSELx` 像唯一出端口。路由表不能把同一个包同时送到两个端口，也不能让包掉进没有出口的黑洞；这就是地址窗口互斥、完备和 default slave 的工程含义。

## 2. AHB slave 至少占用 1KB 地址空间

本讲反复回到 1KB，不是为了背一个数字，而是因为 AHB 地址译码默认以较粗粒度组织 slave 地址窗口。一个 slave 至少占用 1KB，意味着地址窗口大小要满足：

```text
window_size = end_addr - start_addr + 1 >= 1024 byte = 0x400
```

![1KB 地址窗口](<./screenshots/任务035_AMBA总线介绍4/task35_01_1kb_address_window_02m22s.jpg>)

视觉核验/看图要点/漏看后果：02:22-02:37，这张图的教学职责是把“每个 slave 占一个地址窗口”转成可检查的 memory map。先读每个窗口的起始地址、结束地址和大小，再确认它至少覆盖 1KB。漏看这一点，decoder 代码可能只写“看起来能命中”的范围，却没有验证窗口粒度、边界和文档一致性。

对数字前端来说，1KB 规则会落到三个交付物：

- `memory_map.md`：每个 slave 的 base、end、size、访问属性。
- decoder RTL：把 `HADDR` 的范围判断实现成 `HSELx`。
- testbench：至少测试窗口起点、窗口终点、越界地址和 default slave。

如果 memory map 和 decoder 不一致，软件按文档访问一个寄存器，RTL 可能选中另一个 slave；这种错误很难靠“看代码差不多”发现，必须用地址命中测试和波形验证。

## 3. default slave 是地址译码的兜底，不是可有可无的装饰

地址译码必须覆盖所有可能输入。没有命中 SRAM、Flash、APB bridge 的地址，也应该落到 default slave，由它返回确定的错误响应。

![default slave](<./screenshots/任务035_AMBA总线介绍4/task35_02_default_slave_05m06s.jpg>)

视觉核验/看图要点/漏看后果：05:06-05:21，这张图的教学职责是说明 decoder 的输出必须总有归宿。先看普通 slave 都不命中时，访问落到 default slave；再看 default slave 负责返回确定响应。漏看这一点，就会以为非法地址“没人选中就没事”，实际可能让 master 等不到 `HREADY/HRESP` 收尾。

default slave 和组合逻辑默认赋值有相同的工程思路：不要让输入落入“没人管”的路径。组合逻辑漏分支可能推断 latch；总线译码漏分支可能让一次访问没有 `HREADY/HRESP` 收尾。

一个合格的非法地址 testcase 应该能证明：

```text
master 发出非法地址
  -> decoder 未命中普通 slave
  -> default slave 被选中
  -> HRESP 返回 ERROR
  -> HREADY 按协议完成错误响应
  -> master 进入异常处理或丢弃本次事务
```

这条链比“代码里有 default”更重要，因为真正交付时需要证明非法访问不会把系统挂住。

## 4. 被 `HSELx` 选中的 slave 必须回答

从 slave 角度看，`HSELx` 拉高以后，问题就不再是“我想不想理它”，而是“我用哪种方式响应”。slave 可以完成访问，可以插入等待，可以报错，可以让 master 之后重试，但不能沉默。

![slave 响应信号](<./screenshots/任务035_AMBA总线介绍4/task35_03_slave_response_signals_08m32s.jpg>)

视觉核验/看图要点/漏看后果：08:32-08:47，这张图的教学职责是把 slave response 拆成“数据、完成边界、结果状态”三类。先看 `HRDATA`、`HREADY`、`HRESP` 都从 slave/总线响应侧返回；再确认读传输里 `HRDATA` 必须和有效的 `HREADY/HRESP=OKAY` 配合，才算可被 master 接收。漏看这一点，会把“数据线上有值”误判成“读已经成功”。

三根响应线的分工：

| 信号 | 谁驱动 | 回答什么问题 |
|---|---|---|
| `HRDATA` | slave | 读操作返回的数据是什么 |
| `HREADY` | slave/总线汇总 | 当前数据阶段结束了吗 |
| `HRESP` | slave | 这次传输是正常、错误、重试还是拆分 |

常见错误是把 `HREADY=0` 当成“不响应”。它其实也是一种响应：slave 告诉 master 当前还没完成，地址/数据阶段不能按理想流水继续推进。真正危险的是没有任何确定响应，master 不知道等待、报错还是继续。

可以把 `HREADY/HRESP/HRDATA` 理解成一次总线访问的三联回执：`HREADY` 是窗口是否结账，`HRESP` 是盖章结果，`HRDATA` 是读操作的交付物。只拿到交付物但窗口没结账，或者盖章不是 `OKAY`，都不能把这次 transfer 当成正常完成。

## 5. `OKAY` 可以单周期，`ERROR/RETRY/SPLIT` 需要两周期语义

AHB 正常响应 `OKAY` 不破坏流水：本拍采到正常结果，下一拍可以继续推进。但 `ERROR`、`RETRY`、`SPLIT` 会改变 master 原本的下一步计划，因此需要给 master 一个额外周期来处理。

![两周期响应](<./screenshots/任务035_AMBA总线介绍4/task35_04_two_cycle_response_14m43s.jpg>)

视觉核验/看图要点/漏看后果：14:43-14:58，这张图的教学职责是解释为什么非 `OKAY` 响应不能只看一个电平。按 `HCLK` 采样点读：`OKAY` 单周期即可结束；非 `OKAY` 响应会让原本计划好的下一笔地址/数据节奏被打断，所以协议用两周期响应给 master 留出撤回、空闲、重试或释放总线的时间。漏看两周期语义，master 状态机可能在错误响应时继续发下一笔有效地址。

可以把流水被打断的过程写成：

```text
原计划：
T1: A address
T2: A data + A+4 address
T3: A+4 data + A+8 address

发生 RETRY/ERROR/SPLIT：
T2/T3: slave 返回非 OKAY 响应
T3/T4: master 插入 IDLE 或改变下一步
之后：重新发起、报错处理，或释放总线
```

这不是“协议形式复杂”，而是硬件流水的直接后果。master 的地址阶段已经提前发出，如果 slave 突然说这笔不能正常完成，master 必须有一拍时间把下一步从“继续流水”改成“异常处理”。

## 6. `RETRY` 和 `SPLIT` 对 master 相似，对 arbiter 不一样

`RETRY` 和 `SPLIT` 都表示这次传输当前不能完成，master 需要之后再来。对 master 的局部动作来说，两者都可能导致释放总线、插入空闲或重新发起访问。

![Retry 响应时序](<./screenshots/任务035_AMBA总线介绍4/task35_05_retry_timing_19m20s.jpg>)

视觉核验/看图要点/漏看后果：19:20-19:35，这张图的教学职责是把 `RETRY` 从一个响应码读成一段可复现时序。先看 `HRESP=RETRY` 的两周期，再看 `HREADY` 的低/高配合，最后看 master 如何把后续 `HTRANS` 改成 `IDLE`，再重新发起 `NONSEQ`。漏看这张图，会把 `RETRY` 写成“下一拍继续传”，导致 master 没有真正撤回流水线中的后续 transfer。

二者真正的差别在 arbiter：

| 响应 | master 看到什么 | arbiter 可能怎么处理 |
|---|---|---|
| `RETRY` | 这次先别传，稍后重新请求 | 不必降低该 master 的长期优先级 |
| `SPLIT` | 这次先释放总线，等待之后允许再试 | 可以暂时降低或移出该 master 的仲裁优先级 |

这解释了为什么 `SPLIT` 需要 slave 告诉 arbiter “刚才是哪一个 master 被 split”。arbiter 不是只看当前 `HREQ`，还要维护哪个 master 暂时不适合继续占用总线。

## 7. AHB 内部读写数据分开，不按三态总线实现

本讲中间扩展了三态总线。三态的第三种状态是高阻态，常见在芯片 pad 或板级共享线里：输出使能关闭时，驱动端近似断开，不再强行拉高或拉低外部线。

![三态 pad 直觉](<./screenshots/任务035_AMBA总线介绍4/task35_06_tristate_pad_25m26s.jpg>)

视觉核验/看图要点/漏看后果：25:26-25:41，这张图的教学职责是借 pad 解释三态，而不是要求 AHB 内部照搬三态总线。先区分输入、输出、高阻三种 pad 状态，再回到片内互连：芯片内部数字逻辑通常避免真正的 inout 三态总线，更多用 mux 和单向信号表达。漏看这个边界，会把板级/IO 直觉误搬到可综合片内 RTL。

AHB 没有把读写数据合成一组 inout 总线，而是分成：

- `HWDATA`：master 到 slave 的写数据。
- `HRDATA`：slave 到 master 的读数据。

即使同一时刻一次事务不是读就是写，内部总线也通常不用“共享一组线再切方向”的三态方式。原因很直接：片内综合、时序分析、形式验证和互连结构更容易处理明确方向的单向信号。`inout` 在 Verilog 语法里存在，但在可综合片内 RTL 中要极其谨慎，通常只在 pad wrapper 或特殊 IO 边界出现。

## 8. endianness 决定 8/16-bit 访问落在哪些 byte lane

AHB 允许 8-bit、16-bit、32-bit 等不同大小传输。`HSIZE` 决定传输字节数，地址低位决定访问的是 32-bit 数据总线里的哪几个 byte lane；大小端规则决定这些 byte lane 如何解释。

![大小端和 byte lane](<./screenshots/任务035_AMBA总线介绍4/task35_07_endian_byte_lane_33m10s.jpg>)

视觉核验/看图要点/漏看后果：33:10-33:25，这张图的教学职责是把 `HSIZE`、地址低位和 byte lane 绑定起来。先看 32-bit 访问四个 byte 全有效；再看 16-bit/8-bit 访问如何由地址低位选择半字或单字节；最后看大小端如何解释这些 lane。漏看这一点，寄存器字段可能被写到错误字节，仿真里表现为“数据有写入但字段不对”。

对 32-bit AHB 数据总线，可按这个顺序判断：

```text
先看 HSIZE：
  010 -> 32-bit，4 个 byte lane 全有效
  001 -> 16-bit，2 个 byte lane 有效
  000 -> 8-bit，1 个 byte lane 有效

再看 HADDR[1:0]：
  16-bit 访问常看 bit[1]
  8-bit 访问看 bit[1:0]

最后看系统大小端约定：
  master 和 slave 必须一致
```

大小端不是 AMBA 在这一页里替你固定的所有实现细节，关键是 master 和 slave 必须采用同一解释规则。否则 master 认为自己写的是低 16 bit，slave 却按高 16 bit 接收，寄存器字段会错位。

## 9. arbiter 管“谁用总线”，`HGRANT` 加 `HREADY` 才表示真正接管

多个 master 同时存在时，arbiter 决定谁获得总线使用权。它接收 master 的请求和锁定意图，也接收 split 相关信息；它输出 grant、当前 master 编号和锁定状态。

![arbiter 信号](<./screenshots/任务035_AMBA总线介绍4/task35_08_arbiter_signals_37m13s.jpg>)

视觉核验/看图要点/漏看后果：37:13-37:28，这张图的教学职责是把 arbiter 的输入输出按方向分清。先看 `HBUSREQx/HLOCKx` 从 master 来，再看 `HGRANTx/HMASTER/HMASTLOCK` 从 arbiter 出去，最后看 `HSPLITx` 从 slave 反馈回来。漏看方向，仲裁 RTL 很容易把“谁请求、谁授权、谁恢复资格”写反。

典型信号：

| 信号 | 方向 | 含义 |
|---|---|---|
| `HBUSREQx` | master -> arbiter | master 请求使用总线 |
| `HLOCKx` | master -> arbiter | master 请求锁定传输 |
| `HGRANTx` | arbiter -> master | arbiter 授权某 master |
| `HMASTER[3:0]` | arbiter -> system | 当前总线 master 编号，4 bit 可表达最多 16 个 master |
| `HMASTLOCK` | arbiter -> system | 当前传输属于锁定序列 |
| `HSPLITx[15:0]` | slave -> arbiter | split 之后哪些 master 被允许重新尝试 |

`HGRANT` 不是“立刻拥有总线”的完整条件。课程里强调：master 真正控制总线，需要 `HGRANT` 有效，并且当前传输边界允许切换，也就是要看 `HREADY`。

![HGRANT 与 HREADY](<./screenshots/任务035_AMBA总线介绍4/task35_09_hgrant_hready_40m59s.jpg>)

视觉核验/看图要点/漏看后果：40:59-41:14，这张图的教学职责是把“授权”和“接管”分开。先看 `HGRANT` 何时拉高，再看同一采样边界 `HREADY` 是否为 1；arbiter 可以提前给出授权，但只有在 `HREADY=1`、当前传输完成的边界，新的 master 才能真正开始驱动地址和控制。漏看这一点，波形会被提前一拍读错。

锁定传输的含义是：master 希望一段访问不要被其他 master 插入。没有 lock 时，arbiter 可以在合适边界撤回 grant；有 lock 时，arbiter 通常要等该 master 释放锁定请求，才能结束这段总线占用。

更准确的比喻是：`HGRANT` 像排队系统发出的“下一位是你”，`HREADY` 像窗口真正腾出来的边界。只听到叫号但窗口还在处理上一笔业务，新 master 不能把自己的地址和控制塞进系统总线。

## 最小闭环：从地址到响应再到仲裁

把本章落成工程闭环，要能走完这条链：

```text
输入：
  HADDR、HTRANS、HWRITE、HSIZE、HBURST
  HBUSREQx、HLOCKx

译码：
  decoder 判断地址窗口
  产生唯一 HSELx
  未命中普通窗口时选 default slave

响应：
  被选中 slave 返回 HRDATA/HREADY/HRESP
  OKAY 正常完成
  ERROR/RETRY/SPLIT 打断流水并给 master 处理时间

仲裁：
  arbiter 根据 HBUSREQx、HLOCKx、HSPLITx 和策略发 HGRANTx
  HGRANTx 与 HREADY 共同决定新 master 何时真正接管

验收：
  波形能证明每次访问有且只有一个 slave 响应
  非法地址能进入 default slave 并返回 ERROR
  RETRY/SPLIT 不会让总线挂死
  多 master 请求时 grant 和 HMASTER 编号一致
```

## 可复现验证动作：把机制落到波形

读完本章后，至少能复现四个小场景。每个场景都不是为了“跑通一次”，而是为了证明 transfer、response 和 arbitration 的边界没有被写错。

| 场景 | 输入刺激 | 必看波形 | 通过口径 |
|---|---|---|---|
| 地址命中 | 访问 slave 窗口起点、终点、终点后一地址 | `HADDR`、各路 `HSELx` | 起点/终点只选中目标 slave，越界进入 default slave |
| 等待响应 | slave 对一次读拉低 `HREADY` 1-2 拍 | `HREADY`、`HTRANS`、`HADDR`、`HRDATA` | `HREADY=0` 期间地址/控制保持，`HREADY=1 && HRESP=OKAY` 后才采样读数据 |
| 错误响应 | 非法地址或权限错误返回 `ERROR` | `HRESP`、`HREADY`、master 状态 | 非 `OKAY` 按两周期语义处理，master 不继续把下一笔当作正常 SEQ |
| 仲裁切换 | 两个 master 同时请求，总线从 M0 切到 M1 | `HBUSREQx`、`HGRANTx`、`HMASTER`、`HREADY` | `HGRANT` 可先变化，但 `HREADY=1` 边界才切换系统承认的 master |

最小检查顺序：先看 transfer 是否有效，即 `HTRANS` 不是 `IDLE/BUSY`；再看它落到哪个 slave；再看响应何时完成；最后才看下一笔地址是否允许推进。顺序反了，就会把“地址线上出现过”误判成“一笔 transfer 已经完成”。

## 常见误区和失败信号

- 只写地址范围，不测边界地址：起点、终点、终点后一拍地址都必须测。
- decoder 没有 default：仿真里可能表现为 `HREADY` 不回来，系统像卡死。
- 以为 `HSELx` 是 master 发出的：实际是 decoder 根据 `HADDR` 生成的。
- 把 `HREADY=0` 当成错误：它只是等待；错误状态要看 `HRESP`。
- 把 `RETRY` 和 `SPLIT` 写成同一种响应：master 局部动作类似，但 arbiter 优先级处理可能不同。
- 在片内 RTL 中滥用 `inout`：会让综合、时序和验证复杂化；AHB 内部数据通路应优先保持方向明确。
- 忽略大小端一致性：8/16-bit 访问最容易暴露 byte lane 错位。
- 只看 `HGRANT` 不看 `HREADY`：可能误判 master 已经接管总线，实际上一笔旧传输还没结束。

## 自测题

1. 为什么 AHB decoder 必须有 default slave？如果没有，非法地址访问可能在波形上表现成什么？
2. `HSELx` 的输入来源是什么？为什么不建议把它理解成 master 直接指定的 slave 编号？
3. 一个 slave 被选中但暂时不能完成读访问，它至少可以通过哪些信号表达“还没完成”？
4. 为什么 `ERROR/RETRY/SPLIT` 需要两周期响应，而 `OKAY` 可以单周期？
5. `RETRY` 和 `SPLIT` 对 master 的局部动作有什么相似处？对 arbiter 有什么差异？
6. 为什么 AHB 内部通常不用三态 inout 数据总线，而使用 `HWDATA` 和 `HRDATA` 两组单向数据？
7. `HSIZE=001` 做 16-bit 访问时，为什么还要看地址低位和大小端规则？
8. 为什么 `HGRANT=1` 还不一定表示 master 已经真正接管总线？
9. `HREADY=0` 的等待周期内，master/slave 侧哪些信息不能随意推进？
10. 固定长度 burst 遇到 `RETRY` 时，为什么不能把后续 beat 继续当作正常 `SEQ`？

## 自测参考答案与判分点

1. default slave 把未映射地址变成确定 `ERROR` 响应；没有它，非法地址可能无人驱动响应，表现为等待不结束或响应不确定。
2. `HSELx` 来自 decoder，decoder 的输入是 `HADDR`。master 只发地址和控制，不能绕过地址映射直接点名 slave。
3. slave 可以把 `HREADY` 拉低插入等待；完成时配合 `HRESP=OKAY` 和有效 `HRDATA`；不能完成时返回 `ERROR/RETRY/SPLIT`。
4. 非 OKAY 响应会改变 master 原本流水计划，需要额外周期让 master 撤回、空闲、重试或释放总线。
5. 二者都让 master 之后再来；`SPLIT` 还会让 arbiter 记录并调整该 master 的后续优先级或允许条件。
6. 片内互连更适合明确方向的单向信号，便于综合、时序分析和验证；三态主要用于 pad 或外部共享线边界。
7. `HSIZE` 只说明传输宽度，地址低位决定落在哪些 byte lane，大小端决定这些 byte lane 对应数据高低字节的解释。
8. master 接管需要在传输边界发生；`HREADY=1` 表示当前传输完成，此时 grant 才能真正转换成新的地址/控制驱动权。
9. `HREADY=0` 表示当前数据阶段未完成，master 不能把下一笔地址/控制当成已被系统接受；slave 也不能在没有 `HREADYIN` 放行时采样新访问。判分点：必须提到地址/控制保持、状态机不提前推进、读数据不提前采样。
10. `RETRY` 已经宣布当前传输不能按原流水继续完成，固定 burst 的后续 `SEQ` 不能无条件延续；master 需要插入 `IDLE`、释放或重新发起 `NONSEQ`。判分点：必须把 `HRESP` 的异常语义和 burst 的 beat 计数/地址递增联系起来。
