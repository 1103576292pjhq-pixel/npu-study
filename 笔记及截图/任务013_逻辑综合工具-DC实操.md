# 任务13：逻辑综合工具 DC 实操

## 本章知识全景图

### 1. 一眼看懂这讲在讲什么

- 本章主题：把 Design Compiler 的第一次综合实操，从“跟着 GUI 点一遍”改写成“能复现、能查错、能交付”的 Tcl 综合流程。
- 核心概念：实验目录、工艺库、`search_path`、`target_library`、`link_library`、`symbol_library`、`read_verilog`、`analyze/elaborate`、`compile`、`report_area`、`report_timing`、SDF、门级网表。
- 逻辑主线：DC 不是把 Verilog 翻译成门这么简单，它是在指定工艺库和环境模型下，把 RTL 映射成可检查的门级实现。一次合格实操必须留下输入、命令、报告和输出文件，不能只留下“我在 GUI 里点过”的记忆。
- 最短学习路径：先认实验目录和库文件，再读入 RTL，再看 GUI 中的设计对象，最后把手工流程沉淀为 Tcl 脚本和报告闭环。

### 2. 概念地图

| 概念层级 | 核心概念 | 前置知识 | 延伸应用 |
|---|---|---|---|
| 工程入口 | `dc_lab` 实验目录 | Linux 目录、RTL 文件、库文件 | 可复现实验、版本归档、后续自动化 |
| 工艺环境 | `.lib`、`.db`、`.sdb` | 标准单元库、符号库、线载模型 | 工艺角、面积/时序/功耗估算 |
| DC 会话 | `search_path`、`target_library`、`link_library` | Tcl 变量、库搜索路径 | 大项目综合脚本 |
| 设计读入 | `read_verilog`、`analyze/elaborate` | Verilog 模块、顶层名 | 多文件层次化设计 |
| 综合执行 | `link`、`check_design`、`compile` | 层次解析、约束、优化 | QoR 收敛、约束驱动综合 |
| 结果证据 | area/timing/design 报告、SDF、门级网表 | 标准单元、静态时序 | 后仿真、STA、后端交接 |

### 3. 阅读顺序

1. 先把目录结构看成综合证据链：RTL、库、脚本、报告和输出必须能互相对上。
2. 再把库文件看成 DC 能使用的硬件“零件表”：没有正确库，综合结果没有工程意义。
3. 然后把 GUI 操作还原成 Tcl：GUI 用来观察，脚本用来复现。
4. 最后用报告判断结果：能解释 warning、area、timing，才算真的跑完。

## 1. 实验目录是综合证据链，不是文件堆

DC 实操的起点不是打开工具，而是先复制并进入固定实验目录；目录一乱，后面的库、RTL、脚本、报告就失去可追溯性。

![拷贝实验目录并进入 dc_lab](<./screenshots/任务013_逻辑综合工具-DC实操/copy_lab_tree_85s.jpg>)

视觉核验：视频 01:00-02:30，画面显示复制 `DClab/dc_lab` 并进入目录；读者应确认后续库、设计、脚本都在同一棵实验树下。

一个可复现实验目录至少要分清五类对象：

| 目录/文件 | 工程含义 | 检查口径 |
|---|---|---|
| `design` 或 `rtl` | 设计源文件 | 是否能找到顶层模块和依赖模块 |
| `library` | 工艺库和符号库 | 是否包含 DC 能读的 `.db` 和 GUI 需要的 `.sdb` |
| `script` 或 `syn` | Tcl 综合脚本 | 是否能从空会话重跑到报告 |
| `report` | 面积、时序、设计检查报告 | 是否与同一次 `compile` 对应 |
| `out` / `output` | 网表、SDF、DDC 等交付物 | 是否能用于后仿真或下游工具 |

工程上最怕的不是命令不会敲，而是跑完之后说不清这次结果来自哪份 RTL、哪套库、哪条脚本。目录结构就是最小审计链。

## 2. 工艺库决定 DC 能造什么硬件

DC 不能凭空生成门，它只能从目标工艺库里挑标准单元。库配置错了，后面的 area、timing、netlist 都可能只是看起来像结果。

![library 目录中的 db 和 sdb 文件](<./screenshots/任务013_逻辑综合工具-DC实操/lib_files_135s.jpg>)

视觉核验：视频 02:00-08:30，画面先打开 `.lib`，再打开 `.db`；应看到 `.lib` 是人能读的文本模型，`.db` 是 DC 使用的编译格式，`.sdb` 用于图形符号显示。

| 文件类型 | 谁主要使用 | 作用 |
|---|---|---|
| `.lib` | 工程师、库编译流程 | 可读的 Liberty 文本库，描述单元面积、时序弧、功耗、线载模型等 |
| `.db` | Design Compiler | Synopsys 编译后的库格式，综合映射时真正读取 |
| `.sdb` | Design Vision GUI | 图形符号库，让 GUI 能画出门级符号 |
| `typical/slow/fast` | 综合和时序分析 | 对应不同 PVT 条件，影响延迟、面积权衡和违例判断 |

常见库配置如下：

```tcl
set search_path    [list ./library ./design ./script]
set target_library [list typical.db]
set link_library   [list * typical.db]
set symbol_library [list tsmc090.sdb]
```

`target_library` 回答“综合允许把 RTL 映射成哪些标准单元”，`link_library` 回答“解析实例和引用时到哪里找定义”。`search_path` 让文件名可以不带长路径，`symbol_library` 只影响 GUI 显示，不决定综合能用哪些门。

## 3. GUI 是观察窗口，Tcl 才是交付流程

GUI 适合第一次建立直觉：你能看到设计层次、端口、门级结构和报告入口。但团队交付不能依赖手点菜单，因为手点流程无法审计、无法复现、无法放进自动化。

![启动 DC GUI 后的设计环境](<./screenshots/任务013_逻辑综合工具-DC实操/start_dc_gui_720s.jpg>)

视觉核验：视频 11:30-13:00，画面出现 Design Vision/Design Browser 和日志窗口；读者应观察 GUI 的价值是显示对象状态，而不是替代脚本。

一条实操原则足够记住：GUI 用来确认“工具眼里的设计长什么样”，Tcl 用来证明“这个结果可以被别人重跑出来”。

## 4. 读入 RTL 有两条路：直接读入和分析后展开

读入设计不是把文件拖进工具，而是把文本 RTL 变成 DC 内部的设计对象。小实验可以直接 `read_verilog`，正式脚本更常用 `analyze + elaborate`，因为它把“分析源文件”和“展开顶层设计”分开了。

![通过菜单读入设计](<./screenshots/任务013_逻辑综合工具-DC实操/read_design_910s.jpg>)

视觉核验：视频 14:30-16:00，画面从 GUI 菜单进入设计读入；读者应把菜单动作对应到 `read_verilog` 或 `analyze/elaborate`。

两种写法都要会：

```tcl
# 一步读入
read_verilog ./design/verilog/adder.v

# 分析源文件，再展开顶层
analyze -format verilog ./design/verilog/adder.v
elaborate adder
current_design adder
link
```

| 方式 | 更像什么 | 适合场景 |
|---|---|---|
| `read_verilog` | 直接把 Verilog 读成设计对象 | 小模块、单文件、课堂演示 |
| `analyze` | 检查和分析源文件 | 多文件、多语言、需要工作库管理 |
| `elaborate` | 展开顶层和参数化层次 | 正式综合、层次化设计、脚本交付 |
| `link` | 解析未绑定引用 | 检查子模块、库单元、黑盒是否能找到 |

如果 `link` 之前就继续 `compile`，后面的报告可能带着 unresolved design 继续跑。工具不一定立刻停下来，但结果已经不可信。

## 5. 读入后先看对象，再谈优化

读入成功只说明语法和文件路径暂时过关，不说明设计已经可综合。下一步要检查顶层、端口、层次、单元数量和 unresolved reference。

![Design Browser 中的设计对象](<./screenshots/任务013_逻辑综合工具-DC实操/design_browser_1135s.jpg>)

视觉核验：视频 18:30-19:30，画面显示 Design Browser 中的设计层次；读者应确认顶层模块、端口和对象名称是否符合预期。

最小检查顺序：

1. `current_design` 是否设置到预期顶层。
2. 端口数量和方向是否符合 RTL。
3. 是否存在 unresolved reference。
4. 是否意外推断出 latch 或寄存器。
5. `report_area` 中组合/时序单元比例是否与设计类型一致。

![面积报告中的端口、网络和单元信息](<./screenshots/任务013_逻辑综合工具-DC实操/report_area_1570s.jpg>)

视觉核验：视频 25:00-27:00，画面打开 area/design 报告；读者应看总面积以外的 cell 数、端口、网络、线载模型和是否有时序约束信息。

面积报告不是“越小越好”的单一数字。对组合逻辑实验，突然出现大量 sequential cell 或 latch 就是异常；对时序设计，寄存器数量又应与 RTL 打拍位置基本一致。

## 6. `compile` 的本质是库映射和目标权衡

`compile` 不是最后一步，它只是把当前设计在当前库和当前环境下做一次映射与优化。没有约束的组合逻辑示例，主要看面积和基本结构；带时钟的设计，`compile` 会在时序、面积、功耗之间做取舍。

课堂中 GUI 的 compile 选项会出现 map effort、area effort、power effort、clock gating、incremental mapping 等选项。入门阶段不必背每个按钮，但要知道它们都在影响同一个问题：工具为了满足目标，愿意花多少优化代价、采用哪些变换。

正式脚本里，最低闭环通常写成：

```tcl
check_design
compile

report_area   > ./report/adder.area.rpt
report_timing > ./report/adder.timing.rpt
report_design > ./report/adder.design.rpt
```

`check_design` 要放在 `compile` 前，因为它负责暴露结构性错误；报告要放在 `compile` 后，因为它们描述的是本次映射后的结果。

## 7. 脚本化把课堂操作变成交付能力

脚本不是把命令抄一遍，而是固定一次综合的因果顺序：先有库和工作库，再有设计对象，再检查，再综合，再报告，再输出。

![综合脚本中的库设置、读入 RTL 和 elaborate](<./screenshots/任务013_逻辑综合工具-DC实操/script_flow_1845s.jpg>)

视觉核验：视频 29:30-34:30，画面展示 Tcl 脚本骨架；读者应看到库设置、工作库、读入、展开、检查、综合、报告和输出文件按顺序出现。

可复现实验脚本骨架：

```tcl
set search_path    [list ./library ./design ./script]
set target_library [list typical.db]
set link_library   [list * typical.db]
set symbol_library [list tsmc090.sdb]

define_design_lib work -path ./work

analyze -format verilog ./design/verilog/adder.v
elaborate adder
current_design adder
link

check_design
compile

report_design > ./report/adder.design.rpt
report_area   > ./report/adder.area.rpt
report_timing > ./report/adder.timing.rpt

write -format ddc     -hierarchy -output ./out/adder.ddc
write -format verilog -hierarchy -output ./out/adder.mapped.v
write_sdf ./out/adder.sdf
```

这段顺序里最容易被新手跳过的是 `link` 和 `check_design`。如果没有这两步，后面的 `compile` 只是“工具尽力跑了一次”，不是“设计经过结构检查后完成综合”。

## 8. 报告是下一轮修改入口，不是跑完纪念品

报告的价值不是证明你按了 `compile`，而是告诉你下一步该查 RTL、查库、查约束，还是查脚本顺序。

![时序和面积报告输出](<./screenshots/任务013_逻辑综合工具-DC实操/timing_area_reports_2280s.jpg>)

视觉核验：视频 36:30-38:30，画面显示 timing/area 相关报告和输出文件；读者应确认报告与同一次综合运行对应。

| 报告/现象 | 优先怀疑 | 下一步 |
|---|---|---|
| unresolved reference | 文件列表、顶层名、`link_library` | 先修读入和链接，不要继续优化 |
| latch 数量异常 | 组合逻辑分支未赋值、case 覆盖不全 | 回 RTL 查 `always_comb`、默认值、case 分支 |
| area 异常大 | 约束过紧、位宽错误、逻辑复制、库选择 | 对比宽松约束和模块层次面积 |
| timing report 无有效路径 | 缺少时钟/约束、当前设计不对 | 检查 `current_design`、时钟和输入输出约束 |
| 负 slack | 约束太紧、路径太深、库太慢 | 查关键路径，再决定改 RTL、改约束还是换库 |

本讲的组合逻辑示例没有完整时序约束，所以 timing 报告更多是工具报告入口演示。下一讲加入 `create_clock` 和 I/O delay 后，`report_timing` 才真正成为时序收敛证据。

## 9. SDF 和门级网表把综合结果送到后仿真

综合输出里最容易混淆的是 DDC、门级 Verilog 和 SDF。它们都来自综合结果，但服务对象不同。

![静态时序分析资料衔接](<./screenshots/任务013_逻辑综合工具-DC实操/sta_reference_2740s.jpg>)

视觉核验：视频 35:00-41:00，画面讨论 DDC、Verilog 网表、SDF 和后仿真；读者应确认网表描述连接关系，SDF 描述延时信息。

| 输出文件 | 典型命令 | 给谁用 | 作用 |
|---|---|---|---|
| `.ddc` | `write -format ddc` | Synopsys 工具链 | 保存 DC 内部设计数据库，便于继续读取 |
| mapped `.v` | `write -format verilog` | VCS 后仿真、后端工具 | 门级网表，包含标准单元实例连接 |
| `.sdf` | `write_sdf` | 门级带延时仿真 | 标注单元和路径延时 |
| `.rpt` | `report_* > file.rpt` | 设计、验证、后端、review | 记录面积、时序、结构检查结果 |

门级后仿真通常需要“网表 + SDF + 仿真库”。只有网表没有 SDF，仿真更接近零延时连接检查；有 SDF 后，寄存器输出、组合路径和门延时才会以更接近实现的方式进入仿真。

## 10. 从本讲连接到 AI+IC 工程

AI 芯片里的 MAC 阵列、DMA 控制器、NoC 路由、SRAM wrapper 和指令译码器，最后都要经历类似的“RTL -> 综合 -> 报告 -> 网表/约束/延时”链路。NPU 不是只写出能仿真的 Verilog 就结束，真正交付还要回答：

- 这块算子控制逻辑综合后面积主要在哪里？
- 关键路径是加法器、比较器、地址生成，还是控制 MUX？
- 门级网表和 SDF 能不能接到后仿真？
- 报告里的 warning 是否会影响后端或 STA？

所以本讲最重要的练习不是背 DC 命令，而是把每条命令放回前端交付链：输入是什么、工具做了什么、输出能证明什么、失败先查哪里。

## 11. 深层理解：DC 不是“翻译器”，而是带预算的硬件采购员

把综合只理解成“Verilog 变门级网表”会太浅。更准确的比喻是：RTL 像功能需求书，工艺库像供应商零件目录，约束像预算和交付时间，DC 像一个采购员兼装配工程师。它不能凭空造零件，只能从 `target_library` 允许的标准单元里挑；它也不能猜项目目标，必须根据时序、面积、功耗和设计规则去权衡。

所以每条命令都对应一个工程问题：

| DC 动作 | 表面动作 | 深层问题 |
|---|---|---|
| 读库 | 加载 `.db/.lib` | 这次综合能使用哪些门、触发器、时序弧和面积数据 |
| 读 RTL | `read_verilog` 或 `analyze/elaborate` | 需求书是否能被工具理解，顶层和参数是否展开正确 |
| link | 解析引用 | 设计里的模块、库单元和黑盒是否都能找到定义 |
| check_design | 做结构体检 | 是否存在未连接、无驱动、多驱动、隐式 latch 等设计问题 |
| compile | 映射和优化 | 用哪些真实标准单元实现 RTL，并在目标之间取舍 |
| report | 输出证据 | 面积、时序、层次和 warning 是否能支撑下一步决策 |
| write | 交付产物 | 下游仿真、STA、后端和归档分别拿什么文件继续工作 |

这也是为什么 GUI 不能成为交付主线。GUI 像显微镜，适合看对象；Tcl 脚本像实验记录，适合复现。正式项目不能只说“我在 GUI 点过”，必须能用脚本重跑并得到同一批报告。

## 12. 配图复盘：每张图要服务一个判断

本章配图不是操作留念，而是综合证据链：

| 配图 | 读图重点 | 对应判断 |
|---|---|---|
| 拷贝实验目录并进入 `dc_lab` | 当前工作目录和实验树是否正确 | 后续所有路径是否可信 |
| library 目录中的 DB/SDB | 库文件是否存在，格式是否匹配工具 | 没有库就没有真实门级映射 |
| 启动 DC GUI | 工具环境是否能进入 | 环境变量、license、版本是否可用 |
| 通过菜单读入设计 | RTL 能否被工具解析 | 读入成功不等于设计已经健康 |
| Design Browser | 顶层和实例层次是否正确 | link/elaborate 是否把对象建出来 |
| 面积报告 | combinational/sequential/area 分布 | 是否出现异常 latch/寄存器/面积膨胀 |
| 综合脚本 | GUI 动作是否已转成 Tcl | 是否具备可复现交付能力 |
| 时序和面积报告输出 | 报告是否真正生成 | 是否能进入下一轮 debug |
| STA 资料衔接 | 综合结果连接到时序分析 | 学习链路从 DC 过渡到 STA |

读图时要像读实验记录：先问“这张图证明了什么”，再问“如果这一步失败，下一步查哪里”。图只要不能回答这两个问题，就会退化成装饰。

## 13. 报告判读：把结果变成下一步动作

综合报告的价值不在于“有文件”，而在于驱动下一轮修改：

| 报告现象 | 深层含义 | 下一步 |
|---|---|---|
| `unresolved reference` | link 没找到模块或库单元 | 查文件列表、顶层名、库路径和黑盒声明 |
| latch 数量异常 | 组合逻辑路径未完全赋值 | 查 `always_comb`、默认赋值、`case` 覆盖 |
| area 异常变大 | 位宽、复制逻辑、约束或 RTL 写法有问题 | 对比层次面积，定位热点模块 |
| timing 负 slack | 当前结构在约束下太慢 | 看关键路径，不要盲目重复 compile |
| warning 很多但能出网表 | 可能只是“看似成功” | 按 warning 类型分级，不把所有 warning 当噪声 |

综合像体检报告：不能看到“报告已生成”就结束，真正重要的是血项哪一项异常、异常会不会影响手术、下一次复查要改什么。

## 复习与自测

1. `target_library` 和 `link_library` 的区别是什么？
   - 答案要点：`target_library` 决定综合映射可选的标准单元；`link_library` 用于解析设计引用、子模块和库单元。前者偏“用什么门实现”，后者偏“到哪里找定义”。

2. 为什么正式项目不能只靠 GUI 操作 DC？
   - 答案要点：GUI 不利于审计、复现、团队协作和自动化。GUI 可用于观察设计对象，交付必须沉淀为 Tcl 脚本、报告和输出文件。

3. `read_verilog` 与 `analyze/elaborate` 的工程差异是什么？
   - 答案要点：`read_verilog` 更像一步读入；`analyze` 负责分析源文件，`elaborate` 负责展开顶层和参数化设计。多文件、层次化、正式脚本更适合 `analyze/elaborate`。

4. 面积报告里 sequential cell 数量异常增加，可能暗示什么？
   - 答案要点：可能是 RTL 中意外推断了 latch 或寄存器，也可能是设计类型判断错误；应回查 `always` 块、默认赋值、case 覆盖和时序逻辑写法。

5. 门级后仿真通常为什么需要网表和 SDF 一起交？
   - 答案要点：网表提供标准单元实例和连接关系，SDF 提供单元/路径延时。只有网表不能表达真实延时，带 SDF 才能观察门级时序行为。

6. 本章最小可复现实验的通过标准是什么？
   - 答案要点：能从实验目录用 Tcl 重跑，正确读入顶层，`link/check_design` 无关键错误，生成 area/timing/design 报告，输出 DDC、mapped Verilog 和 SDF，并能解释主要 warning/error。
