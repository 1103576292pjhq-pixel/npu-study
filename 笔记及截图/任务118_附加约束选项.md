# 任务118：附加约束选项

## 本章知识全景图

这一讲解决的是 SDC 从“基础约束能跑”到“约束语义可控”的问题。前面已经建立了 `create_clock`、`set_input_delay`、`set_output_delay`、环境属性和综合优化闭环；但真实工程不会只靠最简单的命令形式。端口可能有上升沿和下降沿两套预算，路径可能要按 setup/hold 分别约束，对象集合可能要通过 `-from/-to/-through` 精确定位，综合优化也可能需要按 path group 和权重引导。附加选项的作用，就是把“约束写给谁、在哪个边沿生效、分析 setup 还是 hold、覆盖哪段路径、报告里如何证明”说清楚。

| 约束选项层级 | 解决的问题 | 写错后的失败信号 |
|---|---|---|
| 对象集合 | 命令到底作用到哪些 port、pin、cell、clock | 集合为空、漏端口、clock 被当成 data、约束没有命中对象 |
| `-from/-to/-through` | 把路径范围限定到起点、终点或中间点 | 修错路径、真实 critical path 没被优化或被误放松 |
| `-max/-min` | 区分 setup-like 最大延时和 hold-like 最小延时 | setup 过了但 hold 爆掉，或 min path 完全没建模 |
| `-rise/-fall`、`-clock_fall` | 区分数据边沿和参考时钟边沿 | DDR、负边沿采样或反相 clock 路径分析错误 |
| `-add_delay` | 同一端口保留多条 edge-specific delay | 后一条 delay 覆盖前一条，导致半边接口预算丢失 |
| path group / weight | 让综合工具按工程重点优化 | 工具只盯默认最差路径，重要接口迟迟不收敛 |
| 报告验证选项 | 证明约束对象、范围和数值真的生效 | WNS 看似正常，但 report 中没有目标路径或属性 |

最短学习路径：先把附加选项按“对象范围、分析维度、边沿维度、优化引导、报告核对”分类；再学会用 `get_*` 和 `report_*` 证明每条选项命中了目标；最后把这些选项收进综合脚本，作为交付 SDC 前的检查门。

## 1. 附加选项不是装饰，它决定约束的精确语义

同一条 SDC 命令，少一个选项就可能从“精确约束目标路径”变成“粗糙覆盖一大片对象”。附加选项的核心作用有三类：限定对象、限定分析条件、限定报告检查方式。

例如下面两条命令表面上都设置 input delay，实际语义差很多：

```tcl
set_input_delay -max 0.6 -clock [get_clocks Clk] [all_inputs]

set_input_delay -max 0.6 \
  -clock [get_clocks Clk] \
  [remove_from_collection [all_inputs] [get_ports {Clk rst_n}]]
```

第一条会把所有 input 都纳入普通数据输入，包括 clock 或 reset 的风险很高；第二条先把普通数据端口集合构造出来，再对它们施加 delay。真正的工程差别不在 0.6 ns，而在对象集合是否正确。

判断附加选项是否写对，不靠肉眼看脚本，而靠三类报告：

```tcl
report_port -verbose
report_clock
check_timing
report_timing -from ... -to ... -through ...
report_constraint -all_violators
```

约束脚本的最低可信标准是：命令执行无报错，对象集合非空，报告中能看到属性或路径变化，且没有未解释的 unconstrained path。

## 2. 对象集合：先证明“约束写给谁”

SDC 命令操作的是工具对象，不是文件里的字符串。`[get_ports A]`、`[get_pins U1/Z]`、`[get_cells U2]`、`[get_clocks Clk]` 返回的都是 collection。collection 为空时，很多脚本仍可能继续执行，但约束没有实际对象。

| 对象类型 | 常见命令 | 用途 | 常见错误 |
|---|---|---|---|
| port | `get_ports`、`all_inputs`、`all_outputs` | 顶层接口约束 | 通配符漏总线 bit，clock/reset 被批量当作 data |
| pin | `get_pins` | 精确定位 cell 输入输出 pin | 层次名被改、flatten 后路径失效 |
| cell | `get_cells` | 约束实例、dont_touch、retime 控制 | 误把 module 名当 instance 名 |
| clock | `get_clocks`、`all_clocks` | 时钟相关约束 | clock object 没创建，或同名 port/clock 混用 |
| register | `all_registers` | reg-to-reg path、path group | latch、macro wrapper 或 scan FF 分类不符合预期 |

构造集合时要把“默认覆盖”和“特殊排除”分开写：

```tcl
set DATA_INPUTS  [remove_from_collection [all_inputs]  [get_ports {Clk rst_n scan_en}]]
set DATA_OUTPUTS [all_outputs]

set_input_delay  -max 0.6 -clock [get_clocks Clk] $DATA_INPUTS
set_output_delay -max 0.8 -clock [get_clocks Clk] $DATA_OUTPUTS
```

这类变量不是为了好看，而是为了让报告和审查能复用同一个对象集合。交付前应检查：

```tcl
sizeof_collection $DATA_INPUTS
report_port -verbose $DATA_INPUTS
```

如果集合大小为 0，或者普通数据端口数量明显不对，后续 timing report 再漂亮也不可信。

## 3. `-from/-to/-through`：路径范围比数值更先决定结果

`-from/-to/-through` 用来限定 timing path 的起点、终点和中间点。它们经常出现在 `report_timing`、`group_path`、`set_max_delay`、`set_min_delay`、`set_false_path`、`set_multicycle_path` 这类命令里。

```tcl
report_timing \
  -from [get_clocks ClkA] \
  -to   [get_clocks ClkB] \
  -through [get_pins U_sync/D]
```

读法是：只看从 `ClkA` 发起、到 `ClkB` 捕获、并穿过 `U_sync/D` 的路径。这里最容易犯的错是把 `-from/-to` 当成普通文本过滤。它们实际改变的是路径搜索空间。

| 选项 | 限定什么 | 典型用途 |
|---|---|---|
| `-from` | startpoint 或 launch clock | 输入端、某组寄存器、某个 clock domain 发出的路径 |
| `-to` | endpoint 或 capture clock | 输出端、某组寄存器、某个 clock domain 捕获的路径 |
| `-through` | 路径中必须经过的 pin/net/cell | 调试某段 mux、同步器、跨层次接口、scan/test 逻辑 |

工程判断口径：如果目的是排查，不要一上来写 exception；先用 `report_timing -from/-to/-through` 看真实路径。只有确认默认 STA 关系不符合设计意图，才把同样的对象范围写进约束。

## 4. `-max/-min`：setup 与 hold 不是一件事

`-max` 通常对应最大延时分析，服务 setup 检查；`-min` 通常对应最小延时分析，服务 hold 检查。对 I/O 约束来说，只写 `-max` 可能让 setup 模型成立，但 hold 侧没有足够信息。

```tcl
set_input_delay -max 0.8 -clock [get_clocks Clk] $DATA_INPUTS
set_input_delay -min 0.1 -clock [get_clocks Clk] $DATA_INPUTS

set_output_delay -max 0.7 -clock [get_clocks Clk] $DATA_OUTPUTS
set_output_delay -min 0.0 -clock [get_clocks Clk] $DATA_OUTPUTS
```

可以把它理解成两张预算表：

| 分析 | 关心什么 | 对应失败 |
|---|---|---|
| max/setup | 数据最晚到，会不会赶不上捕获边沿 | setup violation、WNS/TNS 变差 |
| min/hold | 数据最早到，会不会太早冲过保持窗口 | hold violation、min delay 过短 |

很多初学者只会修 setup，因为 setup 的负 slack 更容易和频率目标相连。但工程里 hold 不是“后端再说”的小问题。综合阶段的 min 约束、clock relation 和 exception 如果写错，后端可能要靠大量 delay cell 修补，面积、功耗和 ECO 风险都会增加。

## 5. edge 选项：上升沿、下降沿和 DDR 接口不能靠默认值猜

默认情况下，很多约束以 clock 上升沿和 data 的默认边沿解释。只要设计里出现负边沿采样、DDR、反相 clock、双边沿输入输出，就必须显式说明 edge 关系。

常见形态：

```tcl
set_input_delay -max 0.45 -clock [get_clocks Clk]      -rise [get_ports din]
set_input_delay -max 0.55 -clock [get_clocks Clk]      -fall [get_ports din]
set_input_delay -max 0.50 -clock [get_clocks Clk] -clock_fall [get_ports din_nedge]
```

`-rise/-fall` 描述数据边沿，`-clock_fall` 描述相对参考 clock 的下降沿解释。二者不是同一件事。数据在上升沿变化，和时钟用下降沿采样，是两个维度。

如果同一个端口需要同时保留多条 delay，例如 DDR 输入对上升沿和下降沿都有预算，后写命令可能覆盖先写命令。此时要用 `-add_delay` 保留多条约束：

```tcl
set_input_delay -max 0.35 -clock [get_clocks Clk] -rise [get_ports ddr_d]
set_input_delay -max 0.40 -clock [get_clocks Clk] -fall -add_delay [get_ports ddr_d]
```

失败信号是 report 里只剩一边 delay，或 DDR 接口半边路径没有被分析。遇到这类问题，先查 `report_port -verbose`，不要先改 timing 数值。

## 6. `set_max_delay` / `set_min_delay`：它们是路径预算覆盖，不是 clock 的替代品

`set_max_delay` 和 `set_min_delay` 可以对特定路径施加绝对最大/最小延时要求。它们常用于非标准路径、接口预算、异步控制或需要独立于默认 clock relation 的路径约束。

```tcl
set_max_delay 3.0 \
  -from [get_pins U_req_reg/Q] \
  -to   [get_pins U_ack_sync/D]

set_min_delay 0.2 \
  -from [get_pins U_req_reg/Q] \
  -to   [get_pins U_ack_sync/D]
```

这类命令的关键不是“把路径设成 3 ns”，而是明确告诉工具：这段路径即使不按普通单周期 reg-to-reg 关系分析，也仍然有一个工程上必须满足的延时边界。

使用边界：

| 场景 | 是否适合 |
|---|---|
| 明确需要绝对延时上限的异步握手或接口路径 | 可以，但要配合 CDC/协议验证 |
| 只是普通同步 reg-to-reg 路径太慢 | 不应优先用，应先检查 clock、RTL 和综合优化 |
| 想让 violation 消失 | 不合格，会掩盖真实时序问题 |
| 对某段路径既要 max 又要 min 边界 | 可以成对使用，并检查 setup/hold 报告 |

`set_max_delay` 不能替代 `create_clock`。clock 仍然定义同步世界的基本时间坐标；max/min delay 只是对特定路径施加额外边界或覆盖默认关系。

## 7. path group 和权重：综合优化要被引导到正确路径

综合工具默认按 clock 或路径组优化最差路径，但工程重点未必正好等于默认最差路径。`group_path`、`-weight`、`-critical_range` 这类选项用来告诉工具哪些路径更值得投入优化 effort。

```tcl
group_path -name INPUTS  -from [all_inputs]
group_path -name OUTPUTS -to [all_outputs]
group_path -name REG2REG -from [all_registers] -to [all_registers]

group_path -name REG2REG -weight 5 -critical_range 0.2 \
  -from [all_registers] -to [all_registers]
```

这类选项影响的是综合优化策略，不是设计功能。它适合在 first compile 后读报告，再对剩余 critical path 做定向优化。

判断口径：

- 如果 `report_timing` 显示 INPUTS 一直最差，工具可能长期忽略 reg-to-reg 路径，需要重新分组或调预算。
- 如果某个 path group 权重过高，工具可能用大量面积功耗优化低价值路径。
- 如果 `critical_range` 太宽，工具会优化太多 near-critical path，runtime 和面积可能上升。

path group 的正确使用方式是 report-driven：先看路径分布，再设置分组和权重，再跑 incremental compile，再看 QoR 是否改善。

## 8. 环境约束选项：电气模型也要检查覆盖范围

环境属性命令同样有附加选项和对象范围问题。`set_load`、`set_driving_cell`、`set_input_transition`、`set_max_capacitance` 看起来不像 timing exception，但它们会改变 delay 查表和 DRC 检查。

```tcl
set DATA_INPUTS [remove_from_collection [all_inputs] [get_ports {Clk rst_n}]]

set_driving_cell -lib_cell INVX4 -pin Z $DATA_INPUTS
set_input_transition 0.12 $DATA_INPUTS

set_load 0.05 [all_outputs]
set_max_capacitance 0.20 [current_design]
```

常见判断：

| 命令 | 要核对什么 |
|---|---|
| `set_driving_cell` | library cell 是否存在，输出 pin 是否正确，是否作用到 data input |
| `set_input_transition` | 是否和 driving cell 重复建模，数值单位是否正确 |
| `set_load` | 是否代表实际/预算负载，而不是 max cap |
| `set_max_capacitance` | 是 design rule 上限，不是当前负载值 |

如果环境约束对象写错，timing 报告可能仍有 slack，但 delay 查表基础错了。对 NPU 这类高 fanout、高负载设计，input transition 和 output load 的错误会在后端被放大。

## 9. 约束文件的推荐组织：先默认，再覆盖，再检查

附加选项多了以后，脚本最怕无序堆命令。可维护的 SDC 通常按“对象集合 -> clock -> I/O -> 环境 -> 特殊覆盖 -> 分组 -> 检查报告”的顺序组织。

```tcl
reset_design

# 1. objects
set CLK_PORT    [get_ports Clk]
set RST_PORT    [get_ports rst_n]
set DATA_INPUTS [remove_from_collection [all_inputs] [list $CLK_PORT $RST_PORT]]
set DATA_OUTPUTS [all_outputs]

# 2. clock
create_clock -name Clk -period 2.5 $CLK_PORT
set_clock_uncertainty -setup 0.15 [get_clocks Clk]
set_clock_uncertainty -hold  0.05 [get_clocks Clk]

# 3. I/O timing
set_input_delay  -max 0.8 -clock [get_clocks Clk] $DATA_INPUTS
set_input_delay  -min 0.1 -clock [get_clocks Clk] $DATA_INPUTS
set_output_delay -max 0.7 -clock [get_clocks Clk] $DATA_OUTPUTS
set_output_delay -min 0.0 -clock [get_clocks Clk] $DATA_OUTPUTS

# 4. environment
set_driving_cell -lib_cell INVX4 $DATA_INPUTS
set_load 0.05 $DATA_OUTPUTS

# 5. optimization guidance
group_path -name INPUTS  -from $DATA_INPUTS
group_path -name OUTPUTS -to $DATA_OUTPUTS
group_path -name REG2REG -from [all_registers] -to [all_registers]
```

这个骨架的重点是顺序和检查口径。默认约束先覆盖大多数端口，特殊端口后覆盖；对象集合先定义，后续命令复用；脚本最后用报告证明对象和路径都在。

## 10. 报告核对：附加选项必须在报告里留下证据

附加选项越多，越不能只靠“脚本没有报错”判断。交付前至少做四层核对：

| 核对层 | 命令 | 通过标准 |
|---|---|---|
| 对象存在 | `sizeof_collection`、`report_clock` | 目标集合非空，clock object 数量正确 |
| 属性生效 | `report_port -verbose` | I/O delay、transition、load 等属性能看到 |
| 路径进入分析 | `report_timing -from/-to/-through` | 目标路径出现在 report 中，path group 正确 |
| 约束完整性 | `check_timing`、`report_constraint -all_violators` | 没有未解释 unconstrained、multiple clocks、DRC violation |

失败时按依赖顺序排查：

```text
对象是否存在 -> 集合是否覆盖 -> 命令是否覆盖/被覆盖 -> 路径是否被分析 -> slack 是否需要优化
```

不要倒过来。先调 slack 数字，后查对象，是约束调试里最常见的低效路径。

## 11. 常见误区

| 误区 | 正确口径 |
|---|---|
| 附加选项只是命令细节 | 它们决定对象、边沿、setup/hold 和路径范围 |
| `all_inputs` 可以直接批量用 | 必须排除 clock、reset、scan/test 等非普通 data 输入 |
| 只写 `-max` 就够 | setup 侧需要 max，hold 侧通常还要 min 建模 |
| 后一条同端口 delay 会自动叠加 | 默认可能覆盖，需要 `-add_delay` 保留多条 edge-specific delay |
| `set_max_delay` 可以拿来修普通同步 violation | 它是路径预算覆盖，不是修慢路径的万能药 |
| path group 越多越好 | 分组应服务 report-driven 优化，过度分组会让脚本难维护 |
| report 只看 WNS | 要看对象、path group、arrival/required、端口属性和 unconstrained path |

## 12. 和 DC 输出的连接

任务120 会讲 DC 输出交付包。附加约束选项在这里的意义是：写出的 SDC 不只是文件存在，而是下游 STA/P&R 能读懂同一套约束语义。

一个正式可交付的 SDC 要满足：

1. clock、I/O delay、环境属性、path group 和必要路径覆盖都来自同一版设计数据库。
2. 命名清理后，SDC 仍能命中 netlist 里的对象。
3. 约束选项不会把 clock/reset/test 等特殊对象误当普通数据路径。
4. `check_timing` 和 `report_timing` 能证明约束生效。
5. 特殊路径如果用了 max/min delay 或 exception，必须有单独审查记录，不能混在默认约束里没人知道。

## 自测题与答案

1. 为什么 `all_inputs` 不能直接作为所有 input delay 的对象？

   答：`all_inputs` 可能包含 clock、reset、scan enable、test mode 等非普通数据输入。普通 input delay 描述数据到达端口前的外部预算，clock/reset 被批量纳入会造成语义错误。合格做法是用 `remove_from_collection` 排除特殊端口，并用 `report_port -verbose` 核对。

2. `-max` 和 `-min` 分别服务什么分析？

   答：`-max` 通常服务最大延时/setup 分析，关注数据最晚到是否赶上捕获边沿；`-min` 通常服务最小延时/hold 分析，关注数据最早到是否破坏保持时间。

3. `-rise/-fall` 和 `-clock_fall` 的区别是什么？

   答：`-rise/-fall` 描述数据边沿或约束作用的数据极性；`-clock_fall` 描述约束相对参考时钟下降沿解释。一个是数据边沿维度，一个是时钟参考边沿维度。

4. 同一个 DDR 输入端口需要上升沿和下降沿两套 delay，为什么可能需要 `-add_delay`？

   答：如果后写的 delay 覆盖前写的 delay，报告里只保留一套边沿预算，另一半接口没有被正确分析。`-add_delay` 用来在同一端口上保留多条 edge-specific delay。

5. `set_max_delay` 为什么不能直接替代 `create_clock`？

   答：`create_clock` 定义同步时序分析的基本时间坐标和 clock object；`set_max_delay` 只是在特定路径上施加最大延时边界。没有 clock，普通 reg-to-reg、I/O 和多时钟关系仍无法完整表达。

6. path group 权重设置前必须先看什么报告？

   答：先看 `report_timing` 和 `report_constraint -all_violators`，确认当前最差路径、path group 分布和剩余 violation 类型。没有报告依据的权重调整只是盲目优化。

7. 附加选项写完后，怎样证明它真的生效？

   答：用对象集合检查证明命令有目标；用 `report_port -verbose` 或 `report_clock` 看属性；用 `report_timing -from/-to/-through` 看目标路径；用 `check_timing` 和 `report_constraint` 查缺失、冲突和 violation。

## AI+IC 工程落点

NPU、DMA、NoC bridge、SRAM controller 的约束不会只有一条 clock 和一组 I/O delay。真实项目里会有多组时钟、不同接口预算、scan/test 模式、负边沿或双边沿接口、高 fanout 控制、物理负载预算和分层综合优化。附加约束选项就是把这些工程差异精确写给工具的方式。掌握它的标准不是“能背命令”，而是能解释每个选项约束了哪个对象、改变了哪类分析、报告里应出现什么证据，以及误用后会漏掉什么风险。
