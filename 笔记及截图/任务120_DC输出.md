# 任务120：DC 输出

## 本章知识全景图

DC 输出的核心不是“保存几个文件”，而是把同一版综合结果拆成下游工具各自能读懂的交付接口。综合之后，RTL 已经被映射成标准单元和连线；如果只把网表扔给后端，而没有同步时序约束、物理意图、DFT 信息、命名规则和质量报告，下游看到的就是一个缺上下文的电路壳。

| 交付对象 | 它描述什么 | 主要使用者 | 丢失或写错的直接后果 |
|---|---|---|---|
| gate-level netlist | 标准单元实例、端口、net、pin 连接关系 | P&R、Formality、门级仿真、STA | 后端无法摆放真实 cell；形式验证没有 implementation；门级仿真无法复现综合结构 |
| SDC | clock、I/O delay、例外路径、load/drive 等时序意图 | STA、P&R 优化、形式验证辅助检查 | 下游按错误时钟或无约束路径分析，出现假违例、漏违例或过度优化 |
| DDC | Synopsys 内部设计数据库，保留设计、约束和工具属性 | DC、ICC/ICC2、Formality 等 Synopsys 生态工具 | 同生态工具无法快速恢复综合状态；但它不能替代通用网表和 SDC |
| DEF / scan DEF | 物理布局信息或 scan chain 物理交接信息 | P&R、DFT、ATPG、测试后端 | 物理意图断链，scan chain 连接、排序或测试结构在后端重建困难 |
| report | timing、area、power、QoR、constraint、check_design 等证据 | 前端、后端、验证、项目评审 | 无法判断该版综合是否可交付；问题只能在下游失败后倒查 |
| 网表清理动作 | multiple port net、assign、特殊字符、tri/wire 等兼容性处理 | 所有读入网表的下游工具 | 网表可读性差，第三方工具解析失败，netlist 与 SDC 对象匹配失败 |

最短学习路径：先建立“交付包”视角，再分别理解 netlist、SDC、DDC、DEF/scan DEF 和 report 的职责，最后掌握 `set_fix_multiple_port_nets`、`verilogout_no_tri`、`change_names` 这类网表清理动作为什么必须在写出前完成。

## 视觉核对清单

DC 输出图要按“交付包”而不是“文件后缀”读。netlist 是结构图纸，SDC 是时序合同，DDC 是 Synopsys 内部档案，DEF/scan DEF 是物理和测试交接单，report 是验收报告。只交一个网表，就像只把机器外壳交给下游，没有说明书、检验单和接口合同。

| 截图 | 看图要点 | 漏看后果 |
|---|---|---|
| Data Needed for Physical Design or Layout | 不同下游工具需要不同数据 | 以为 `write verilog` 就是综合结束 |
| multiple port net / buffer 修复 | 裸 `assign`、多端口直连要在写出前清理 | 下游读入失败或 Formality 匹配困难 |
| 输出命令汇总 | 清理、命名、写出、report 有依赖顺序 | 文件生成但不同版、不同名、不同约束 |

## 1. DC 输出是一份交付契约，不是单文件导出

综合交付包必须让每个下游工具拿到自己需要的“对象、约束和证据”。P&R 需要标准单元和物理上下文，STA 需要时序约束，Formality 需要可比较的 implementation，DFT/ATPG 需要 scan 结构，项目评审需要报告判断这版结果是否达标。

一个常见误区是把 `write -format verilog` 当成综合结束的全部。网表只能说明“电路由哪些 cell 连接而成”，不能说明“哪些路径应该计时、哪些路径是假路径、端口外部环境怎样、scan chain 怎么接、这版 timing 是否收敛”。这些信息必须通过 SDC、DEF/scan DEF、DFT 文件和 report 一起交付。

正式工程里要遵守同版原则：netlist、SDC、DDC、DEF/scan DEF、report 必须来自同一次综合数据库，使用同一套 library、top name、约束版本和命名规则。只替换其中一个文件会制造隐蔽风险。例如网表经过 `change_names`，但 SDC 仍引用旧对象名，STA 会出现 `can't find object`；DDC 是昨天的，网表是今天的，Formality 可能把真正的功能差异误判成工具读入问题。

## 2. gate-level netlist 交付结构电路

gate-level netlist 是综合后最重要的通用结构文件。RTL 里的 `always`、`case`、算术表达式和连续赋值已经被综合成标准单元实例、连线和端口映射；后端真正摆放的是 `DFF`、`AND`、`MUX`、`BUF`、`INV`、`TIEHI/TIELO` 这类 library cell，而不是 RTL 语句。

| 维度 | RTL | gate-level netlist |
|---|---|---|
| 描述对象 | 功能行为、寄存器传输、组合逻辑意图 | 标准单元实例、net、pin 连接 |
| 使用阶段 | 前端设计、功能仿真、代码评审 | P&R、门级仿真、形式验证、STA |
| 下游关注点 | 功能是否写对 | cell 是否可映射、连接是否可读、命名是否稳定 |
| 典型失败信号 | 仿真功能错误、综合推断异常 | unmapped cell、unresolved reference、illegal name、assign/tri 兼容问题 |

写出网表时常见命令形态是：

```tcl
write -format verilog -hierarchy -output out/my_design.gv
```

`-format verilog` 决定输出为 Verilog 网表，`-hierarchy` 保留层次，`-output` 指定文件。层次是否保留要和项目交付规则一致：保留层次便于 debug、形式验证和局部 ECO；完全 flatten 可能利于某些优化，但会让信号追踪和模块边界变差。

网表交付的最低要求不是“文件存在”，而是下游能读入并定位对象。读入失败通常来自四类问题：library cell 名和后端库不一致、顶层端口和约束不一致、命名含特殊字符导致解析不一致、裸 `assign` 或 `tri` 结构被某些工具误读。任务120后半段重点处理的 multiple port net、`verilogout_no_tri` 和 `change_names`，就是在降低这些兼容性风险。

## 3. SDC 交付时序意图

SDC 是下游理解时序问题的标准语言。网表告诉工具“电路是什么”，SDC 告诉工具“哪些路径要按什么条件检查”。没有 SDC，后端工具即使能读入网表，也不知道主时钟周期、端口外部延迟、异步时钟关系、例外路径、负载和驱动环境。

| SDC 内容 | 它告诉下游什么 | 写错后的后果 |
|---|---|---|
| `create_clock` / generated clock | 时钟源、周期、波形、派生关系 | 同步路径无分析基础；派生时钟路径可能被漏算 |
| input/output delay | 片外逻辑占用的时序预算 | I/O 路径过于乐观或过于悲观，接口 timing 失真 |
| clock uncertainty / latency | 时钟抖动、偏斜、传播模型 | 余量估计错误，后端优化目标漂移 |
| false path | 功能上不需要计时的路径 | 未声明会产生假违例；误声明会掩盖真实违例 |
| multicycle path | 允许多拍完成的路径 | 未声明会强行按单拍优化；误声明会放松真实单拍路径 |
| clock group | 异步或互斥时钟关系 | CDC/异步路径可能被错误计时或错误放过 |
| load/drive | 输入驱动和输出负载模型 | 延迟估计失真，端口路径结果不可信 |

写出 SDC 的典型命令是：

```tcl
write_sdc out/my_design.sdc
```

工程上不能把 SDC 当作 DC 运行脚本的复制品。DC 脚本可以有 `compile_ultra`、优化开关、设计读入命令和调试变量；SDC 只保留约束语义，供 STA、P&R 和其他下游工具解释。视频里强调第三方 layout 工具不理解 DC 私有 compile directives，原因就在这里：下游需要的是标准化约束，不是前端工具操作历史。

SDC 的失败信号很具体：`read_sdc` 后出现 unresolved object、clock 数量不对、端口 delay 没挂上、false path 或 multicycle path 对象为空、report_timing 出现大量 unconstrained endpoints。遇到这些信号，优先检查命名是否和 netlist 同步，top 是否一致，层次路径是否被 flatten 或改名。

## 4. DDC 保留 Synopsys 生态内部状态

DDC 是 Synopsys 工具内部数据库格式。它通常比纯 Verilog 网表携带更多工具状态，例如设计层次、综合属性、部分约束、library 绑定和实现信息。它的价值是让同生态工具快速恢复综合上下文，而不是让所有工具都读它。

```tcl
write -format ddc -hierarchy -output out/my_design.ddc
```

DDC 的正确定位是“内部交接和可恢复快照”。如果后续还要在 DC 中继续调试、在 ICC/ICC2 里读入设计、或在 Synopsys 生态里做形式验证和物理综合联动，DDC 会比重新读入 Verilog 加 SDC 更省事，也更少丢工具属性。

DDC 不能替代正式跨工具交付包。第三方 P&R、STA 或门级仿真工具未必读 DDC；即使读入 Synopsys 工具，项目归档也仍需要可审计的 netlist、SDC 和 report。正式交付时保留 DDC 是加分项，不是通用接口的替代品。

## 5. DEF、scan DEF 和 DFT 信息把物理与测试链路接上

DEF 描述物理设计信息，例如 die/core 区域、row、track、macro、pin、blockage、placement 或其他物理对象。普通逻辑综合并不总是能产出完整物理 DEF，但在 topographical flow、物理感知综合或 scan 相关流程中，DEF/scan DEF 会成为前端和后端之间的重要桥梁。

scan DEF 或 DFT 相关文件服务的是测试结构交接。scan chain 的数量、顺序、scan in/out、scan enable、test mode、lockup latch 或压缩结构如果没有稳定传给后端和 ATPG，后端可能在布局布线时破坏 scan 连接，测试向量生成也会遇到链路不匹配。

| 信息类型 | 下游用它做什么 | 失效后果 |
|---|---|---|
| macro / blockage / placement | 约束物理布局，减少后端重猜设计意图 | macro 位置不合理，拥塞、长线和 timing 问题放大 |
| scan chain order | 保持 scan chain 连接和物理可实现性 | scan stitching 失败，ATPG chain mismatch |
| test mode / scan enable 相关约束 | 区分功能模式和测试模式 | 测试路径被正常模式约束误压，或功能路径被测试逻辑污染 |
| DFT report | 证明 scan 插入、链数量、覆盖率和规则检查状态 | 测试团队无法判断这版是否可进入 ATPG |

DEF/scan DEF 的操作闭环要先承认边界：不是每个 DC 练习都会真实产出这类文件。若当前 flow 只是普通逻辑综合，不要伪造 `write_def` 成果；若使用 DC Graphical、physical-aware synthesis 或 DFT/scan flow，就必须把生成、读回和报告三件事放进验收。

```tcl
    # 1. 物理信息只在当前 flow 已经建立 physical context 时写出
    # 命令名和选项以项目 flow 为准
write_def -output out/TOP_NAME.def

    # 2. scan/DFT 交接只在已经插入或导入 scan chain 后写出
    # 常见项目会有独立 DFT 脚本或后端脚本承接
    # write_scan_def -output out/TOP_NAME.scan.def

    # 3. 生成可审查报告，不只交一个 DEF 文件
report_scan_path  > reports/TOP_NAME.scan_path.rpt
report_dft_signal > reports/TOP_NAME.dft_signal.rpt
```

下游 smoke 也要分清对象。物理 DEF 的读回重点是 unit、die/core、row、macro、pin、blockage 是否可解析；scan DEF 的读回重点是 chain count、scan in/out、scan enable、test mode、lockup latch 和 chain order 是否与 DFT report 一致。它像把厂房地形图和检修通道图一起交给施工队：地形图告诉后端怎么摆，检修通道图告诉测试团队怎么从芯片里把状态串出来，二者不能互相替代。

| 交接物 | 最小读回动作 | PASS 信号 | FAIL 信号 |
|---|---|---|---|
| DEF | 后端/P&R 环境读入 DEF，并检查 die/core、row、macro、pin、blockage | 物理对象数量和坐标可解释 | unit/layer 不匹配，macro 或 blockage 丢失 |
| scan DEF | DFT/P&R/ATPG 环境读入 scan 交接信息 | chain 数量、scan in/out、scan enable 与 report 一致 | chain mismatch、端点找不到、test mode 信号丢失 |
| DFT report | 查 scan path、DFT signal、规则检查 | test signal 可追踪，规则 violation 可解释 | scan enable/test mode 未定义，chain order 不可信 |

对 AI 芯片尤其要重视这类交接。NPU 里通常有 SRAM macro、DMA、NoC、计算阵列和大量寄存器阵列，物理位置和 scan 结构会影响线长、拥塞、时钟树、功耗和测试时间。前端如果只交网表，不交物理或 DFT 上下文，后端会被迫重新推断，风险会在布局布线和测试阶段集中爆发。

## 6. report 是交付包的证据层

report 不是“给人看的附属文件”，而是判断这版输出能否流向下游的证据层。netlist 和 SDC 说明设计对象，report 说明当前对象是否已经通过必要检查。

| 报告 | 应检查什么 | 不合格信号 |
|---|---|---|
| `report_timing` / `report_qor` | WNS/TNS、关键路径、路径分组、优化质量 | 关键路径未收敛，path group 缺失，QoR 异常倒退 |
| `report_area` | cell 面积、层次面积、宏单元占比 | 面积突增，模块面积和预期不符 |
| `report_power` | 动态功耗、静态功耗、时钟功耗 | 时钟网络或组合逻辑功耗异常 |
| `check_design` | 设计结构合法性、未连接、黑盒、宽度等 | unresolved reference、unconnected port、multiple drivers |
| `check_timing` | 时序约束完整性 | unconstrained endpoints、missing clock、invalid generated clock |
| `report_constraint` | max delay、setup/hold、DRC 类约束 | max_transition、max_capacitance、fanout 违规 |
| DFT/scan report | scan chain、test protocol、规则检查 | chain count 不符，scan enable/test mode 不可追踪 |

正式交付时，report 要和交付文件同版归档。否则下游发现 timing 或读入问题时，前端无法判断问题来自综合本身、约束版本、library 版本，还是后端导入方式。

## 7. multiple port net 和 assign 清理决定网表兼容性

multiple port net 指多个端口直接挂在同一条 net 上，或端口、常量、输出之间通过隐式连接形成多端口网络。RTL 里这种写法可能很自然，但写成 gate-level netlist 后，某些下游工具不希望看到大量裸 `assign`、`tri` 或端口直连，因为它们更期待标准单元实例加 pin/net 的结构。

视频给出的关键动作是：

```tcl
set_fix_multiple_port_nets -all -buffer_constants
compile_ultra
```

这条命令的目标不是改变功能，而是把不稳定的连接表达变成显式硬件结构。`-all` 覆盖所有相关 multiple port nets，`-buffer_constants` 会把常量连接也通过 buffer 或 tie cell 形式稳定下来。这样 `assign OUT = IN`、常量直接驱动多个端口等结构会更容易转成下游工具熟悉的 cell-pin-net 关系。

assign 清理要避免两个极端。第一个极端是保留大量裸 `assign`，结果 P&R、门级仿真或形式验证读入时出现兼容问题。第二个极端是手工删除 `assign`，破坏原功能。正确做法是让综合工具在受控命令下插入 buffer/tie cell，并用形式验证或门级仿真确认功能等价。

常见失败信号包括：网表里仍有大批 `assign`，常量没有变成 tie cell，多个 output port 共用一条 net，下游读入时提示 illegal continuous assignment，或者 Formality 把结构清理后的对象匹配失败。这些问题应该在写出网表前修掉，而不是交给后端临时绕开。

## 8. `verilogout_no_tri` 和 `change_names` 解决文本网表的可读性

DC 内部可以管理很多 Verilog 语义细节，但文本网表要被不同工具解析。`tri`、转义名、方括号、反斜杠、特殊符号、层次分隔符等，在不同工具和不同脚本语言里可能解释不一致。

```tcl
set_app_var verilogout_no_tri true
change_names -rules verilog -hierarchy
```

`verilogout_no_tri` 的作用是避免写出三态相关的 `tri` 形式，尽量转成更普通的 `wire` 表达。课程画面里强调“Convert tri to wire - eliminate assign”，要理解成网表文本兼容性处理：让下游少面对 Verilog 语义角落。

`change_names -rules verilog -hierarchy` 的作用是按 Verilog 规则清理层次内对象名。比如 bus 名、转义名、含特殊字符的 cell/net/port 名，如果在 netlist、SDC、DEF 中表现不一致，下游脚本就会找不到对象。命名清理必须和 SDC 同步验证：只改网表不检查约束，等于把问题从 Verilog 文件移动到 SDC 文件。

| 问题 | 表面现象 | 正确处理 |
|---|---|---|
| bus 名带特殊字符 | `read_verilog` 或 `read_sdc` 对同一对象解析不同 | 统一用 Verilog 命名规则写出，并检查 SDC 对象匹配 |
| escaped name | 下游脚本里路径匹配困难 | 写出前层次化改名，避免反斜杠依赖 |
| `tri` 或裸 `assign` | 第三方工具不接受或优化语义不一致 | 设置输出变量，配合 multiple port net 修复 |
| netlist 与 SDC 命名不同步 | SDC 报对象为空、clock 或 delay 没挂上 | 同版写出并做 `read_verilog` + `read_sdc` smoke |

## 9. 推荐脚本顺序：先清理，再写出，再验收

正式脚本不要把命令堆成文件列表，而要体现依赖顺序。网表清理类命令应在写出前生效，约束和网表应来自同一数据库，报告应在同版环境下生成。

```tcl
    # 1. 修复会污染最终网表的连接表达
set_fix_multiple_port_nets -all -buffer_constants
compile_ultra

    # 2. 清理文本网表兼容性
set_app_var verilogout_no_tri true
change_names -rules verilog -hierarchy

    # 3. 写出通用交付文件
write_sdc out/my_design.sdc
write -format verilog -hierarchy -output out/my_design.gv

    # 4. 写出 Synopsys 内部恢复文件
write -format ddc -hierarchy -output out/my_design.ddc

    # 5. 如果当前 flow 产生物理或 scan 交接信息，再写出对应 DEF/DFT 文件
    # write_def -output out/my_design.def

    # 6. 生成同版报告
report_qor        > reports/my_design.qor.rpt
report_timing     > reports/my_design.timing.rpt
report_area       > reports/my_design.area.rpt
report_power      > reports/my_design.power.rpt
check_design      > reports/my_design.check_design.rpt
check_timing      > reports/my_design.check_timing.rpt
report_constraint > reports/my_design.constraint.rpt
```

实际项目脚本要以当前工具版本和公司 flow 为准。学习时重点不在记死文件名，而在记住交付逻辑：清理网表结构，稳定命名，写出标准接口，保留内部数据库，导出物理/DFT 交接信息，最后用报告证明该版输出可被下游接收。

## 10. SVF 是 DC 写给 Formality 的变换账本

DC 输出包里还要特别记住 SVF。它不像 gate netlist 那样描述最终电路，也不像 SDC 那样描述时序意图；SVF 更像综合过程的“翻译账本”，记录 DC 把 RTL 变成网表时做过哪些重命名、寄存器合并、常量传播、FSM 重编码、clock gating 或 datapath 重构。

如果没有 SVF，Formality 面对的就像两份被不同编辑改过名字和段落顺序的合同：内容可能一样，但页码、标题、条款编号都变了。工具只能靠名字和结构硬猜，unmatched 会明显增加，真实功能差异也更难从匹配噪声里分出来。

DC 侧最小动作通常是先打开 SVF 记录，再综合和写出，最后关闭记录：

```tcl
set_svf out/TOP_NAME.svf

compile_ultra

write -format verilog -hierarchy -output out/TOP_NAME.gv
write -format ddc     -hierarchy -output out/TOP_NAME.ddc
write_sdc out/TOP_NAME.sdc

set_svf -off
```

SVF 的验收不是“文件存在”这么简单，而是要能被 Formality 在 match 前读入，并且和同一次综合输出的 netlist/DDC 对得上。若 `TOP_NAME.svf` 来自旧 run，网表来自新 run，Formality 可能得到一份错版字典：它越努力按字典翻译，越可能把本来能匹配的对象引到错误方向。

| DC 输出 | 下游 Formality 用法 | 错版或缺失后的症状 |
|---|---|---|
| `out/TOP_NAME.gv` | 作为 implementation 结构对象 | cell、net、pin 可读但匹配困难 |
| `out/TOP_NAME.ddc` | 作为 Synopsys implementation 快照 | 版本或库不一致时读入失败 |
| `out/TOP_NAME.sdc` | 辅助约束和对象检查 | 对象空、clock/exception 不一致 |
| `out/TOP_NAME.svf` | 在 match 前提供综合变换 guidance | unmatched 激增，retiming/FSM/datapath 难解释 |
| reports | 证明输出来自同一版 run | 无法判断问题来自综合、交付还是验证设置 |

因此 DC 输出后的最小 smoke 不应只跑 `read_verilog` 和 `read_sdc`，还要安排一次 Formality setup 级检查：reference 读 RTL，implementation 读 netlist 或 DDC，match 前读入同版 SVF。SVF 就像把综合这条河上每座桥的位置标出来；没有它，验证工具仍能游过去，但很可能在最宽、最急的地方耗尽时间。

## 工程练习

1. 给 DC 输出包建最小 smoke test。

   合格答案：新开目录读入 gate netlist；读入标准单元库；读入 SDC；确认 top、clock、端口 delay、exception 对象不为空；检查 `check_design/check_timing/report_constraint` 无阻塞级错误；Formality 能以 RTL 为 reference、netlist 或 DDC 为 implementation 建立基本 match。

2. 判断 multiple port net 清理是否成功。

   合格答案：最终 netlist 中裸 `assign` 明显减少或消失，常量连接通过 tie cell/buffer 表达，下游 `read_verilog` 不报 illegal continuous assignment，Formality 不因清理后的对象命名不同大量 unmatched。

## 11. 正式交付包如何验收

交付包验收要从“能不能读、读得对不对、是否同版、是否有证据”四层检查。只看文件是否生成是不够的。

| 检查项 | 验收动作 | 通过标准 | 失败信号 |
|---|---|---|---|
| 文件同版 | 核对输出时间、run id、top、library、约束版本 | netlist、SDC、DDC、report 来自同一次 run | 文件时间混杂，报告 top 和网表 top 不一致 |
| netlist 读入 | 在后端或独立环境 `read_verilog` | 无 unresolved module、unmapped cell、illegal syntax | cell 找不到、端口重复、非法字符、assign 报错 |
| SDC 读入 | `read_sdc` 后检查 clocks、I/O delay、exceptions | clock 数量和预期一致，对象匹配非空 | `can't find object`、unconstrained endpoints 大量出现 |
| DDC 恢复 | Synopsys 工具 `read_ddc` | 可恢复层次、约束和设计对象 | 版本不兼容、library link 失败、设计属性丢失 |
| DEF / scan DEF | P&R/DFT 工具读入 | 物理对象、scan chain 或 test 信息可解析 | scan chain mismatch、placement 信息缺失、DEF unit/layer 不符 |
| multiple port net | 检查网表和工具 warning | 裸 `assign` 和常量多端口连接被控制在项目允许范围 | 大量 `assign`、multiple port net warning、constant driver 异常 |
| 命名一致性 | netlist、SDC、DEF 对象交叉查询 | 特殊字符已清理，约束能命中对象 | 改名后 SDC 失效，层次路径找不到 |
| 报告完整性 | 检查 timing、area、power、QoR、check 类报告 | 关键报告存在且没有阻塞级 error | 缺 report，或 check_design/check_timing 有未解释 error |
| 下游 smoke | 至少跑一次 P&R import、STA read、Formality setup | 能进入下一阶段，不靠手工补文件 | 下游第一步就要求重新导出或手工修网表 |

这张表可以当交付前的硬门。真正合格的 DC 输出包，不是“目录里有 `.gv`、`.sdc`、`.ddc`”，而是这些文件能被下游读入，读入后的对象互相对得上，并且报告能证明这版综合没有把问题甩给后续阶段。

## 12. 和 AI+IC 工程的连接

在小练习里，DC 输出问题看起来只是命令格式；在 NPU 或 AI 加速器工程里，它直接影响后端、验证和测试能否并行推进。计算阵列、SRAM、DMA、NoC 和控制寄存器会制造大量层次、宽 bus、常量连接和 scan 链，任何命名不一致、SDC 对象丢失、scan 信息缺口都会被规模放大。

前端工程师要形成一个交付习惯：综合不是在 `compile_ultra` 结束，而是在下游能稳定读入这版交付包后才结束。能写出网表只是第一步，能解释每个文件给谁用、出了问题看哪个失败信号，才算掌握 DC 输出。

## 自测题与答案

1. 为什么 DDC 不能替代 netlist 和 SDC？

   答案：DDC 是 Synopsys 内部数据库，适合同生态工具恢复综合状态；netlist 和 SDC 是跨工具交付接口。第三方 P&R、STA、仿真或归档流程通常仍需要 Verilog gate netlist、标准 SDC 和报告。

2. gate-level netlist 和 RTL 的核心区别是什么？

   答案：RTL 描述设计行为和寄存器传输，gate-level netlist 描述标准单元实例及其 pin/net 连接。后端摆放的是标准单元，不是 `always` 或 `case` 语句。

3. SDC 写错为什么会比网表语法错更隐蔽？

   答案：网表语法错通常读入阶段就失败；SDC 写错可能仍能读入，但 clock、I/O delay 或 exception 没有正确挂到对象上，导致 STA 结果过松或过紧，后续才暴露 timing 风险。

4. `set_fix_multiple_port_nets -all -buffer_constants` 解决什么问题？

   答案：它把多端口直连和常量连接转成更显式的 buffer/tie cell 等结构，减少最终网表中的裸 `assign` 和下游不兼容连接表达。

5. `change_names -rules verilog -hierarchy` 后为什么必须重新检查 SDC？

   答案：命名规则改变后，SDC 中引用的端口、pin、net 或层次路径可能不再匹配。判定口径是 `read_sdc` 后没有对象为空、clock 和 delay 能挂到预期对象。

6. report 在 DC 输出包里承担什么角色？

   答案：report 是证据层，用来证明这版网表和约束是否通过 timing、area、power、QoR、check_design、check_timing 等检查。没有 report，下游无法判断问题是前端未收敛还是导入阶段产生。

7. DEF 和 scan DEF 的边界是什么？

   答案：DEF 主要描述物理布局对象和物理约束；scan DEF 或 DFT 文件描述 scan chain 和测试结构交接信息。二者都服务后端，但一个偏物理实现，一个偏可测试性链路。

8. 判断一份 DC 输出包是否正式可交付，至少要看哪三类信号？

   答案：第一，看下游能否读入 netlist、SDC、DDC/DEF 等文件且无阻塞错误；第二，看对象是否同版并能互相匹配，例如 SDC 能命中网表对象；第三，看 timing、check_design、check_timing、QoR、DFT 等报告是否存在且无未解释的阻塞级问题。
