# 任务01：数字IC设计流程

## 本章知识全景图

数字 IC 前端不是“把 RTL 写出来”，而是把需求、架构、RTL、验证、综合和时序证据一路收敛到可交付 Netlist。

| 知识块 | 本讲解决的问题 | 必须形成的工程判断 |
|---|---|---|
| 芯片产业链 | 设计公司在产业链里交付什么 | 前端交付设计数据、约束和验证证据，不交付实体芯片 |
| 需求与指标 | 为什么不能直接开始写 RTL | 指标决定架构，架构决定 RTL 的边界和代价 |
| 架构与 RTL | 架构图和代码是什么关系 | RTL 是架构的可综合表达，不是架构的替代品 |
| 仿真与验证 | 怎样证明功能不是“看起来对” | testcase 只能证明局部场景，验证计划要覆盖状态空间 |
| 综合与 STA | 工具把 RTL 推到哪一步 | 综合产出门级网表，STA 判断目标时钟下是否稳定 |
| 形式验证与 DFT | 后续为什么还要查等价性和可测性 | 等价性、防制造缺陷可测性，是功能仿真替代不了的问题 |
| 前后端边界 | 前端做到哪里算可交付 | 前端通常交到 Netlist 和约束证据，后端从物理实现继续收敛 |

最短学习路径：先背流程顺序，再给每一步补上“输入、动作、输出、失败回退”。只会说名词还不算懂；能说出失败时该回 RTL、回 testbench、回约束还是回架构，才开始进入工程视角。

可以把数字前端流程理解成“把一句产品愿望变成施工队能照图施工的工程包”。需求像业主说“我要一栋能住人的楼”，架构像决定几层、几部电梯、承重墙放哪里，RTL 像结构图纸，验证像压力测试和消防验收，综合与 STA 像把图纸换成具体材料并检查梁柱能不能承受目标负载。这个比喻的边界也要记住：芯片不是盖楼，工具会做大量自动优化；但“每一层都要有输入、输出和验收证据”这一点是相通的。

## 1. 芯片价值为什么先从产业链讲起

课程一开始从手机、CPU、基带、存储、摄像头和电源管理芯片讲起，是为了把“芯片很重要”转成岗位边界：数字前端站在设计链路上游，负责把功能意图变成后续制造能接收的设计数据。

![集成电路产业链位置](<./screenshots/任务001_数字IC设计流程/industry_chain_1100s.jpg>)

视频验证：`11:00-11:05`，画面应能看到设计公司、晶圆厂、封装测试、组装厂、成品整机之间的串联关系。

这张图只看三件事：设计公司交付的是设计数据，晶圆厂负责把数据变成硅片，封测厂负责把制造后的芯片变成可测试、可封装、可交付的器件。不要把它当产业科普图背厂名，要把它当“前端错误会向后游走”的责任链。

这张图不要按厂名背，而要按交付物理解：

| 环节 | 主要动作 | 与前端的关系 |
|---|---|---|
| IC 设计公司 | 定义功能、做架构、写 RTL、验证、综合、交付数据 | 数字前端主要在这里工作 |
| 晶圆厂 | 根据设计数据制造晶圆 | 前端的时序、面积、功耗选择会影响实现成本 |
| 封测厂 | 封装芯片并做测试 | DFT 质量会影响测试效率和可测覆盖 |
| 组装厂 | 把芯片装进板级或整机系统 | 芯片接口、功耗和可靠性会在系统中暴露 |

前端虽然不拿烙铁、不做版图、不封装芯片，但前端的错误会向后放大。架构选错会导致面积和性能不收敛；约束写错会导致 STA 假通过或过度悲观；DFT 不充分会导致回片后测不出制造缺陷。

## 2. 数字 IC 设计为什么不从 RTL 开始

RTL 是实现语言，不是需求本身。一个设计必须先说清做什么功能、面向什么系统、接口怎么交互、目标频率是多少、面积和功耗有没有预算，再进入架构和 RTL。

课程里用 FFT 电路举例，真正要保留的是这个拆解口径：

| 设计信息 | 低质量说法 | 工程化说法 |
|---|---|---|
| 功能 | 做一个 FFT | 对输入采样序列做 FFT，输出频域结果 |
| 接口 | 有输入输出 | `clk/rst_n/data_i/valid_i/ready_o/data_o/valid_o` 等信号如何握手 |
| 性能 | 越快越好 | 目标频率、吞吐率、延迟拍数、是否流水 |
| 约束 | 后面再看 | 工艺库、面积上限、功耗目标、时钟约束 |
| 系统位置 | 独立模块 | 上游是谁、下游是谁、是否接总线或 DMA |

![数字 IC 标准设计流程](<./screenshots/任务001_数字IC设计流程/design_flow_2430s.jpg>)

视频验证：`24:20-24:40`，画面应进入标准设计流程页，老师开始把算法、接口定义、RTL coding、仿真等串起来。

这张流程图的关键不是框多，而是每个框都有门禁：上一步没给出足够证据，下一步就会带着假设继续放大错误。比如架构指标没定就写 RTL，后面 timing 违例时你会分不清是代码写法问题，还是一开始并行度就不够。

需求没有收敛，架构就不会稳定；架构不稳定，RTL 就会反复推翻。速度指标会推导出并行度、流水线和缓存策略；功耗指标会推导出时钟门控、低功耗单元和访问模式；面积指标会推导出资源共享和模块边界。这些决定都发生在 RTL 之前。

## 3. 架构不是 PPT，RTL 不是全部设计

架构回答“系统怎样分块和流动”，RTL 回答“这些分块怎样落成可综合电路”。把架构跳过，后面的仿真、综合和 STA 会不断替你补课。

一个小控制器可以把这条链说明白：

1. 需求：收到 `start` 后拉高 `busy`，计数 8 拍后拉高 `done` 一拍。
2. 架构：一个 FSM 控制状态，一个计数器记录拍数，接口包含 `clk/rst_n/start/busy/done`。
3. RTL：状态寄存器、next-state 组合逻辑、计数器、输出逻辑。
4. 仿真：覆盖 reset、单次 start、连续 start、done 宽度、busy 保持时间。
5. 综合：给出时钟约束，检查面积和 timing。
6. 交付：说明接口时序、已验证场景、未覆盖风险、约束文件和报告。

这条链里，RTL 只占第 3 步。没有需求和架构，代码不知道为什么存在；没有仿真、综合和交付证据，代码不能成为工程结果。

架构图像“交通路网图”，RTL 像把每条路、每个红绿灯、每个闸口落成可工作的控制电路。只看 RTL 就像只看某个路口的信号灯程序，看不出整座城市为什么堵；只看架构图不写 RTL，又只是漂亮路线图，没有任何车能真正跑起来。

## 4. 仿真和验证不是同一个词

功能仿真回答“在这些输入场景下输出是否正确”；验证体系回答“应该被检查的状态空间是否被系统性覆盖”。写一个 testbench 跑通几个 testcase 是必要动作，但不能把一次 PASS 当成完整验证。

![仿真与验证分工](<./screenshots/任务001_数字IC设计流程/simulation_verification_2600s.jpg>)

视频验证：`26:00-26:10`，画面应能看到 RTL coding / RTL simulation 与 verification plan / IP level / full chip verification 的分工。

这张图要看分层：左侧更像“把代码跑起来”，右侧更像“证明该查的风险都被查过”。仿真是验证体系里的工具，不是验证体系本身。

前端工程师至少要会搭基础 testbench、组织 testcase、看波形、读日志、定位失败；验证工程师会进一步设计 verification plan、覆盖率模型、随机约束、scoreboard、回归体系和全芯片验证策略。两者相互配合，但问题层级不同。

一个合格的功能仿真证据至少包含：

| 证据 | 作用 |
|---|---|
| testcase 列表 | 说明跑了哪些场景 |
| 预期输出 | 说明什么叫通过 |
| 仿真日志 | 记录 PASS/FAIL |
| 波形 | 用于定位时序、握手、状态跳转 |
| 失败回溯 | 说明 bug 在 RTL、testbench 还是用例假设里 |

## 5. 综合、STA、形式验证、DFT各查不同风险

综合不是把代码“翻译一下”，而是把 RTL 映射到特定工艺库里的门级结构，输出 Netlist。相同 RTL 在不同工艺库、不同约束下，面积、时序和功耗可能完全不同。

![STA 与 DFT 位置](<./screenshots/任务001_数字IC设计流程/sta_dft_3000s.jpg>)

视频验证：`29:58-30:20`，画面应出现 STA、PrimeTime/Tempus、DFT、scan chain 等关键词。

这张图要抓住两个后续接口：STA 把前端逻辑放进时间预算里检查，DFT 把芯片制造后的可测性提前设计进去。它们都不是 RTL 功能仿真的替代品，而是查另外两类风险。

这几个环节的检查对象不能混：

| 环节 | 检查对象 | 不能替代什么 |
|---|---|---|
| 功能仿真 | RTL 在具体输入下的功能行为 | 不能证明所有状态都覆盖 |
| 逻辑综合 | RTL 能否映射到工艺库并满足约束 | 不能证明综合前后完全等价 |
| STA | 时钟约束下路径是否满足 setup/hold | 不能证明功能逻辑正确 |
| 形式验证 | RTL 与综合后网表是否等价 | 不能替代场景级 debug |
| DFT | 芯片制造后缺陷能否被测试结构暴露 | 不能改善功能规格本身 |

STA 的刀句是：它不问“逻辑对不对”，它问“这个逻辑在目标时钟下能不能稳定工作”。形式验证的刀句是：它不靠跑几个输入样例，而是确认 RTL 和网表是不是等价设计。DFT 的刀句是：它面向量产测试，不是功能设计装饰项。

## 6. 前端闭环的终点是 Netlist

前端流程不是从 RTL 直线走到交付，而是一个持续收敛的闭环：代码风格检查、功能仿真、逻辑综合、综合后仿真、STA，每一步失败都可能回到不同位置。

![RTL 到 Netlist 前端闭环](<./screenshots/任务001_数字IC设计流程/frontend_to_netlist_3430s.jpg>)

视频验证：`34:30-34:40`，画面应看到 RTL Code 到 Netlist 的流程，以及代码修改、约束修改的回退路径。

这张图最该看的是回退箭头。前端不是瀑布式“写完往下交”，更像带闸门的循环流水线：某个闸门不过，就要判断回 RTL、回约束、回架构还是回验证计划。

失败回退要按信号判断：

| 失败信号 | 优先回退位置 | 判断理由 |
|---|---|---|
| testcase FAIL | RTL 或 testbench | 功能行为和预期不一致 |
| 波形握手异常 | 接口定义或状态机 | 数据有效、ready/valid、状态跳转可能不一致 |
| 综合报不可综合 | RTL 写法 | 代码结构不能映射硬件 |
| 面积过大 | 架构或资源复用 | 不是简单改语法能解决 |
| STA violation | 时钟/约束/路径/架构 | 需要判断是约束不合理还是路径太长 |
| 形式验证不过 | 综合前后等价性 | 需要查综合设置、黑盒、约束或代码边界 |

前端真正交付的不是“代码写完”，而是 RTL、约束、testbench、仿真日志、波形证据、综合脚本、Netlist、timing/area/power 报告、已知风险说明。这组证据让别人能接着跑、接着查、接着实现。

## 7. 本讲复习与自测答案

| 自测题 | 合格答案 |
|---|---|
| 数字 IC 设计为什么不从 RTL 开始 | 因为 RTL 必须由需求、指标、接口和架构约束推导出来 |
| 架构和 RTL 的区别是什么 | 架构定义模块、接口、数据流和瓶颈，RTL 把它们写成可综合电路 |
| 仿真和验证的区别是什么 | 仿真检查具体场景，验证体系检查覆盖空间 |
| 综合和 STA 的区别是什么 | 综合生成门级网表，STA 检查目标时钟下的时序路径 |
| 形式验证解决什么 | 检查 RTL 与综合后网表是否功能等价 |
| DFT 解决什么 | 让制造缺陷在回片测试中更容易被测出来 |
| 前端和后端通常在哪里交接 | Netlist、约束、报告和验证证据 |

最小练习：选一个计数器、FIFO 或小控制器，写出 `需求 -> 架构 -> RTL -> 仿真 -> 综合 -> STA -> 交付` 七步，每一步至少给一个可检查证据。写不出证据，说明还停在听课层，没有进入工程层。
