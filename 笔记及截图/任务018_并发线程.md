# 任务18：SystemVerilog 并发线程

## 本章知识全景图

### 一眼看懂这讲在讲什么

- **本章主题**：SystemVerilog 仿真中的并发线程如何创建、调度、等待和结束。
- **核心概念**：`initial`、`always`、`begin/end`、`fork/join`、`join_any`、`join_none`、父进程、子进程、仿真时间线。
- **逻辑主线**：SV 并发不是操作系统线程课，而是仿真器在同一条仿真时间轴上调度多个过程；读懂 `fork/join` 的关键是算清父进程何时阻塞、子进程何时结束、未结束线程是否继续存在。
- **最短学习路径**：先理解多个 `initial/always` 天然并发，再区分顺序块和并发块，最后用时间线推导 `join`、`join_any`、`join_none`。

| 概念层级 | 核心概念 | 前置知识 | 延伸应用 |
|---|---|---|---|
| 仿真过程 | `initial` / `always` | 仿真 0 时刻、事件触发 | TB 启动、时钟生成、monitor |
| 语句块 | `begin/end` | 顺序执行 | 把多条语句封装成一个子进程 |
| 并发块 | `fork/join` | 子进程、父进程 | 并行驱动、并行等待 |
| 等待规则 | `join` / `join_any` / `join_none` | 延时、事件等待 | timeout、后台 monitor |
| 生命周期 | 未结束子进程 | 进程清理 | `disable fork`、测试隔离 |

**读 `fork/join` 不要看代码行顺序，要把每个子进程放到同一条仿真时间轴上，再看父进程在 `join` 点按哪条规则继续。**

## 1. SV 并发的起点：多个过程块本来就是并行调度

`initial` 和 `always` 不是按源码上下顺序一个执行完再执行另一个。仿真开始时，多个过程块会被仿真器作为独立过程调度；谁先打印、谁先改变信号，取决于延时、事件和调度区域，而不是文件里的上下位置。

![并发线程主题](<./screenshots/任务018_并发线程/concurrent_intro_165s.jpg>)

🔍 视觉验证：视频 01:37-03:30（并发线程入口页：应看到 `always` 与 `initial` 被放在并行调度语境中。）

例子：

```systemverilog
initial begin
    #10 $display("%0t A", $time);
end

initial begin
    #5  $display("%0t B", $time);
end
```

输出顺序是：

```text
5  B
10 A
```

因为两个 `initial` 都从仿真 0 时刻启动，第二个只等待 5 个时间单位。源码先写 A 不代表 A 先发生。

![initial 与 always 并发](<./screenshots/任务018_并发线程/always_initial_parallel_210s.jpg>)

🔍 视觉验证：视频 02:10-10:20（`always/initial` 对比页：应看到多个过程块不是源码串行执行。）

RTL 里的多个 `always_ff/always_comb` 也要按硬件并行理解。它们描述的是并行存在的电路块，仿真器只是用事件调度模拟这个并行世界。

## 2. `begin/end` 是顺序块，`fork/join` 是并发块

`begin/end` 把多条语句包成一个顺序执行的语句块；`fork/join` 把顶层语句分裂成多个并发子进程。两者都能“包语句”，但时间语义完全不同。

![fork/join 总览](<./screenshots/任务018_并发线程/fork_join_overview_330s.jpg>)

🔍 视觉验证：视频 05:26-06:00（fork 总览页：应看到 `join`、`join_any`、`join_none` 三种等待规则并列。）

顺序块：

```systemverilog
begin
    #10 $display("A");
    #20 $display("B");
end
```

结果：A 在 10，B 在 30。第二条语句要等第一条完成。

并发块：

```systemverilog
fork
    #10 $display("A");
    #20 $display("B");
join
```

结果：A 在 10，B 在 20。两条顶层语句从进入 `fork` 的同一时刻开始计时。

![fork 创建子进程](<./screenshots/任务018_并发线程/fork_join_definition_1345s.jpg>)

🔍 视觉验证：视频 22:24-25:00（fork 子线程图：应看到顶层语句生成子进程，父进程在 `join` 点等待。）

## 3. `fork...join`：父进程等所有子进程结束

`join` 是最严格的等待规则：父进程停在 `join`，直到当前 `fork` 里所有子进程都结束。

```systemverilog
initial begin
    $display("%0t start", $time);

    fork
        #10 $display("%0t A", $time);
        #20 $display("%0t B", $time);
        #30 $display("%0t C", $time);
    join

    $display("%0t after join", $time);
end
```

输出：

```text
0  start
10 A
20 B
30 C
30 after join
```

父进程不是等“第一条子语句”，也不是等“源码最后一条子语句”，而是等最晚结束的子进程。上例最长子进程是 30，所以 `after join` 在 30 打印。

## 4. fork 内的 `begin/end`：多条语句可以合成一个子进程

`fork` 只把顶层语句变成并发子进程。如果顶层语句是一个 `begin/end` 块，那么这个块整体是一个子进程，块内部仍然顺序执行。

![fork 内 begin/end 分组](<./screenshots/任务018_并发线程/begin_end_inside_fork_1670s.jpg>)

🔍 视觉验证：视频 27:49-35:00（fork 内分组图：应看到两个 `begin/end` 块各自作为一个并发分支。）

```systemverilog
fork
    begin
        #10 $display("A1");
        #10 $display("A2");
    end

    begin
        #5  $display("B1");
        #30 $display("B2");
    end
join
```

这里是两个子进程，不是四个：

| 子进程 | 内部顺序 | 完成时间 |
|---|---|---|
| A | `#10 A1`，再 `#10 A2` | 20 |
| B | `#5 B1`，再 `#30 B2` | 35 |

所以父进程在 35 继续。这个规则对 testbench 很重要：如果你希望“一组动作”作为一个并发分支，就必须用 `begin/end` 包住。

## 5. 时间线推导：先找进入 fork 的当前时间

很多 fork 题错在忘记父进程进入 fork 时已经不是 0 时刻。推导时要先写下父进程当前时间，再从这个时间点启动每个子进程。

![时间线推导](<./screenshots/任务018_并发线程/join_timeline_1835s.jpg>)

🔍 视觉验证：视频 30:35-35:00（时间线推导页：应看到各子进程完成点被放到同一条时间轴上比较。）

```systemverilog
initial begin
    #10;
    fork
        #50 $display("%0t A", $time);
        begin
            #20 $display("%0t B1", $time);
            #30 $display("%0t B2", $time);
        end
    join
    #80 $display("%0t after", $time);
end
```

推导：

1. 父进程先 `#10`，进入 fork 时是 10。
2. A 子进程：10 + 50 = 60。
3. B 子进程：10 + 20 + 30 = 60。
4. `join` 等到 60。
5. 父进程再 `#80`，所以 `after` 在 140。

一旦养成这种时间线写法，`fork/join` 就不再靠猜。

## 6. `fork...join_any`：任意一个子进程结束，父进程就继续

`join_any` 只等最早结束的子进程。它常用于“多个条件谁先完成就采用谁”的场景，比如响应等待和 timeout 竞争。

![join_any 规则](<./screenshots/任务018_并发线程/join_any_rule_2405s.jpg>)

🔍 视觉验证：视频 40:05-45:00（`join_any` 规则页：应看到父进程在最早完成分支之后继续。）

```systemverilog
fork
    #50 task_a();
    #20 task_b();
    #80 task_c();
join_any

$display("%0t after join_any", $time);
```

父进程在 20 继续，因为 `task_b` 最早结束。但这并不表示 `task_a` 和 `task_c` 自动结束。它们仍可能继续运行，除非你显式清理。

testbench 常用模式：

```systemverilog
fork
    drive_transaction();
    monitor_response();
    timeout_watchdog();
join_any
disable fork;
```

`join_any` 负责“先拿到一个结果就继续”，`disable fork` 负责“停止其他还没结束的分支”。如果漏掉清理，旧 monitor 或 timeout 可能污染下一轮测试。

## 7. `fork...join_none`：父进程不等待，子进程成为后台过程

`join_none` 表示父进程不在这里等待子进程结束。它适合启动后台 monitor、coverage collector、长时间观察任务，但必须有生命周期管理。

![join_none 规则](<./screenshots/任务018_并发线程/join_none_rule_2605s.jpg>)

🔍 视觉验证：视频 43:25-47:00（`join_none` 规则页：应看到父进程不等待，子进程以后台过程存在。）

```systemverilog
initial begin
    fork
        #10 $display("%0t A", $time);
        #20 $display("%0t B", $time);
    join_none

    $display("%0t parent continue", $time);
    #100 $display("%0t parent done", $time);
end
```

推导时要注意一个细节：`join_none` 产生的子进程通常会等父进程遇到阻塞语句或终止后才开始推进。也就是说，不能简单说“所有东西立刻一起跑”，还要看父进程 `join_none` 后面有没有 `#delay`、`wait`、事件控制或结束。

后台线程的风险：

- 旧 monitor 继续监听，导致下一轮 test case 打印旧结果。
- 旧 timeout 继续跑，晚些时候误报错误。
- 后台驱动还在改变接口信号，污染新的 transaction。

因此 `join_none` 适合“启动后台”，不适合“忘记后台”。

## 8. 延时题的通用解法

![延时推导题](<./screenshots/任务018_并发线程/delay_reasoning_3020s.jpg>)

🔍 视觉验证：视频 50:20-52:00（延时推导题页：应看到 fork 内最大完成时间与父进程后续延时被合并计算。）

通用步骤：

1. 标出父进程当前时间。
2. 每遇到一个 `fork`，列出顶层子进程。
3. 每个子进程内部如果有 `begin/end`，按顺序累加。
4. `join` 取最大完成时间。
5. `join_any` 取最小完成时间，但保留其他子进程风险。
6. `join_none` 父进程立即继续，但要看子进程启动和清理。
7. 最后把父进程后续 `#delay` 加上。

可以把每个子进程写成表格：

| 分支 | 起点 | 内部延时 | 完成时间 |
|---|---:|---:|---:|
| A | 10 | 50 | 60 |
| B | 10 | 20 + 30 | 60 |
| C | 10 | 80 | 90 |

看到表格后，`join`、`join_any`、`join_none` 的差异会非常清楚。

## 9. RTL 并行和 testbench 并发不要混为一谈

硬件天然并行，RTL 用多个 `always_ff/always_comb`、连续赋值和模块实例描述这种并行。`fork/join` 则主要是仿真过程调度能力，常用于 testbench 中同时驱动、监控、等待和超时。

| 场景 | 推荐写法 | 原因 |
|---|---|---|
| 描述寄存器更新 | `always_ff @(posedge clk)` | 可综合时序逻辑 |
| 描述组合选择 | `always_comb` / `assign` | 可综合组合逻辑 |
| 同时驱动和监控 DUT | `fork...join_any` + 清理 | testbench 并发流程 |
| 启动后台 monitor | `fork...join_none` | testbench 后台任务 |
| 等所有并行动作结束 | `fork...join` | testbench 同步点 |

不要因为硬件并行就随手在 RTL 里写 `fork`。设计硬件结构时，应把并行性写成明确的电路结构；验证环境中，才用 `fork/join` 表达多条仿真流程。

## 10. 和 AI+IC / NPU 学习的连接

NPU 验证里，`fork/join` 会高频出现：一个线程喂输入 feature map，一个线程收输出 activation，一个线程做 scoreboard，一个线程守 timeout。真正会用并发线程，不是能背 `join_any` 定义，而是能保证一轮测试结束后没有残留线程污染下一轮。

典型 NPU testbench 结构：

```systemverilog
task automatic run_one_case(input case_cfg_t cfg);
    fork
        drive_input_stream(cfg);
        collect_output_stream(cfg);
        timeout_watchdog(cfg.max_cycles);
    join_any

    disable fork;
    check_scoreboard();
endtask
```

这里的核心是生命周期：任何一个分支先完成，都要明确是否应该停止其他分支。如果是 timeout 先完成，可能要报错；如果是 collector 收完，可能要停止 driver/timeout 并检查结果。并发线程写得好，回归才稳定。

## 11. 深层理解：fork/join 管的不是“快慢”，而是生命周期

`fork/join` 最容易被理解成“并行跑，所以更快”。这个理解不够。它真正管理的是父进程和子进程的生命周期：父进程什么时候停下来等，什么时候继续往下走，留下的子进程是否还在后台运行。

可以把父进程想成项目经理，把子进程想成几支小组：

- `join`：经理等所有小组都交付，才开下一会。
- `join_any`：任意一组先交付，经理就先继续，但其他小组不会自动下班。
- `join_none`：经理把任务派出去后立刻离开，小组继续在后台干。

这个比喻的重点是“没等不代表不存在”。很多 testbench 不稳定，不是因为语法错，而是上一轮 case 留下的后台线程还在驱动信号、打印日志或触发 timeout。

## 12. 配图复盘：用时间线读懂每个分支

| 配图 | 读图重点 | 推导动作 |
|---|---|---|
| 并发线程主题 | 本讲对象是仿真线程 | 不要把它直接等同于 RTL 硬件并行 |
| initial 与 always 并发 | 多个过程从仿真时间 0 启动 | 先画全局时间轴 |
| fork/join 总览 | 三种 join 形式 | 标注父进程何时继续 |
| fork 创建子进程 | 顶层语句如何变成子进程 | 分清每个分支的起点 |
| fork 内 begin/end 分组 | begin/end 把多语句合成一个子进程 | 不要把块内每句误算成独立分支 |
| 时间线推导 | 延时如何叠加 | 进入 fork 的当前时间是基准 |
| join_any 规则 | 最早结束分支让父进程继续 | 其他分支是否清理要另行判断 |
| join_none 规则 | 父进程不等待 | 后台线程可能跨越后续代码 |
| 延时推导题 | 从例题检验规则 | 用表格列出分支开始/结束时间 |

## 13. 操作闭环：并发题的四列表

遇到 fork/join 延时题，用四列表，不要靠感觉：

| 分支 | 开始时间 | 分支内部延时 | 结束时间 |
|---|---:|---:|---:|
| 子进程 A | 进入 fork 的时间 | `#delay` 累加 | 开始 + 延时 |
| 子进程 B | 进入 fork 的时间 | `#delay` 累加 | 开始 + 延时 |
| 子进程 C | 进入 fork 的时间 | `#delay` 累加 | 开始 + 延时 |

然后再判断：

- `join`：父进程继续时间 = 最大结束时间。
- `join_any`：父进程继续时间 = 最小结束时间；其余分支仍可能运行。
- `join_none`：父进程继续时间 = 进入 fork 的当前时间；所有子进程在后台继续。

工程上还要补最后一步：如果父进程继续后要结束本轮 case，就必须决定是否 `disable fork`、`wait fork` 或等待 scoreboard drain。并发线程像放出去的无人机，起飞很容易，难的是知道什么时候回收、哪些还在空中、哪一架已经失控。

## 复习与自测

1. **推导题**：两个 `initial` 块分别 `#10` 和 `#5` 后打印，谁先打印？  
   **答案**：`#5` 的先打印。两个 `initial` 从仿真 0 时刻并发启动。

2. **判断题**：`fork` 内每一行代码都是一个独立子进程。  
   **答案**：不严谨。`fork` 内每条顶层语句是一个子进程；如果顶层语句是 `begin/end`，块内部多条语句属于同一个子进程并顺序执行。

3. **推导题**：进入 fork 时刻为 10，三个子进程延时分别为 20、50、80。`join`、`join_any` 后父进程分别何时继续？  
   **答案**：`join` 在 90 继续，等最晚完成；`join_any` 在 30 继续，等最早完成。

4. **工程题**：为什么 `join_any` 后常接 `disable fork`？  
   **答案要点**：`join_any` 只让父进程在第一个子进程结束后继续，其他子进程不会自动结束；`disable fork` 用于清理同一 fork 作用域中残留分支，避免后台线程污染后续测试。

## 工程核对口径

本章合格标准：

1. 能画出任意 `fork/join` 代码的父进程继续时间。
2. 能解释 `join_any` 和 `join_none` 后为什么可能残留后台线程。
3. 能说明 `begin/end` 在 fork 内怎样改变“子进程数量”。
4. 能把 `fork/join` 用在 testbench driver、monitor、timeout、scoreboard，而不是滥用于 RTL。
5. 能在一轮 case 结束前写出清理或等待策略。
