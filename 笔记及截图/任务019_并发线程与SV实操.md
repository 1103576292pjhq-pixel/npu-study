# 任务19：并发线程与 SV 实操

## 本章知识全景图

### 一眼看懂这讲在讲什么

- **本章主题**：把上一讲的 `fork/join` 语义落到可运行的 VCS + Makefile 练习中，用日志输出验证并发线程推导。
- **核心概念**：`join_any`、`join_none`、`wait fork`、`disable fork`、VCS、Makefile、`TEST_CASE`、`$display`。
- **逻辑主线**：并发语法只有通过可复现仿真才算真正学会；本讲先处理子进程生命周期，再用 Makefile 选择练习文件，用 VCS 编译运行，用 `$display` 的时间和顺序反证自己的推导。
- **最短学习路径**：复习 join 规则 -> 理解 `disable fork` / `wait fork` -> 进入工程目录 -> 用 Makefile 参数选 case -> 运行 VCS -> 用输出检查时间线。

| 概念层级 | 核心概念 | 前置知识 | 延伸应用 |
|---|---|---|---|
| 并发语义 | join_any / join_none | 父子进程、仿真时间 | timeout、后台 monitor |
| 线程清理 | `disable fork` / `wait fork` | fork 作用域 | 防止测试污染 |
| 编译工具 | VCS | SystemVerilog 文件 | 生成仿真可执行程序 |
| 工程入口 | Makefile / `TEST_CASE` | 命令行、变量 | 批量切换练习 |
| 结果证据 | `$display` 输出 | `$time`、日志 | 验证调度理解 |

**实操不是把命令跑通，而是让“输入文件、编译命令、运行结果、时间线推导”形成闭环；如果输出顺序解释不出来，语法就还没真正掌握。**

## 1. 从 `join_none` 复习进入：父进程不等，不代表子进程消失

`join_none` 的陷阱是“父进程继续”和“子进程生命周期”被混在一起。父进程可以立刻往后执行，但 fork 里的子进程仍然存在，只是作为后台过程推进。

![join_none 练习题](<./screenshots/任务019_并发线程与SV实操/join_none_question_300s.jpg>)

🔍 视觉验证：视频 04:50-05:10（`fork_join_none` 例题页：应看到题目要求判断哪些 `$display` 会出现以及出现时间。）

推导 `join_none` 时要写三行：

```text
父进程进入 fork 的时刻：T0
父进程 join_none 后是否遇到阻塞：#delay / wait / event / finish
子进程从何时开始推进、何时结束
```

如果只凭“父进程不等”下结论，很容易漏掉后台线程继续打印、继续改变量、继续触发 timeout 的风险。上一讲的 `join_none` 是机制，本讲开始把它变成可验证的输出顺序。

## 2. `disable fork`：清理当前 fork 作用域里还没结束的分支

`join_any` 经常和 `disable fork` 连用：前者让父进程在任意一个子进程结束后继续，后者终止当前 fork 作用域中剩余未完成的子进程。没有 `disable fork`，先完成的分支只是让父进程往后走，其他分支还可能继续污染环境。

![disable fork 语义](<./screenshots/任务019_并发线程与SV实操/disable_fork_830s.jpg>)

🔍 视觉验证：视频 13:42-14:20（`disable fork` 讲解页：应看到它用于退出当前 fork 作用域里尚未结束的分支。）

经典模式：

```systemverilog
fork
    begin
        wait_device_1();
        winner = 1;
    end
    begin
        wait_device_2();
        winner = 2;
    end
    begin
        wait_device_3();
        winner = 3;
    end
join_any

disable fork;
```

语义链：

1. 三个分支并发等待。
2. 任意一个设备先响应，`join_any` 让父进程继续。
3. 父进程执行 `disable fork`，停止另外两个仍在等待的分支。
4. 后续测试只处理胜出的那个响应。

`disable fork` 的作用域必须小心。复杂 testbench 中最好把竞争逻辑包在一个独立 task 或命名 fork 块内，避免把同一父进程下不相关的后台线程也杀掉。

## 3. `wait fork`：有时不是清理，而是等待所有子进程完成

`disable fork` 用于“不要再等了，剩下的停掉”；`wait fork` 用于“父进程前面创建的子进程都结束后再继续”。二者解决的是不同生命周期问题。

| 语句 | 作用 | 典型场景 |
|---|---|---|
| `join` | 在 fork 末尾等待所有子进程 | 当前并发块必须全部完成 |
| `join_any` | 等任意一个完成 | 响应和 timeout 竞争 |
| `join_none` | 父进程不等待 | 后台 monitor |
| `disable fork` | 停止当前 fork 作用域未完成进程 | 结束竞争、清理 timeout |
| `wait fork` | 等待当前进程派生的子进程全部结束 | 后台任务收尾 |

并发线程的实操价值就在这里：你不只要知道线程能开，还要知道它们何时该结束、何时该被杀、何时必须等到全部完成。

## 4. 进入 VCS 实操：先确认目录、文件和 Makefile

软件操作型视频不能只记录“运行 VCS”。真正可复现的入口是：当前目录是什么，练习文件在哪里，Makefile 怎样把文件名传给 VCS，运行结果怎样回到 `$display`。

![VCS 与 Makefile 实操入口](<./screenshots/任务019_并发线程与SV实操/vcs_makefile_intro_890s.jpg>)

🔍 视觉验证：视频 14:28-20:30（VCS 实操入口：应看到画面从并发语法切到 Linux/Vim/VCS 目录和 Makefile。）

操作链：

```bash
pwd
ls
vim Makefile
make clean
make TEST_CASE=fork_join_any.sv
```

每一步都要有检查目标：

| 步骤 | 检查什么 | 失败信号 |
|---|---|---|
| `pwd` | 是否在练习目录 | 编译找不到文件 |
| `ls` | 是否有 `.sv` 和 Makefile | `No rule to make target` |
| 看 Makefile | VCS 命令和变量是否正确 | 变量名不一致 |
| `make clean` | 清掉旧产物 | 老 simv 干扰判断 |
| `make TEST_CASE=...` | 跑指定文件 | 运行了错误 case |

## 5. Makefile 的 `TEST_CASE`：把“跑哪个练习”参数化

Makefile 不是本讲重点，但它是仿真可复现的入口。`TEST_CASE` 变量让你不用每次手写长 VCS 命令，只需要换一个源文件名就能切换练习。

![Makefile 变量](<./screenshots/任务019_并发线程与SV实操/makefile_variables_1465s.jpg>)

🔍 视觉验证：视频 24:20-25:20（Makefile 变量页：应看到 `TEST_CASE` 指向当前要编译的 SV 文件。）

简化写法：

```makefile
TEST_CASE ?= fork_join.sv
SIM       ?= simv

all:
	vcs -sverilog $(TEST_CASE) -o $(SIM)
	./$(SIM)

clean:
	rm -rf $(SIM) csrc simv.daidir ucli.key *.log
```

命令行覆盖：

```bash
make TEST_CASE=task_function.sv
make TEST_CASE=fork_join.sv
make TEST_CASE=fork_join_any.sv
make TEST_CASE=fork_join_none.sv
make TEST_CASE=disable_fork.sv
```

![Makefile 文件目标](<./screenshots/任务019_并发线程与SV实操/makefile_file_target_2225s.jpg>)

🔍 视觉验证：视频 23:20-28:30（Makefile 文件选择页：应看到 `TEST_CASE`、源文件名和 VCS 命令三者如何对齐。）

常见错误：

- `TEST_CASE` 指向不存在的 `.sv` 文件。
- Makefile 里变量名叫 `TESTCASE`，命令里却写 `$(TEST_CASE)`。
- 源文件依赖 package/interface，但 VCS 只编译一个文件。
- 没有 clean，旧 `simv` 让你误以为新代码运行了。

## 6. 编译通过不等于行为正确：`$display` 才是并发语义证据

VCS 编译通过只说明语法和依赖基本过关；并发线程是否按预期调度，要看仿真输出里的时间戳和打印顺序。

![make 编译运行](<./screenshots/任务019_并发线程与SV实操/make_run_1645s.jpg>)

🔍 视觉验证：视频 24:55-27:30（make 运行页：应看到 VCS 编译命令执行并生成仿真可执行程序。）

![display 输出结果](<./screenshots/任务019_并发线程与SV实操/display_output_1825s.jpg>)

🔍 视觉验证：视频 29:50-30:10（`$display` 输出页：应看到日志时间和打印顺序，用来反推 join 规则是否理解正确。）

读输出时按这四问：

1. 这一行由哪个子进程打印？
2. 打印时 `$time` 是多少？
3. 它为什么先于/晚于另一行？
4. 当前 join 类型改变了父进程的哪个继续点？

示例：

```systemverilog
initial begin
    fork
        #50 $display("%0t long", $time);
        #10 $display("%0t short", $time);
    join_any
    $display("%0t parent", $time);
    disable fork;
end
```

期望输出：

```text
10 short
10 parent
```

如果 `long` 也在 50 打印，说明 `disable fork` 没有按预期清理，或者你清理的不是同一个 fork 作用域。

## 7. 按语法点选择练习文件：每个 case 都要先写预期

练习不是把所有文件都 make 一遍，而是每个文件对应一个语义点。运行前先在纸上或笔记里写预期输出，再用日志验证。

![选择不同 test case](<./screenshots/任务019_并发线程与SV实操/test_selection_2825s.jpg>)

🔍 视觉验证：视频 47:00-50:15（练习文件列表页：应看到多个 case 文件按不同并发语法点组织。）

建议顺序：

| 练习文件 | 先验证什么 | 通过标准 |
|---|---|---|
| `task_function.sv` | task/function 调用与参数副作用 | 输出值符合预期 |
| `fork_join.sv` | `join` 等所有子进程 | 父进程最后继续 |
| `fork_join_any.sv` | 最早完成分支让父进程继续 | 父进程时间等于最小完成时间 |
| `fork_join_none.sv` | 父进程不等待后台进程 | 后台输出仍可出现 |
| `disable_fork.sv` | 清理未结束分支 | 被杀分支不再输出 |

🔍 视觉验证：视频 48:05-48:25（fork/join + task 练习页：应看到并发分支与 task 调用组合出现。）

每跑一个 case，至少记录：


这比“我运行过了”更接近工程训练。

## 8. 操作失败时先定位链路，不要直接怀疑语法

VCS 实操失败大致分三层：文件链路、编译链路、行为链路。不要一上来就改 SV 代码。

| 失败现象 | 先查 | 常见原因 |
|---|---|---|
| `make: *** No rule` | Makefile 是否存在、目标名是否正确 | 不在目录、文件名错 |
| VCS 找不到文件 | `TEST_CASE`、相对路径 | 变量指向错误 |
| package/interface 未定义 | 编译文件列表 | 只编了一个文件 |
| 编译通过但输出不对 | `$display` 时间线 | join 规则推导错 |
| 输出多了旧分支 | `disable fork` / 后台线程 | 未清理子进程 |

并发语法的 bug 经常不是“语法错误”，而是“生命周期没有收尾”。这也是 `join_any`、`join_none` 实操一定要看输出的原因。

## 9. 最小可复现实验：响应与 timeout 竞争

下面是把本讲内容压缩成一个可练习的最小 test：

```systemverilog
module tb;
    initial begin
        fork
            begin
                #30;
                $display("%0t response arrived", $time);
            end
            begin
                #100;
                $display("%0t timeout", $time);
            end
        join_any

        $display("%0t parent continues", $time);
        disable fork;
        #10 $finish;
    end
endmodule
```

期望输出：

```text
30 response arrived
30 parent continues
```

`timeout` 不应在 100 打印，因为 `disable fork` 已经把未完成的 timeout 分支停止。这个实验比背定义更能检查你是否真的理解 `join_any + disable fork`。

## 10. 和 AI+IC / NPU 学习的连接

NPU 验证常见结构是“驱动输入、收集输出、timeout、scoreboard 并发运行”。Makefile 参数化和 `$display` 输出判读是最低成本的验证闭环；后面换成 UVM、cocotb 或更复杂的仿真脚本，本质仍是同一件事：输入可追溯，运行可复现，输出可解释。

一个 NPU test case 至少要保留：

```text
TEST_CASE 或 seed
输入 tensor / transaction 配置
编译运行命令
关键输出日志
timeout 是否被清理
scoreboard 是否通过
```

如果这些证据缺失，仿真“跑过”不等于设计可信。

## 11. 深层理解：实操不是“跑一下”，而是建立可复现证据链

并发线程语法如果只停留在纸面推导，容易产生假理解。任务 19 的价值是把 `fork/join` 放进 VCS/Makefile 实操：你要能选择 case、运行、读 `$display`、解释输出顺序，并在失败时知道是时间线推错、Makefile 参数错，还是残留线程没清理。

可以把这套流程看成法庭证据链：

| 证据 | 证明什么 |
|---|---|
| `TEST_CASE` | 本轮到底跑的是哪个实验，不是凭记忆 |
| Makefile 变量 | 输入如何传给 VCS，流程是否可重复 |
| 编译日志 | 语法、文件列表和宏是否通过 |
| `$display` 输出 | 并发时间线是否符合预期 |
| 波形或截图 | 输出顺序背后的信号/时间关系 |
| `clean` | 下一轮不会受旧产物污染 |

没有证据链的“跑过了”不算验证；它更像口头保证。工程上真正可信的是：给别人同一份目录和同一条命令，别人也能得到同样输出，并能解释每一行日志。

## 13. 操作闭环：一轮并发实操的标准记录

每跑一个 case，都记录这 6 行：

```text
case 名称：
手推预期输出：
运行命令：
实际输出：
是否有残留线程：
结论与下一步：
```

失败时按三层定位：

| 层次 | 典型问题 | 检查动作 |
|---|---|---|
| 文件链路 | case 文件没选中、旧产物未清 | `make clean`，确认 `TEST_CASE` 和 filelist |
| 编译链路 | 语法或宏错误 | 读 compile log，定位文件行号 |
| 行为链路 | 输出顺序不符合预期 | 重画时间线，查 join 类型、`begin/end` 分组、`disable fork` 作用域 |

这套记录以后可以直接迁移到 NPU 回归：case/seed、输入配置、运行命令、日志、波形、scoreboard 结论都必须可追溯。

## 复习与自测

1. **判断题**：`join_any` 结束后，其他子进程会自动停止。  
   **答案**：错。`join_any` 只让父进程继续，其他子进程仍可能运行，需要 `disable fork` 等方式清理。

2. **操作题**：为什么建议 `make clean` 后再 `make TEST_CASE=...`？  
   **答案要点**：清理旧 `simv`、中间目录和日志，避免旧产物干扰判断，确保本轮输出来自当前文件。

3. **结果判读题**：VCS 编译通过但 `$display` 输出顺序不符合预期，先查什么？  
   **答案要点**：先查自己的时间线推导、join 类型、`begin/end` 分组、后台线程是否清理；编译通过只说明语法过关。

4. **工程题**：用一句话说明 Makefile 在本讲中的作用。  
   **答案**：Makefile 把 VCS 编译运行流程参数化，让每个 `TEST_CASE` 可以用固定命令复现，并把输入文件和输出日志对应起来。

## 工程核对口径

本章通过标准：

1. 能用 Makefile 参数稳定切换不同 `TEST_CASE`。
2. 每个 case 运行前能写出手推输出，运行后能逐行对照 `$display`。
3. 编译通过但行为不对时，先查时间线和线程清理，而不是乱改语法。
4. 能解释 `disable fork` 的作用域，避免误杀或漏杀后台线程。
5. 能把一次小实验沉淀成可复现记录，给下一轮回归复用。
