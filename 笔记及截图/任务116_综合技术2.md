# 任务116：综合技术2

## 本章知识全景图
这一讲把综合优化从“技术清单”推进到“收敛流程”：pipeline 或 retiming 解决长路径，multi-core 减少 runtime，first compile 后读 report，再用 incremental compile 和 path group 权重定向优化；如果仍有不可接受 violation，就必须改约束或改 RTL。

| 流程节点 | 解决的问题 | 判断标准 |
|---|---|---|
| pipeline | 组合路径太长，频率上不去 | 是否允许增加 latency、面积、功耗 |
| register retiming | pipeline 分布不均，某级仍违反 | 是否允许移动寄存器位置和名字 |
| multi-core optimization | 综合 runtime 太长 | 是否只是加速运行，而非修复设计 |
| report_constraint | 总体还有哪些 violation | 先看全局问题类别 |
| report_timing | 最差路径慢在哪里 | 看 path、cell delay、net delay、slack |
| incremental compile | first compile 后继续定向优化 | 对剩余 critical path 加强 effort |
| modify constraint / RTL | 优化仍无法收敛 | 判断问题来自约束还是结构 |

![pipeline 仍违反 timing 的场景](<./screenshots/任务116_综合技术2/video_dense_01_02m43s.jpg>)

最短学习路径：先理解 pipeline 和 retiming 的结构变化；再掌握 compile/report/incremental 的闭环；最后学会判断 violation 是否可接受，以及什么时候必须回到约束或 RTL。

## 视觉核对清单

这一讲的图要按“收敛回路”读：pipeline/retiming 是改路，multi-core 是加工人，incremental compile 是返工修重点，timing report 是验收单。加工人不会修坏路，返工也必须先看验收单，否则只是更快、更贵地绕圈。

| 截图 | 看图要点 | 漏看后果 |
|---|---|---|
| pipeline / retiming | 用寄存器边界重新分配组合 delay | 以为所有 timing violation 都能靠 sizing 解决 |
| multi-core optimization | 多核只缩短 runtime，不改变 QoR 本质 | 把加速当成修 timing |
| incremental compile | first compile 后读报告再定向加强 | 盲目 incremental，面积/功耗涨但问题没变 |
| optimization summary | compile 前要先设 hierarchy、retiming、path group、runtime 策略 | 选项后补无效或影响不清 |
| timing report | 看 path group、slack、cell/net delay、required time | 不知道该改 RTL、约束还是物理环境 |

## 1. pipeline：切短 data path，但会增加 latency 和寄存器
如果一条组合 data path 太长，周期被最慢 stage 限制。pipeline 的做法是在路径中插入寄存器，把长组合逻辑切成多个较短 stage。

```text
原始：RegA -> long combinational path -> RegB
pipeline：RegA -> logic1 -> RegP1 -> logic2 -> RegP2 -> RegB
```

收益是频率提高，代价是寄存器增加、面积功耗增加、数据延迟增加。它适合吞吐优先的 datapath，不适合严格 latency 或协议周期固定的控制路径。

## 2. retiming：移动寄存器，让 slack 重新分配
pipeline 后仍违反 timing，说明寄存器切分位置可能不合理。register retiming 允许工具移动、合并、拆分寄存器，把组合逻辑延时重新分配到 pipeline stage。

![retiming solution](<./screenshots/任务116_综合技术2/video_dense_02_05m26s.jpg>)

视频里的方案包括：

```tcl
set_optimize_registers true [get_designs pipeline_block]
compile_ultra -scan -timing -retime
```

retiming 的直觉：如果前一级 path 负 slack，后一级有大量正 slack，可以把寄存器边界移动，让两级负担更均衡。

retiming 的边界必须非常清楚。不能随便移动的寄存器包括：软件可见状态寄存器、CDC 同步链、scan/test 特殊寄存器、协议边界寄存器、和外部接口严格对齐的寄存器。对这些点使用 `set_dont_retime` 或保留层次，是在保护功能和验证边界，不是保守落后。

![resulting pipeline](<./screenshots/任务116_综合技术2/video_dense_03_08m10s.jpg>)

注意边界：

- retiming 会改变寄存器位置。
- 可能改变寄存器名字。
- scan/DFT、形式验证、调试脚本要配合。
- 固定位置寄存器需要 `set_dont_retime`。

## 3. multi-core optimization：加速综合，不修复错误约束
`set_host_options -max_cores` 允许 `compile_ultra` 使用多核并行处理。

![multi-core optimization](<./screenshots/任务116_综合技术2/video_dense_04_10m53s.jpg>)

```tcl
set_host_options -max_cores 4
compile_ultra
```

它解决 runtime，不解决约束完整性、RTL 结构问题或环境属性缺失。如果约束对象错了，多核只是更快地产生错误结果。

## 4. incremental compile：first compile 后对剩余关键路径定向加强
first compile 后要先分析报告，再决定是否 incremental。不要把 incremental 当成固定仪式。

![incremental compile](<./screenshots/任务116_综合技术2/video_dense_05_13m37s.jpg>)

典型流程：

```tcl
compile_ultra -scan -timing -retime
report_constraint -all_violators
report_timing

    # only if remaining critical paths need more effort
compile_ultra -scan -timing -incremental
```

incremental compile 会花更多 runtime，也可能增加面积或功耗。它适合剩余 violation 有明确优化空间的情况，不适合掩盖错误约束。

## 5. 仍然违反约束：先判断是否可接受
如果 incremental 后仍有 timing 或 DRC violation，第一步不是继续堆选项，而是判断 violation 是否可接受。

![still violating constraints](<./screenshots/任务116_综合技术2/video_dense_06_16m20s.jpg>)

可接受的情况：

- 约束故意保守，真实目标没有那么紧。
- violation 很小，并有后端优化空间。
- 项目允许降频、留风险或阶段性 waiver。

不可接受的情况：

- 真实频率目标无法满足。
- DRC/transition/max cap 明显超限。
- report_timing 指向 RTL 结构过深、fanout 太大、pipeline 不足。

不可接受时只有两条主路：

1. 修改约束并重新综合：如果发现 clock、input/output delay、uncertainty、path group 设置不合理。
2. 修改 RTL 并从头再跑：如果路径结构本身不可收敛。

## 6. 综合优化脚本汇总：first compile 前要先设策略
视频中给出 optimization summary before first compile。它不是让你机械复制，而是提醒：很多优化策略必须在 compile 前设置。

![optimization summary before first compile](<./screenshots/任务116_综合技术2/video_dense_07_19m04s.jpg>)

```tcl
    # control hierarchy / boundary
set_boundary_optimization [get_designs sub] false
set_ungroup [get_designs keep_hier] false

    # control retiming
set_dont_retime [get_cells fixed_reg*] true
set_optimize_registers true [get_designs pipeline_block]

    # path groups
group_path -name INPUTS  -from [all_inputs]
group_path -name OUTPUTS -to [all_outputs]
group_path -name COMBO   -from [all_inputs] -to [all_outputs]
group_path -name REG2REG -from [all_registers] -to [all_registers]

    # runtime
set_host_options -max_cores 4
```

![optimization summary with notes](<./screenshots/任务116_综合技术2/video_dense_08_21m47s.jpg>)

脚本注释要写清楚目的：为什么禁 boundary optimization、为什么保留 hierarchy、为什么某些寄存器不能 retime。否则后续维护者不知道这些选项是在保护架构边界，还是历史遗留。

## 7. compile、analyze、incremental 的闭环
完整收敛流程：

![compile analyze incremental compile](<./screenshots/任务116_综合技术2/video_dense_09_24m31s.jpg>)

```tcl
compile_ultra -scan -timing
report_constraint -all_violators
report_timing

    # if needed
group_path -name critical_range -weight 5 -from ... -to ...
compile_ultra -scan -timing -incremental
report_constraint -all_violators
report_timing
```

关键是 analyze。没有 report 分析的 incremental，是盲目加 effort。

## 8. timing report：先看整体，再看 path information
`report_timing` 默认报告每个 path group 中 worst slack 的路径。读报告时不要只看 slack 数字，要看路径结构。

![timing reports](<./screenshots/任务116_综合技术2/video_dense_10_27m14s.jpg>)

Path information section 至少要看：

- startpoint / endpoint
- launch clock / capture clock
- path group
- data arrival time
- data required time
- slack
- cell delay 和 net delay 分布
- transition / capacitance 是否异常

![path information section](<./screenshots/任务116_综合技术2/video_dense_11_29m58s.jpg>)

常用选项：

![report timing options](<./screenshots/任务116_综合技术2/video_dense_12_32m41s.jpg>)

```tcl
report_timing -delay max
report_timing -from [get_clocks Clk1] -to [get_clocks Clk2]
report_timing -through [get_pins U1/Z]
report_timing -nworst 10 -max_paths 20
report_timing -path full
```

如果 report 里 cell delay 高，可能要看逻辑结构或 cell sizing；如果 net delay 高，可能与 fanout、负载、物理相关；如果 required time 异常，可能是约束设置错。

报告驱动决策可以压缩成三条：

| 报告症状 | 优先解释 | 下一步 |
|---|---|---|
| cell delay 占比高 | 组合逻辑太深、cell 太弱、算术结构差 | 看 DesignWare、重构 RTL、pipeline/retiming |
| net delay 占比高 | fanout 大、负载大、物理距离或拥塞 | register replication、buffer、物理约束/后端协同 |
| required time 异常 | clock、uncertainty、I/O delay、exception 或 path group 错 | 先修约束，不要盲目 incremental |

## 工程练习

1. 写出 compile-analyze-incremental 的 PASS/FAIL。

   合格答案：first compile 后必须有 `report_constraint` 和 `report_timing`；剩余 violation 的路径类型、slack、cell/net delay 分布可解释；incremental 后 WNS/TNS、violator 数量或目标 path group 有改善；若没有改善，要停止堆选项，回查约束或 RTL。

2. 判断 timing violation 该改 RTL 还是改约束。

   合格答案：若 required time、clock、delay、path group 明显不合理，先改约束；若约束真实且 report 指向组合级数过深、fanout 大、pipeline 不足，则改 RTL；若 net delay 占比高，可能要引入物理约束或后端协同。

## 复习与自测
1. pipeline 和 retiming 的区别是什么？  
   答：pipeline 增加寄存器切短路径；retiming 移动/合并/拆分寄存器，重新分配已有或允许优化的 pipeline 边界。

2. incremental compile 前为什么必须先读报告？  
   答：只有报告能说明剩余 violation 来自哪类路径、是否有优化空间、是否需要调整 path group 或约束。

3. 多核优化为什么不能解决 timing violation 的根因？  
   答：它只减少 runtime，不改变 RTL 结构、约束语义或环境属性。

4. timing violation 不可接受时，什么时候改 RTL？  
   答：当约束真实、report 指向组合逻辑过深、fanout 太大、pipeline 不足或结构不可优化时，必须改 RTL。

## AI+IC 连接
NPU datapath 的频率收敛常常依赖 pipeline、retiming 和 report-driven incremental compile。关键不是把所有选项都打开，而是判断哪些寄存器可以移动、哪些控制路径不能增加 latency、哪些 violation 应该靠 RTL 重构解决。AI 芯片工程中的 PPA 收敛，本质就是这种“微架构边界 + 综合报告 + 后端现实”的闭环。
