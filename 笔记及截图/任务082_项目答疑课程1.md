# 任务82：项目答疑课程1

## 本章知识全景图

这节答疑课解决的是 SD host CMD 通路最容易混成一团的几类问题：命令号到底是什么、双向 CMD 线什么时候由 Host 驱动、命令帧怎样逐位送出、响应为什么从某个 offset 才开始保存，以及 CRC7 何时生成、接收和比较。它不是百科式 SD 协议课，而是一次 RTL 读码纠偏：把零散提问整理成一条可以在波形和代码里核对的机制链。

逻辑主线很短：先分清 `command_index` 和 `argument`，再分清 `out_command_direction` 和 CMD 数据位；发命令时用 `sd_command_pos` 与 `shift_r` 逐位吐出命令帧，收响应时按协议前缀跳过 offset，把 payload 与 CRC 分开保存，最后用本地重算 CRC 和卡返回 CRC 形成闭环。

| 机制节点 | 关键对象 | 一句话结论 | 读 RTL 时的检查点 |
|---|---|---|---|
| 命令字段 | `in_command_index`、`in_command_argument` | `command_index` 是 6 bit 命令号，`argument` 才是命令携带的 32 bit 参数 | 不要把 CMD7/CMD16/CMD17 的编号和 RCA、block length、address 混成同一类数据 |
| 双向线方向 | `out_command_direction` / `out_cmd_dir` | direction 是输出使能，不是 CMD 线上发送的 0/1 数据 | `0` 的含义是 Host 不驱动总线，不等价于“正在接收数据位 0” |
| 命令帧输出 | `sd_command_pos`、`shift_r`、`in_has_send_bit` | 当前输出位和后续缓存位被拼成一组移位链 | reset 默认高电平，发送起点再拉出 start bit |
| 响应截取 | `in_has_receive_bit`、`response0..3`、`in_serial_cmd` | 前缀位不进 payload，短响应和长响应的保存窗口不同 | short response 从 bit 7 开始存 32 bit；long response 最高段只有 24 bit 有效 |
| CRC 闭环 | `receive_crc_reg`、`generate_crc_reg`、`out_cmd_receive_crc_error` | 接收 CRC 和本地重算 CRC 必须在完整窗口后比较 | short response 在 46，long response 在 134 附近比较，不能提前判错 |

最短学习路径：

1. 先把 SD 命令帧记成 `start + transmission + index + argument + CRC7 + end`。
2. 再把 CMD pad 记成一根双向线：Host 发命令时驱动，等卡响应时释放。
3. 然后用发送计数器解释 `sd_command_pos/shift_r` 的装载与移位。
4. 最后用接收计数器解释 payload offset、CRC 接收窗口和 CRC 比较时刻。

## 1. 先把命令号和参数拆开

`in_command_index` 的含义只有一个：它是 SD 命令帧里的 6 bit 命令号。CMD7、CMD16、CMD17 这些名字里的数字，就是这个字段的取值；真正随命令变化而解释的数据，是另一个 32 bit 的 `in_command_argument`。

| 字段 | 位宽 | 例子 | 应该怎样理解 |
|---|---:|---|---|
| `in_command_index` | 6 bit | CMD7、CMD16、CMD17 | 协议规定的命令类型，告诉卡“我要执行哪种动作” |
| `in_command_argument` | 32 bit | RCA、block length、block address | 当前命令携带的参数，具体含义由命令号决定 |

![command index 搜索定位](<./screenshots/任务082_项目答疑课程1/task82_01_command_index_search.jpg>)

这张图的教学作用是把问题落回真实 RTL：`grep in_command_index` 后可以看到该信号进入 `sd_cmd_send_shift_register.v`，并被拼进待发送命令帧。读到这类代码时，不要问“这个 7 是不是数据 7”，而要问“这里是不是正在发 CMD7”。如果是 CMD16，那么 `argument` 往往才是 block length；如果是 CMD17，`argument` 往往才是读地址。

命令帧可以先用这个结构记住：

```text
start bit 0
+ transmission bit 1
+ command index 6 bit
+ argument 32 bit
+ CRC7 7 bit
+ end bit 1
= 48 bit command frame
```

这个结构解释了后面两个问题：为什么发送端要按 bit 计数，为什么 CRC7 只覆盖前面的固定窗口，而不是把 end bit 也算进去。

## 2. `out_command_direction` 是双向 pad 的输出使能

`out_command_direction` 不是 CMD 线上真正传出去的数据位，它控制的是 Host 端是否驱动这根双向 CMD 线。Host 发送命令时要驱动；命令发完以后，Host 必须释放 CMD 线，让 SD 卡有机会拉低 start bit 并返回 response。

| 状态 | `out_command_direction` 的合理含义 | 为什么 |
|---|---|---|
| `CMD_STATE_SEND` | `1` | Host 正在把命令帧逐位送到卡，必须驱动 CMD |
| `CMD_STATE_STOP` | `0` | 发送已结束，Host 不应继续占线 |
| `CMD_STATE_WAIT_RECEIVE` | `0` | Host 等待卡响应，必须释放双向线 |
| `CMD_STATE_RECEIVE` | `0` | Host 只采样卡返回的数据，不驱动 CMD |

![command direction 答疑](<./screenshots/任务082_项目答疑课程1/task82_02_command_direction_answer.jpg>)

图中答疑的关键点是第二条：`out_cmd_dir=0` 并不自动等价于“receive 操作正在发生”。它只说明 Host 当前不驱动 CMD。`CMD_STATE_STOP` 和 `CMD_STATE_WAIT_RECEIVE` 也会让 direction 为 0，因为这两个状态都不能继续推总线。真正的 receive 要看状态机是否进入接收状态，以及输入采样计数器是否已经捕捉到响应帧。

这里还容易混 `command_pos` / `command_neg`。它们不是一个表示高电平、一个表示低电平，而是同一条 CMD 输出逻辑在不同时钟边沿或不同采样相位上的版本。高速模式下用 pos/neg 版本，是为了满足接口时序和数据推出相位，不是为了创造两个协议字段。

## 3. `sd_command_pos` reset 为 1，是在保护空闲态

CMD 线的空闲态是高电平，start bit 才是低电平。`sd_command_pos` reset 为 1，不是把 start 误写成 end，也不是随手给的默认值，而是让输出寄存器在复位后自然站到空闲态。

![sd_command_pos reset 为 1](<./screenshots/任务082_项目答疑课程1/task82_03_sd_command_post.jpg>)

这张图对应的问题是：“`sd_cmd_pos <= 1'b1` 里的 1 是不是 end，0 是不是开始？”正确口径是：reset 阶段不在发送命令帧，谈不上当前位属于 start 还是 end；它只是让 CMD 输出寄存器默认等于总线空闲值。这样即使输出使能在异常情况下短暂打开，也更像 idle，而不是让对端误以为新命令帧已经开始。

写 RTL 时，这类默认值的判断标准不是“仿真主路径能不能跑通”，而是“复位、软复位、状态跳转时会不会在外部接口上制造非法边沿”。在接口类设计里，空闲态默认值通常比内部寄存器好不好看更重要。

## 4. `{sd_command_pos, shift_r}` 是当前输出位加 8 位后备队列

`{sd_command_pos, shift_r}` 这种拼接赋值不要按“新定义了一个 9 bit 协议字段”理解。左边的 1 bit 是当前要推出到 CMD pad 的输出寄存器，后面的 8 bit 是下一批待移出的缓存。一次并行装载后，后续周期再按 bit 逐步向外移。

![shift assignment 9 bit 搬运](<./screenshots/任务082_项目答疑课程1/task82_04_shift_assignment.jpg>)

图中的第二个问题提到 `in_has_send_bit[2:0] == 3'b0`，它通常意味着发送计数走到某个 8 bit 边界，可以重新装载下一组待输出位。这个写法的工程意图是减少逐位拼大 mux 的复杂度：每 8 个 bit 做一次并行准备，中间周期只做移位。

可以用下面的抽象模型理解，不需要把它当成真实源码逐字对应：

```verilog
// 当前周期推出 sd_command_pos，后续 bit 留在 shift_r。
{sd_command_pos, shift_r} <= next_9_bits;

// 后续周期继续把 shift_r 里的 bit 推到 sd_command_pos。
{sd_command_pos, shift_r} <= {shift_r, next_tail_bit};
```

这段逻辑在波形里应该表现为两件事：`sd_command_pos` 每个发送 bit 周期都稳定给出当前 CMD 位；`shift_r` 在装载边界更新一组值，然后在非边界周期继续移位。如果验证时只盯 `shift_r`，不同时看 `sd_command_pos`，就会漏掉真正推出到 pad 的那一位。

## 5. CRC7 是按发送窗口更新的 LFSR，不是事后附上的神秘常数

CRC7 的 RTL 本质是固定反馈的移位寄存器：每输入一个参与保护的 bit，就根据多项式反馈更新一次 `crc_reg`。它不是靠查表随便填出的 7 bit，也不是等完整命令帧拼完后再临时算一个常数。

对 SD 命令帧来说，CRC7 的直观边界是：

```text
参与 CRC7 更新：start bit + transmission bit + command index + argument = 40 bit
不参与 CRC7 更新：CRC7 字段本身 + end bit
```

所以代码里常见的写法是：发送前 40 bit 时持续更新 CRC；进入 CRC 字段输出窗口后停止更新，把已经稳定的 CRC 寄存器逐位送出；最后再发送 end bit。这个边界解释了“为什么 40 bit 后要停下来”：如果继续把 CRC 字段也喂回 CRC 生成器，得到的就不是协议规定的 command CRC。

答疑里还问到“要不要单独检查 command CRC”。Host 端发送 command CRC 后，真正检查这个 CRC 的是卡。Host 能观察到的是卡是否给 response、response 是否超时、response CRC 是否正确。因此 Host 端再对自己发出去的 command CRC 做一套完整自检，通常收益低、复杂度高；更有效的闭环是把发送、等待响应、接收 CRC 和错误分支做完整。

## 6. response offset 从 7 开始，是因为前缀不是 payload

接收 response 时，不能从 `in_has_receive_bit == 0` 就把所有串行位塞进 `response0`。响应帧前面有协议前缀，例如 start、transmission、命令索引或保留字段；CPU 或上层控制逻辑真正关心的是后面的 payload。

![response offset 答疑](<./screenshots/任务082_项目答疑课程1/task82_06_response_offset.jpg>)

这张图的教学作用是把 offset 和寄存器位宽连起来看。短响应里，`in_has_receive_bit >= 7` 到 `<= 38` 正好保存 32 bit payload；所以 `response0 <= {response0[30:0], in_serial_cmd}` 是合理的左移串入：旧的低 31 位上移，新采到的串行位进入最低位。

长响应更容易误读。R2 类长响应常要保存 120 bit 有效 payload，但代码用 `response3..response0` 四个 32 bit 寄存器承接。`4 x 32 = 128` 比 120 多 8 bit，所以最高段 `response3` 不会被完整写满：

| 接收窗口 | 保存目标 | 实际保存位数 | 读法 |
|---|---|---:|---|
| 7-30 | `response3` | 24 bit | 最高有效段，不是完整 32 bit |
| 31-62 | `response2` | 32 bit | 中间 payload |
| 63-94 | `response1` | 32 bit | 中间 payload |
| 95-126 | `response0` | 32 bit | 最低 payload |

如果复查或调试时看到 `response3[30:0]` 参与移位，不要立刻判定位宽错误。关键要看这个寄存器被写入多少次、最终哪些 bit 被上层使用。这里的“看似 32 bit 寄存器”只是 RTL 承载容器，有效数据范围由接收窗口定义。

## 7. 接收 CRC 和本地生成 CRC 必须分成两条线

`receive_crc_reg` 和 `generate_crc_reg` 不能混用。前者保存的是卡在 response 末尾发来的 CRC 位；后者是 Host 用自己刚接收到的 response 内容重新计算出来的 CRC。两条线只有在各自窗口都结束后才有比较意义。

![receive CRC 寄存器答疑](<./screenshots/任务082_项目答疑课程1/task82_07_receive_crc_register.jpg>)

图里可以看到长响应时 `in_has_receive_bit >= 127 && <= 133` 的窗口会把 7 bit 串入 `receive_crc_reg`。短响应同理，只是窗口更早，通常在 payload 之后的 39-45。这里的 `in_serial_cmd` 不是“应该放在 CRC 前面还是后面”的抽象问题，而是同一根 CMD 输入线上按时间顺序采到的当前 bit：处在 payload 窗口时，它参与 payload 保存和本地 CRC 生成；处在 CRC 窗口时，它进入 `receive_crc_reg`。

这也是验证时最容易出错的地方。测试平台不能只检查最后的 `out_cmd_receive_crc_error`，还要能解释错误来自哪里：

| 错误类型 | 典型波形表现 | 应该检查 |
|---|---|---|
| payload offset 错 | `response0..3` 整体错位，CRC 也可能随之错 | `in_has_receive_bit` 的 payload 保存窗口 |
| 接收 CRC 窗口错 | payload 正确，但 `receive_crc_reg` 少一位或多一位 | 39-45 或 127-133 的窗口边界 |
| 本地 CRC 更新错 | `receive_crc_reg` 对，但 `generate_crc_reg` 不对 | CRC 多项式反馈、更新使能、初值和停止时刻 |
| 比较过早 | 两个 CRC 还没稳定就报错 | `out_cmd_receive_crc_error` 的赋值条件 |

## 8. CRC 比较点是响应接收的最后一道闸

CRC 比较必须等 response payload 和 response CRC 都完整接收后再做。短响应的比较点比长响应早，长响应因为 payload 更长，比较点自然推迟。

![CRC 比较时刻答疑](<./screenshots/任务082_项目答疑课程1/task82_08_crc_compare_timing.jpg>)

图中的关键条件是：短响应在 `in_has_receive_bit == 46` 附近比较，长响应在 `in_has_receive_bit == 134` 附近比较。比较表达式本身并不复杂：

```verilog
out_cmd_receive_crc_error <= !(generate_crc_reg == receive_crc_reg);
```

真正重要的是这个表达式出现的状态和计数位置。它必须在 `CMD_STATE_RECEIVE` 中发生，必须位于 CRC 位全部采完之后，必须区分 long response 和 short response。任何一个条件错位，都会造成“RTL 看起来有 CRC 比较，但系统行为不可信”。

这条闭环可以用一行检查路径概括：

```text
Host 发 command -> 释放 CMD -> 等 card response -> 保存 payload -> 接收 response CRC -> 本地重算 CRC -> 比较 -> 给出错误/成功分支
```

这也是为什么本节不建议把 command CRC 再孤立做一套 Host 自检。对 SD host 控制器来说，更有工程价值的是保证这条闭环不断：发错命令要能 timeout，收错响应要能 CRC error，收对响应要能稳定进入后续数据或状态处理。

## 9. 把答疑问题落成 RTL 和验证检查点

这节答疑课的核心产物不是几句定义，而是一组可检查的设计规则。写 RTL 或看波形时，可以按下面顺序排查：

| 检查点 | 看什么 | 通过口径 |
|---|---|---|
| 命令字段 | `in_command_index` 与 `in_command_argument` | index 只决定命令类型，argument 按命令语义解释 |
| 输出方向 | `out_command_direction` 与状态机 | 只有发送命令时 Host 驱动 CMD，等待和接收阶段释放 |
| 空闲默认值 | reset 后 `sd_command_pos` | 默认为 1，不制造伪 start bit |
| 移位链 | `sd_command_pos`、`shift_r`、`in_has_send_bit` | 装载边界和逐位输出一致，当前输出位没有丢 |
| payload offset | `in_has_receive_bit` 与 `response0..3` | 前缀位跳过，短/长响应窗口符合协议长度 |
| CRC 接收 | `receive_crc_reg` | 只在 response CRC 窗口串入 7 bit |
| CRC 生成 | `generate_crc_reg` | 只在受保护数据窗口更新，进入 CRC 字段后不继续吃 CRC 本身 |
| CRC 比较 | `out_cmd_receive_crc_error` | 等两个 CRC 都稳定后再比较，长短响应比较点不同 |

如果要把它写进 testbench，最小验证集不需要一开始就铺很大：先构造一个短响应成功用例、一个短响应 CRC 错误用例、一个长响应成功用例、一个 response timeout 用例。每个用例都要在波形里能回答三件事：Host 什么时候释放 CMD，payload 从哪个 bit 开始保存，CRC 在哪个 bit 比较。

## 自测题

1. `in_command_index = 7` 表示什么？  
   答：表示当前命令号是 CMD7。它不是参数值 7，参数要看 `in_command_argument`。

2. `out_command_direction = 0` 是否一定表示正在 receive？  
   答：不一定。它只表示 Host 不驱动 CMD；`CMD_STATE_STOP`、`CMD_STATE_WAIT_RECEIVE` 和 `CMD_STATE_RECEIVE` 都可能让它为 0。

3. `sd_command_pos` reset 为 1 的原因是什么？  
   答：CMD 空闲态是高电平，reset 为 1 能避免复位后在外部 CMD 线上制造伪 start bit。

4. `{sd_command_pos, shift_r}` 为什么可以按 9 bit 移位链理解？  
   答：因为 `sd_command_pos` 是当前要推出的 1 bit，`shift_r` 是后续 8 bit 缓存。二者拼接赋值是在一起装载或移位，不是协议新增了 9 bit 字段。

5. command CRC7 为什么在前 40 bit 后停止更新？  
   答：SD 命令帧中参与 CRC7 的是 start、transmission、command index 和 argument，共 40 bit；CRC 字段本身和 end bit 不应再反馈进 CRC 生成器。

6. short response 为什么从 `in_has_receive_bit >= 7` 开始保存 payload？  
   答：0-6 附近是 response 的协议前缀，不是上层要读的 32 bit payload；从 7 开始保存才能让 `response0` 对齐有效数据。

7. long response 用四个 32 bit 寄存器保存时，为什么最高段只有 24 bit 有效？  
   答：有效 payload 是 120 bit，`4 x 32` 是 128 bit，多出的 8 bit 不是有效 payload，所以最高寄存器只需要承接 24 bit。

8. `receive_crc_reg` 和 `generate_crc_reg` 的区别是什么？  
   答：`receive_crc_reg` 保存卡发来的 7 bit CRC；`generate_crc_reg` 是 Host 根据收到的 response 内容本地重算出的 CRC。二者稳定后才能比较。

9. CRC 比较为什么不能提前做？  
   答：提前比较时，payload、接收 CRC 或本地生成 CRC 可能还没完整稳定，错误标志会变成计数错位造成的假错误，而不是协议 CRC 真错。

10. 验证这段 CMD 通路时，最小应该覆盖哪些场景？  
    判定口径：至少覆盖短响应成功、短响应 CRC 错、长响应成功、response timeout；每个场景都能在波形里说明 direction 释放点、payload 保存窗口和 CRC 比较点。
