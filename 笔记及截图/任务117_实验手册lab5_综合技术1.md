# 任务117：实验手册 lab5 综合技术 1

## 本章知识全景图
这节课不是教“再跑一次 DC”，而是教你把一个有层次、有时序目标、有 floorplan 约束的设计，按真实综合交付流程跑到可检查状态。

| 知识单元 | 解决的问题 | 本节结论 |
|---|---|---|
| lab5 定位 | 为什么叫综合技术实验 | 目标是把约束、脚本、网表、报告、物理意图串成闭环 |
| design specification | 跑综合前必须先读什么 | top、端口、层次、clock、pipeline、blockage、timing critical 都会变成命令或报告检查项 |
| DC Graphical | 为什么不用普通 compile 思维 | DCG 在综合阶段引入 topographical / floorplan 信息，提前暴露物理实现风险 |
| 多核运行 | 为什么先看 CPU 资源 | 综合优化搜索空间大，多核决定运行时间和优化可承受度 |
| 结果验收 | 怎么判断实验不是“跑完就算” | timing、area、physical、netlist、SDC/DDC/report 都要有证据 |

最短学习路径：先把 PDF 里的 design spec 逐条翻译成综合约束，再看 DCG 如何用 floorplan 约束指导 compile，最后用报告和输出文件判断能不能交给后端。

## 1. lab5 的主线：从规格到可交付综合结果
lab5 的价值在于把“综合”从单点命令变成工程闭环。你不只是执行 `compile_ultra`，还要证明综合满足设计规格，且输出能进入后端、STA、形式验证或后续检查。

| 验收对象 | 要检查什么 | 失败信号 |
|---|---|---|
| timing | clock、I/O 约束、critical path、WNS/TNS | 负 slack、未约束路径、假路径漏设 |
| area / QoR | 面积、buffer 数量、层次优化效果 | 面积异常膨胀、复制逻辑过多 |
| physical | floorplan、blockage、placement density | standard cell 进入禁放区，局部拥塞过密 |
| hierarchy | input/middle/output、pipeline 模块边界 | 层次被误 flatten，后续 ECO/验证难定位 |
| output | gate netlist、DDC、SDC、report | 下游工具无法读入或对象缺失 |

如果只看工具是否退出，就会把“脚本跑完”误当成“设计收敛”。真正的综合结果必须能被报告证明、被下游工具读取、被后端继续优化。

## 2. design specification 是脚本的来源，不是课件背景
视频中展示的 PDF 规格包括 top 名、输入输出端口、module 层次、pipeline 模块、output register、instance location、floorplan 和 timing critical 要求。每一项都要落到脚本或检查表里。

| 规格项 | 脚本/检查落点 | 为什么不能跳过 |
|---|---|---|
| design top name | `current_design`、`link`、输出文件命名 | top 错了，所有报告都在比错对象 |
| input/output | `set_input_delay`、`set_output_delay`、load/drive | 接口环境漏建模会造成虚假的 timing 通过 |
| clock input | `create_clock`、clock uncertainty/latency | 没有时钟就没有同步时序分析 |
| pipeline block | 层次保留、单独优化、路径检查 | 误优化会破坏可读性和验证映射 |
| fixed instance | placement / dont_touch / location 约束 | 固定对象被移动会违反物理规格 |
| output register | 输出接口结构检查 | 非寄存输出会放大接口时序风险 |

读规格的顺序比敲命令更重要：先知道“这个设计必须长成什么样”，再判断命令是否把它综合成了那个样子。

## 3. DC Graphical 的关键不是界面，而是物理感知
DC Graphical / topographical 模式会在逻辑综合阶段参考物理信息。课程里给出 core size，并指定左上角一块区域不可放置 standard cell。这说明综合阶段已经开始考虑后端可实现性。

这一步的真实目的有三个：

1. 提前估计线长和拥塞，避免普通 DC 里乐观的 timing 在后端崩掉。
2. 把 blockage、macro、instance location 等物理意图纳入综合优化。
3. 让前端输出不只是布尔等价网表，而是更接近可布局布线的结构。

对 NPU、DMA、NoC、SRAM-heavy 设计尤其重要。宽数据通路和存储宏会让局部拥塞、长线和时钟树压力放大；前端如果完全不看物理信息，后端会用更高代价替你补课。

## 4. 终端实操要抓住“状态变化”
视频中间进入 VNC 和 lab5 目录，先检查 CPU 核数，再启动 DCG/脚本。这个过程的重点不是 UI 操作，而是环境可复现。

| 操作 | 目的 | 成功信号 |
|---|---|---|
| 进入 lab5 目录 | 让相对路径和脚本约定成立 | RTL、script、report、output 都能找到 |
| 查看 CPU 核数 | 判断综合可用并行资源 | 工具能多核运行，compile 时间可接受 |
| 启动 DCG/topographical | 让物理约束生效 | floorplan 相关命令不报不支持 |
| 执行 Tcl | 固化流程，避免手敲不可复现 | log 能记录每步命令和输出 |
| 查看 report | 把结果从“跑过”变成“可验收” | timing/QoR/physical 报告可读 |

终端截图里后半段出现大量 report 输出，这正是综合实验的高价值部分：它让你看到脚本实际跑到了哪里、工具接受了哪些输入、最终吐出了哪些证据。

## 5. lab5 最小可复现实验链
lab5 的操作链要像一次有监理记录的施工：先确认自己站在正确工地，再确认材料、图纸和地形约束都装进工具，最后看验收单，而不是只看机器有没有响过。

一个可复现实验链可以压成下面的骨架。具体目录名和脚本名以课程环境为准，但职责顺序不能乱：

```sh
cd lab5
ls rtl scripts constraints reports out logs
nproc
dc_shell-topo -f scripts/run.tcl | tee logs/lab5.log
```

```tcl
set_host_options -max_cores 4

read_verilog [glob rtl/*.v]
current_design TOP_NAME
link

source constraints/top.sdc
    # 读入 floorplan、blockage、placement 或 topographical 相关设置
    # 具体命令以实验脚本为准

check_design
check_timing
compile_ultra

write -format verilog -hierarchy -output out/TOP_NAME.gv
write -format ddc     -hierarchy -output out/TOP_NAME.ddc
write_sdc out/TOP_NAME.sdc

report_qor        > reports/TOP_NAME.qor.rpt
report_timing     > reports/TOP_NAME.timing.rpt
report_area       > reports/TOP_NAME.area.rpt
report_constraint > reports/TOP_NAME.constraint.rpt
check_design      > reports/TOP_NAME.check_design.rpt
check_timing      > reports/TOP_NAME.check_timing.rpt
```

这段骨架里最容易被新手漏掉的是 `link`、`check_timing` 和输出报告。`link` 像把图纸上的每个零件号和仓库里的真实零件对上；`check_timing` 像验收前确认所有时钟、I/O 和例外路径都有合同；report 则是最后能交给别人复核的签字页。

| 环节 | PASS 信号 | FAIL 信号 |
|---|---|---|
| 目录与路径 | `rtl/constraints/scripts/reports/out/logs` 都能找到 | 相对路径失效，脚本找不到 RTL 或 SDC |
| 读入与 link | top 存在，无 unresolved module | top 名错、库缺失、模块悬空 |
| 约束加载 | clock、I/O delay、critical path 对象存在 | unconstrained endpoints、empty collection |
| DCG / topographical | 物理约束相关命令被接受 | floorplan/blockage 命令无效或被忽略 |
| compile | 无阻塞级 error，QoR/timing report 生成 | 只看到命令结束，没有任何验收报告 |
| 输出交付 | netlist、DDC、SDC、report 同版生成 | 只生成网表，缺 SDC 或 report |

## 6. 本节的工程判断口径
| 问题 | 合格回答 |
|---|---|
| 为什么要读 design spec | 因为综合脚本的对象、约束和验收条件都来自 spec |
| 为什么 DCG 要考虑 floorplan | 因为 timing、area 和拥塞在物理实现中耦合，逻辑综合不能完全脱离布局 |
| 为什么要输出报告 | 报告是判断约束是否满足的证据，不是附属文件 |
| DFT 在本节做不做 | 不做。课程提到 scan insertion 由 test group 后续执行，本实验只记录边界 |
| 什么时候算本实验通过 | 输出文件存在，报告显示约束满足，物理约束未违反，下游工具可继续读 |

## 工程练习

1. 给 lab5 建一页验收表。

   合格答案：列出输入 RTL、约束、库、floorplan/physical 约束；列出输出 netlist、DDC、SDC、report；检查 `report_qor/report_timing/report_area` 是否存在；确认 WNS/TNS、约束 violation、物理相关 warning 都可解释。没有证据文件的“通过”不能算通过。

2. 判断 DCG/topographical 的价值。

   合格答案：它把物理估计提前带入综合，帮助 timing 和拥塞更接近后端；但它不能替代 P&R，也不能保证最终布局无拥塞。它像在设计阶段先看地形图，不是已经修好了路。

## 自测与答案
1. DCG 和普通 DC 思维的关键差别是什么？  
答案：DCG 在综合阶段参考 topographical/floorplan 信息，普通 DC 思维更容易只看逻辑和时序抽象。

2. 为什么 output register 要写进设计规格？  
答案：它决定输出接口是否由寄存器驱动，影响接口 timing、后端收敛和形式验证边界。

3. 如果综合后后端发现某区域极度拥塞，前端应回查什么？  
答案：floorplan/blockage 是否进入综合、placement density 报告、macro 周边逻辑、关键路径是否被物理估计低估。

4. “compile 成功”为什么不是验收标准？  
答案：compile 成功只说明命令运行完，不说明 timing、physical、层次、输出文件和下游读取都合格。
