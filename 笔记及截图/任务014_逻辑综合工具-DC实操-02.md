# 任务14：逻辑综合工具 DC 实操 02

## 本章知识全景图

### 1. 一眼看懂这讲在讲什么

- 本章主题：在第 13 章 DC 基本综合流程上加入时序逻辑、时钟约束、I/O delay 和下游交付文件。
- 核心概念：同步复位、寄存器输出、`man`/`help`、`check_library`、`check_timing`、`create_clock`、`set_input_delay`、`set_output_delay`、`remove_from_collection`、`report_timing`、slack、`write_sdc`、`write_sdf`、mapped netlist、DDC。
- 逻辑主线：综合工具只有在知道时钟和外部 I/O 时间预算后，才知道“多快算合格”。同一份 RTL 在不同约束下可能得到不同网表，所以网表必须和 SDC、SDF、报告一起交付。
- 最短学习路径：先把组合加法器改成寄存器输出，再用 DC 帮助系统查命令，再逐步加 clock、input delay、output delay，最后通过 timing report 和导出文件完成闭环。

### 2. 概念地图

| 概念层级 | 核心概念 | 前置知识 | 延伸应用 |
|---|---|---|---|
| RTL 对象 | 带 `clk/rst_n` 的时序逻辑 | `always @(posedge clk)`、寄存器 | 控制器、流水线、接口寄存 |
| 约束语言 | SDC、`create_clock`、I/O delay | 时钟周期、setup/hold、端口 | STA、后端布局布线 |

| 时序报告 | `report_timing`、slack、关键路径 | 组合路径、寄存器路径 | 频率收敛、路径优化 |
| 交付文件 | SDC、SDF、DDC、mapped netlist | 第 13 章综合输出 | 后仿真、STA、后端交付包 |

### 3. 阅读顺序

1. 先理解为什么时序设计必须有约束：没有 clock，工具不知道寄存器路径的时间边界。
2. 再学习 DC 的 `man` 帮助系统：不会命令时先查语义和例子，不靠猜。
3. 然后建立 SDC 三件套：`create_clock`、`set_input_delay`、`set_output_delay`。
4. 最后看 slack 如何随时钟周期变化，并把网表、SDC、SDF、DDC 一起导出。

## 1. 时序逻辑让 DC 必须面对“多快算够快”

组合逻辑只问功能和映射，时序逻辑还要问数据必须在多少时间内从一个寄存器到下一个寄存器。没有时钟约束，DC 不知道该优化到什么速度。

![带输出寄存器的加法器结构](<./screenshots/任务014_逻辑综合工具-DC实操-02/registered_output_500s.jpg>)

视觉核验：视频 05:00-08:30，画面把加法器输出改成寄存器输出，并加入 `clk` 与低有效复位；读者应识别这是从组合逻辑转向时序逻辑的关键边界。

典型 RTL 形态：

```verilog
always @(posedge clk) begin
    if (!rst_n) begin
        sum_out <= 32'b0;
        cout    <= 1'b0;
    end else begin
        {cout, sum_out} <= a + b;
    end
end
```

这段代码让 DC 看到寄存器，但还没有告诉 DC 两件事：

- `clk` 的周期是多少。
- 外部输入什么时候到、输出要给外部留下多少时间。

因此本章的重点不是“多敲几个命令”，而是把芯片外部世界和内部寄存器路径放进同一个时间预算里。

## 2. `man`/帮助系统是 DC 实操的第一调试工具

DC 命令很多，可靠做法不是凭记忆硬敲，而是用 `man <command>` 或命令前缀查语法、选项、description 和 example。

![check_library 命令帮助](<./screenshots/任务014_逻辑综合工具-DC实操-02/check_library_842s.jpg>)

视觉核验：视频 10:00-17:00，画面多次通过 `man` 查看 `set_app_var`、`read_verilog`、`check_library` 等命令；读者应学会先读 description 和 example，再落到脚本。

实操中有三类错误可以靠帮助系统快速定位：

| 错误类型 | 现象 | 处理 |
|---|---|---|
| 命令名记错 | DC 报 unknown command | 用前缀或 `man` 查正确命令 |
| 变量名记错 | 报 not an application variable | 查 `set_app_var` 或变量名 |
| 选项遗漏 | 命令能执行但被 ignored | 查 example，确认 `-clock`、对象集合等参数 |

课堂中故意敲错 `target_library` 相关变量，就是为了说明：DC 报错信息通常已经指出“变量不是合法 application variable”，不要跳过报错继续跑。

## 3. 库检查先于 QoR 分析

`check_library` 的作用是确认库环境可用。库不可信时，面积和时序报告看起来再完整，也不能作为真实 QoR。

```tcl
set search_path    [list ./library ./design ./script]
set target_library [list typical.db]
set link_library   [list * typical.db]

check_library
```

`check_library` 至少帮你排除三类问题：

- `target_library` 指向的 `.db` 文件找不到。
- `link_library` 解析不完整，实例或库单元无法绑定。
- 当前库版本、符号库或路径配置与脚本不一致。

正式流程里，库检查和设计检查要放在 `compile` 前。否则你可能在一个错误环境中得到“看起来很努力”的综合结果。

## 4. `create_clock` 建立寄存器路径的时间坐标

时钟约束是时序综合的基准。`create_clock` 告诉 DC：哪个端口是时钟、周期是多少、波形是什么。

![create_clock 帮助和命令示例](<./screenshots/任务014_逻辑综合工具-DC实操-02/create_clock_help_1640s.jpg>)

视觉核验：视频 24:00-29:00，画面查看 `create_clock` 帮助并解释周期、上升沿、下降沿和默认占空比；读者应确认 `-period` 是 timing 分析的核心输入。

基本写法：

```tcl
create_clock -name clk -period 10 [get_ports clk]
```

这条约束建立的是 10 ns 周期的 `clk`。如果不额外指定 waveform，工具通常按默认占空比建立波形；如果要写完整波形，可以用类似：

```tcl
create_clock -name clk -period 10 -waveform {0 5} [get_ports clk]
```

时钟约束让工具可以检查寄存器到寄存器路径：

```text
launch flop Q
  -> combinational logic
  -> capture flop D

数据路径延时 + setup + 不确定性 <= 时钟周期
```

`create_clock` 选错对象时，timing report 可能很“干净”，但那只是因为真正的寄存器路径没有被约束到。

## 5. `set_input_delay` 描述外部已经消耗的时间

输入 delay 不是芯片内部输入端口的延时，而是外部世界把数据送到本芯片输入脚之前已经花掉的时间。

![set_input_delay 约束输入端口](<./screenshots/任务014_逻辑综合工具-DC实操-02/input_delay_2145s.jpg>)

视觉核验：视频 30:00-41:00，画面使用 `set_input_delay`，并通过 `[all_inputs]`、`remove_from_collection` 把 `clk` 从普通输入集合中移除；读者应特别确认时钟端口不能当成普通 data input 约束。

典型路径：

```text
外部寄存器 Q
  -> 外部组合逻辑/PCB/封装
  -> 本芯片 input port
  -> 本芯片内部组合逻辑
  -> 本芯片寄存器 D
```

约束写法：

```tcl
set data_inputs [remove_from_collection [all_inputs] [get_ports clk]]

set_input_delay 5 -max -clock clk $data_inputs
set_input_delay 1 -min -clock clk $data_inputs
```

为什么要移除 `clk`？因为 `[all_inputs]` 会包含所有输入端口，其中也包含时钟和复位。时钟是时间基准，不是普通数据；把时钟端口加 input delay，会污染约束语义。

AMD Vivado 约束文档也把 input delay 放在相对时钟的 I/O 时序建模语境中使用；工具不同，基本 SDC 思想一致：用外部时间预算约束内部可用时间。

## 6. `set_output_delay` 给外部接收端留下时间

输出 delay 描述的是数据离开本芯片后，外部接收端仍需要的时间。它会压缩本芯片内部从寄存器到输出端口可使用的时间。

![set_output_delay 约束输出端口](<./screenshots/任务014_逻辑综合工具-DC实操-02/output_delay_2515s.jpg>)

视觉核验：视频 41:00-45:00，画面加入输出 delay 并再次检查约束；读者应把输出 delay 理解为“留给外部接收端的时间”，不是“输出端口自己变慢”。

路径模型：

```text
本芯片寄存器 Q
  -> 本芯片内部组合逻辑
  -> output port
  -> PCB/封装/外部接收逻辑
  -> 外部寄存器 D
```

典型写法：

```tcl
set_output_delay 5 -max -clock clk [all_outputs]
set_output_delay 1 -min -clock clk [all_outputs]
```

输入 delay 消耗的是“到达本芯片之前已经花掉的时间”，输出 delay 保留的是“离开本芯片之后还必须留出的时间”。两者本质上都在切分一个系统级时钟周期。

## 7. `check_timing` 和报告让约束是否覆盖变得可见

约束写完后不能直接 `compile` 完事，必须检查时钟、输入输出 delay 和未约束路径。

课堂中先运行 `check_timing`，工具会提示哪些路径没有约束；加入 input delay 后，再检查时，普通输入端口相关报错会减少。这一步的价值是证明约束对象确实选中了。

建议的检查顺序：

```tcl
check_timing
report_clock
report_constraints -all_violators
report_timing
```

| 检查项 | 看什么 | 失败信号 |
|---|---|---|
| `report_clock` | 是否存在 `clk`，周期是否正确 | 没有 clock、周期不是预期 |
| `check_timing` | 是否有 unconstrained path | input/output 没约束、generated clock 漏约束 |
| `report_constraints` | 违例路径与约束覆盖 | 大量 violator 或对象为空 |
| `report_timing` | 起点、终点、数据路径、slack | slack 为负、路径对象不合理 |

约束错误时最危险的情况不是报红，而是不报错。没有被约束到的路径不会违例，但那不等于它能工作。

## 8. 时钟越紧，slack 越小，直到违例

本章通过修改时钟周期演示了 slack 的含义：10 ns 时余量较大，收紧到 5 ns 余量变小，再收紧到 2 ns 出现 timing violation。

![mapped netlist 截图](<./screenshots/任务014_逻辑综合工具-DC实操-02/mapped_netlist_3445s.jpg>)

视觉核验：视频 45:00-58:00，画面先报告 10 ns 下满足时序，再把周期收紧并观察 slack 下降直至 violated；读者应关注 slack 数值随周期变化，而不是只看 pass/fail。

slack 可理解为：

```text
slack = required time - arrival time
```

- 正 slack：路径在要求时间前到达，有余量。
- 零附近：刚好压线，工程上通常还要考虑不确定性和裕量。
- 负 slack：路径晚到，当前约束下违例。

负 slack 不等于“DC 坏了”。它是在告诉你：目标频率、库、路径结构或约束假设之间存在冲突。下一步要看关键路径，判断是加法器太长、MUX 太深、位宽太大，还是约束写得不合理。

## 9. SDC、SDF、DDC、网表必须同批次导出

综合交付不是只交一个 `.v` 文件。网表说明结构，SDC 说明这个结构是在什么约束下生成的，SDF 说明延时，DDC 方便 Synopsys 工具链继续读取。

![导出 SDC 文件](<./screenshots/任务014_逻辑综合工具-DC实操-02/write_sdc_2840s.jpg>)

视觉核验：视频 46:00-50:00，画面用 `write_sdc` 导出约束；读者应确认 SDC 是当前会话中时钟和 I/O delay 的固化版本。

![导出 SDF 与 DDC 文件](<./screenshots/任务014_逻辑综合工具-DC实操-02/write_sdf_ddc_2955s.jpg>)

视觉核验：视频 50:00-61:00，画面继续查 `write`/`write_sdf` 命令并导出下游文件；读者应确认网表、SDF、SDC、DDC 来自同一次综合。

常见导出：

```tcl
write_sdc ./out/adder32.sdc
write_sdf ./out/adder32.sdf
write -format ddc     -hierarchy -output ./out/adder32.ddc
write -format verilog -hierarchy -output ./out/adder32.mapped.v
```

![导出文件汇总与帮助信息](<./screenshots/任务014_逻辑综合工具-DC实操-02/write_artifacts_summary_3605s.jpg>)

视觉核验：视频 59:00-61:30，画面总结导出的 Verilog 网表、SDF、SDC 等文件；读者应确认这些文件分别服务后仿真、STA、后端和工具继续读取。

| 文件 | 交给谁 | 说明 |
|---|---|---|
| mapped Verilog | 门级后仿真、后端 | 标准单元实例和连接关系 |
| SDC | STA、后端 | 时钟、I/O delay 等约束 |
| SDF | 门级带延时仿真 | 单元和路径延时标注 |
| DDC | DC/PrimeTime 等 Synopsys 工具 | 内部设计数据库 |
| report | review、调试、签核前检查 | 面积、时序、约束覆盖和 warning 证据 |

## 10. 本章完整脚本骨架

```tcl
set search_path    [list ./library ./design ./script]
set target_library [list typical.db]
set link_library   [list * typical.db]

read_verilog ./design/verilog/adder32_reg.v
current_design adder32_reg
link

check_design
check_library

create_clock -name clk -period 10 [get_ports clk]

set data_inputs [remove_from_collection [all_inputs] [get_ports clk]]
set_input_delay  5 -max -clock clk $data_inputs
set_input_delay  1 -min -clock clk $data_inputs
set_output_delay 5 -max -clock clk [all_outputs]
set_output_delay 1 -min -clock clk [all_outputs]

check_timing
report_clock

compile

report_area   > ./report/adder32_reg.area.rpt
report_timing > ./report/adder32_reg.timing.rpt

write_sdc ./out/adder32_reg.sdc
write_sdf ./out/adder32_reg.sdf
write -format ddc     -hierarchy -output ./out/adder32_reg.ddc
write -format verilog -hierarchy -output ./out/adder32_reg.mapped.v
```

这份脚本的关键点是先检查库和设计，再建时钟和 I/O 约束，再检查 timing 覆盖，最后才 compile 和导出。顺序错了，文件仍可能生成，但工程含义会变弱。

## 11. 从本讲连接到 AI+IC 工程

AI 加速器里的矩阵乘单元、累加树、地址生成器和 DMA 接口，都要在目标频率下通过综合与 STA。`create_clock` 决定 NPU 目标频率，I/O delay 决定模块与外部 SRAM、总线或上级子系统的时间预算，`report_timing` 决定瓶颈是在算术路径、控制路径还是接口路径。

对 AI+IC 学习最有价值的练习是：把一个 32-bit 加法器逐步换成 MAC、比较树或地址累加器，观察同一周期约束下 slack 和面积如何变化。这样才能理解“RTL 写法”和“芯片能跑多快”之间的真实关系。

## 12. 深层理解：SDC 是“时间预算合同”，不是命令清单

时序约束最容易被学成几个命令：`create_clock`、`set_input_delay`、`set_output_delay`。但真正理解它们，要把设计看成一段接力赛。前一级电路把数据交到本模块输入端，本模块内部组合逻辑继续传递，最后在输出端交给下一级。时钟周期就是整场接力的总时间，input delay 表示前一棒已经花掉的时间，output delay 表示后一棒还需要预留的时间，留给本模块的只是中间那段。

所以：

- `create_clock` 不是“告诉工具有个 clk”，而是给所有寄存器路径建立时间坐标。
- `set_input_delay` 不是“输入端口自己有延时”，而是声明数据到达模块输入前，外部世界已经消耗了多少预算。
- `set_output_delay` 不是“输出端口自己慢”，而是给外部接收端保留建立时间、布线和下游组合逻辑预算。
- `check_timing` 不是形式步骤，而是检查预算合同有没有漏签：没有约束的路径可能比负 slack 更危险，因为工具根本没被要求优化它。

如果把约束当命令清单，脚本能跑但设计可能没有被正确要求；如果把约束当时间合同，就会自然追问“谁发射、谁接收、这段路有多少时间、哪段路没人管”。

## 13. 配图复盘：从命令截图读出时间模型

| 配图 | 读图重点 | 深层理解 |
|---|---|---|
| 带输出寄存器的加法器结构 | 寄存器边界在哪里 | 时序分析看的是寄存器到寄存器或端口到寄存器路径 |
| `check_library` 帮助 | 如何先验证库 | 没有可用库，后面的 timing/area 没有可信基础 |
| `create_clock` 帮助 | 周期、波形和 clock object | 工具从这里得到 required time 的基准 |
| `set_input_delay` | 输入端口如何扣预算 | 外部已花时间越多，内部可用时间越少 |
| `set_output_delay` | 输出端口如何预留预算 | 不给下游留时间，模块局部看似通过也可能系统失败 |
| mapped netlist | RTL 已被映射为标准单元 | 约束会影响工具选择更快或更小的门 |
| 导出 SDC | 约束可交给下游 | 后端和 STA 必须拿到同一套时间假设 |
| 导出 SDF/DDC | 延时和工具态保存 | 后仿真和 Synopsys 链路继续使用 |
| 导出汇总 | 产物成套出现 | 同批次产物才能避免版本错配 |

图像不是为了证明“我点过这个按钮”，而是帮助你把每条命令放到时间预算模型中。

## 14. 操作闭环：时序问题不能靠重复 compile 解决

当 slack 变小或为负时，先做三层判断：

| 层次 | 要问的问题 | 典型处理 |
|---|---|---|
| 约束层 | 周期、input/output delay 是否合理？有没有误把 clk 当普通输入？ | 修正 SDC，先让问题定义正确 |
| 路径层 | 关键路径经过哪些寄存器、组合单元和层次？ | 读 `report_timing`，定位真正瓶颈 |
| RTL/架构层 | 路径太长是加法器、比较器、MUX、译码，还是接口预算过紧？ | 分流水、改结构、调整位宽或重新分配预算 |

重复 `compile` 像考试没看错题就一直重交答卷。工具可能换一种映射方式，但如果约束不合理或路径结构本身太长，结果不会凭空变好。

## 复习与自测

1. 为什么 `create_clock` 是寄存器到寄存器时序分析的基准？
   - 答案要点：它定义时钟对象、周期和波形，工具用它计算 required time。没有时钟，寄存器路径没有时间坐标。

2. `set_input_delay` 表示芯片内部输入端口延时吗？
   - 答案要点：不是。它表示外部发射路径到本芯片输入端口前已经消耗的时间，从而压缩内部输入端口到寄存器的可用时间。

3. 为什么要从 `[all_inputs]` 中移除 `clk`？
   - 答案要点：`clk` 是时钟基准，不是普通数据输入。把它当 data input 加 delay 会污染约束，导致检查和优化语义错误。

4. 同一份 RTL 在不同 SDC 下为什么可能得到不同网表？
   - 答案要点：约束会改变优化目标。更紧的周期可能让 DC 选择更快更大的单元、改变逻辑结构或复制逻辑；宽松约束可能更偏面积。

5. slack 从正变负说明什么？
   - 答案要点：required time 小于 arrival time，路径在当前约束下晚到。应看关键路径和约束假设，不能只机械重复 compile。

6. SDC、SDF、DDC、mapped Verilog 分别服务什么下游？
   - 答案要点：SDC 给 STA/后端约束，SDF 给门级带延时仿真，DDC 给 Synopsys 工具继续读，mapped Verilog 给后仿真和后端结构输入。

1. 给一个寄存器到寄存器路径，能否画出 launch clock、data path、capture clock、required time、arrival time 和 slack？
2. 给一个模块输入端口，能否解释 input delay 扣掉的是外部发射路径时间，而不是端口本身的神秘延时？
3. 看到 unconstrained path，能否说明它为什么比显式负 slack 更容易被忽视？
