# 任务115：综合技术1

## 本章知识全景图
这一讲开始讲 DC 的综合优化技术。它不是“多背几个 compile 选项”，而是理解工具为了改善 timing、area、power 会怎样改写结构：展开层次、跨边界优化、替换算术结构、复制寄存器、移动寄存器、划分 path group。每种技术都有收益，也会改变后续验证、后端和调试边界。

| 技术 | 改变了什么结构 | 主要收益 | 主要代价/边界 |
|---|---|---|---|
| default `compile_ultra` | 调用更强综合算法 | QoR 提升 | runtime 增加，依赖 license |
| DesignWare | 高级运算映射成库组件 | 算术/存储结构更优 | 需要验证映射和授权 |
| arithmetic optimization | 常数表达式重写 | 面积和延时下降 | RTL 写法要让工具看懂 |
| boundary optimization | 跨模块边界优化 | 删除冗余逻辑、改善 timing | 可能破坏层次边界 |
| auto ungroup | 展平层次 | 更多全局优化机会 | 后端/验证/复用边界变弱 |
| register replication | 复制高扇出寄存器 | 降低 fanout、改善 critical path | 面积功耗增加 |
| adaptive retiming | 移动/合并/拆分寄存器 | 重新分配 slack | 寄存器位置和名字可能变化 |
| path group | 改变优化关注点 | 避免只优化最差一组路径 | 分组和权重要合理 |

![综合优化需求](<./screenshots/任务115_综合技术1/video_dense_01_04m12s.jpg>)

最短学习路径：先理解 `compile_ultra` 默认会做哪些优化；再看算术、层次、寄存器三类结构变化；最后用 path group 解决“工具优化方向不符合工程重点”的问题。

## 视觉核对清单

综合优化的图不能当作“工具魔法列表”看。更准确的比喻是修高速公路：DesignWare 是换成熟桥梁，boundary optimization 是拆掉不必要收费站，register replication 是增加分流车道，retiming 是移动中途休息站，path group 是告诉施工队先修主干道。

| 截图 | 看图要点 | 漏看后果 |
|---|---|---|
| default `compile_ultra` | 强优化依赖好 RTL、好约束、正确库 | 把 compile 选项当万能药 |
| DesignWare / arithmetic | 算术结构可被成熟实现替换 | 只看 RTL 运算符，不理解综合后结构变化 |
| boundary / ungroup | 层次优化会改变调试、DFT、形式验证边界 | QoR 变好但交付边界失控 |
| register replication / retiming | 以面积或寄存器位置换 slack | 名字/位置变化后形式验证和调试困难 |
| path groups | 指挥工具优化不同路径类别 | 工具只盯默认最差路径，工程重点被忽略 |

## 1. 综合优化目标：不是 timing 越激进越好，而是 PPA 可交付
视频开头列出需求：meet aggressive timing goals、good post-layout correlation、good quality RTL code、complete and accurate constraints、compile top-down。真正的含义是：综合优化依赖 RTL 质量和约束质量；如果约束不完整，强行上更高 effort 只会优化错误目标。

![default compile_ultra optimizations](<./screenshots/任务115_综合技术1/video_dense_02_08m24s.jpg>)

`compile_ultra` 默认会调用更强技术，包括：

- DesignWare 选择。
- 宽扇入门的宏映射。
- 逻辑级和门级 critical path 优化。
- 层次级优化和边界优化。
- 更高 effort 的 timing 优化算法。

它的前提是约束准确。约束错，工具越努力，结果越偏。

## 2. critical path re-synthesis：工具会把慢路径拿出来重综合
critical path re-synthesis 的思路是：先找违反或接近违反的关键路径，再把这部分组合逻辑返回逻辑级重新优化，而不是只做局部 gate sizing。

![critical path re-synthesis](<./screenshots/任务115_综合技术1/video_dense_03_12m37s.jpg>)

这种技术适合组合逻辑结构确实可以重写的路径。它不能解决所有问题：如果路径慢是因为接口预算错误、路径跨层次被限制、或 RTL 本身缺 pipeline，重综合只能缓解，不能根治。

## 3. DesignWare：让高级运算调用成熟实现
DesignWare 是 Synopsys 提供的 IP 和 datapath 组件集合，常用于算术、比较、乘法、除法、FIFO、RAM、shift register 等结构。

![DesignWare library](<./screenshots/任务115_综合技术1/video_dense_04_16m49s.jpg>)

它的价值：

- 避免手写低质量复杂运算结构。
- 对算术 datapath 有更好的 QoR。
- 与综合器优化流程配合更深。

风险也很明确：

- 需要 DesignWare license。
- 网表中可能出现 `DW_` 前缀组件。
- 形式验证和后端流程要能处理这些映射。

## 4. arithmetic optimization：常数乘法、公共子表达式和比较器优化
算术优化不是“工具聪明”这么简单，而是利用代数等价把贵结构变便宜。

![arithmetic expression optimization](<./screenshots/任务115_综合技术1/video_dense_05_21m02s.jpg>)

典型例子：常数乘法。

$$
105 = 64 + 32 + 8 + 1 = 2^6 + 2^5 + 2^3 + 1
$$

所以：

$$
x \times 105 = (x << 6) + (x << 5) + (x << 3) + x
$$

这能把通用乘法器改成移位加法结构。视频还提到 constant/operand folding、common sub-expression sharing、SOP/POS transformation、comparison sharing 等优化，本质都是减少冗余逻辑、降低级数或复用中间结果。

RTL 写法会影响优化效果。写得过度黑盒、层次过死、或表达式被拆得让工具看不出公共结构，算术优化就难发挥。

## 5. boundary optimization：跨模块边界删掉冗余
boundary optimization 允许工具穿过模块边界优化。例如两个子模块边界两侧有可合并的逻辑，工具可以在保持功能等价的前提下删除、吸收或重排。

![boundary optimization](<./screenshots/任务115_综合技术1/video_dense_06_25m14s.jpg>)

禁用方式：

```tcl
compile_ultra -no_boundary_optimization
set_boundary_optimization [get_designs sub2] false
```

何时禁用：

- 层次边界要交给后端 floorplan。
- 低功耗/多电压边界不能被破坏。
- 子模块后续复用或单独验证。
- 调试脚本依赖层次和实例名。

## 6. auto-ungroup：展平层次换更大优化空间
auto-ungroup 比 boundary optimization 更激进：它可能把子模块层次打散，让逻辑进入上层统一优化。

![auto-ungroup example](<./screenshots/任务115_综合技术1/video_dense_07_29m26s.jpg>)

收益是工具能看到更多跨模块冗余；风险是层次边界消失，后端、验证、调试、复用会变复杂。

控制方式：

```tcl
compile_ultra -no_autoungroup
set_ungroup [get_designs keep_this_block] false
set_ungroup [get_designs small_block] true
```

判断口诀：小而纯逻辑的局部层次可以考虑打散；承载架构边界、时钟/电源边界、验证边界的层次不要随便打散。

## 7. register replication：用面积换 fanout 和 timing
高 fanout 会让驱动寄存器输出负载变大，transition 变差，critical path 变慢。register replication 的做法是复制寄存器，让每个副本驱动较少负载。

![register replication](<./screenshots/任务115_综合技术1/video_dense_08_33m39s.jpg>)

```text
原始：1 个寄存器 -> 200 个下游负载
复制：3 个寄存器副本 -> 每个驱动约 60-70 个负载
```

收益是 timing 改善，代价是寄存器数量增加、面积功耗增加、等价验证和调试命名更复杂。它适合修复高 fanout 控制或 enable 信号，不适合无脑复制所有寄存器。

## 8. adaptive retiming：移动寄存器而不是只换门
retiming 允许工具在保持端到端功能等价的前提下移动、合并或拆分寄存器，把组合逻辑延时重新分摊到不同 pipeline stage。

![adaptive retiming fundamentals](<./screenshots/任务115_综合技术1/video_dense_09_37m51s.jpg>)

风险：

- 寄存器位置变化。
- 寄存器名字变化。
- 形式验证、DFT、调试脚本需要配合。
- 固定位置的寄存器不应被 retime。

控制命令常见形态：

```tcl
set_dont_retime [get_cells fixed_reg*] true
set_optimize_registers true [get_designs pipeline_block]
```

## 9. path group：让工具按工程重点优化
默认情况下，每条 timing path 属于对应 capture clock 的 path group。工具通常先优化每个 group 中最差的 critical path。如果所有路径混在一起，某些工程上重要但不是最差的路径可能被忽略。

![path groups](<./screenshots/任务115_综合技术1/video_dense_10_42m04s.jpg>)

典型分组：

```tcl
group_path -name INPUTS  -from [all_inputs]
group_path -name OUTPUTS -to [all_outputs]
group_path -name COMBO   -from [all_inputs] -to [all_outputs]
group_path -name REG2REG -from [all_registers] -to [all_registers]
```

如果 reg-to-reg path 被忽略，可能是 input/output 约束分区太差，工具把注意力花在其他路径上。

![reg-to-reg paths ignored](<./screenshots/任务115_综合技术1/video_dense_11_46m16s.jpg>)

near-critical path optimization 则解决另一个问题：只修最差路径可能导致次差路径随后变成新瓶颈。对接近 critical 的路径也给优化关注，可以提升整体 timing 稳定性。

![near critical path optimization](<./screenshots/任务115_综合技术1/video_dense_12_50m28s.jpg>)

## 优化技术对交付边界的影响

综合优化不是只改变 timing 数字，它会改变后续验证和调试能看到的结构。每打开一个强优化，都要知道它把什么边界变松了。

| 技术 | 对 RTL 结构的改变 | 对 Formality / DFT / debug 的影响 |
|---|---|---|
| DesignWare | 运算符替换成库里的成熟算术结构 | 需要库和 SVF 支撑匹配；debug 不能再按原 RTL 运算符找门 |
| boundary optimization | 跨模块边界删除或重排逻辑 | 层次边界变模糊，ECO 和模块级 debug 更难 |
| auto-ungroup | 直接展平部分层次 | DFT、后端 floorplan、形式匹配都要适应新层次 |
| register replication | 复制高 fanout 寄存器 | 名字和扇出结构变化，Formality 依赖 guidance 匹配 |
| retiming | 移动寄存器位置 | compare point 改变，必须有 SVF/retiming guidance，否则 match 难度上升 |

path group 的权重可以理解成给施工队分配人力：默认情况下工具可能只盯全局最差路径；加权后，某类路径会获得更多优化资源。权重不是越高越好，过度偏向某组会让其他组 QoR 倒退。

## 工程练习

1. 判断某个优化是否值得打开。

   合格答案：先看 report 是 timing、area、power 还是 fanout 问题；再判断优化会不会破坏需要保留的 hierarchy、DFT 边界、ECO 可读性或形式验证匹配；最后用 before/after 的 WNS/TNS、area、power 和 report_qor 比较。优化像手术，不是补品。

2. 给 path group 建 PASS/FAIL。

   合格答案：`report_timing` 能按 INPUTS、OUTPUTS、COMBO、REG2REG 等 group 输出；每个 group 的 worst path 可解释；权重调整后工具确实把 effort 放到目标 group；没有把无关路径优化得很好却让关键 reg-to-reg 继续恶化。

## 复习与自测
1. `compile_ultra` 为什么不能替代好约束？  
   答：它只是在给定约束目标下更努力优化；目标错或缺失时，优化结果不可信。

2. boundary optimization 和 auto-ungroup 的区别是什么？  
   答：boundary optimization 跨边界优化局部冗余；auto-ungroup 可能直接打散层次，影响更大。

3. register replication 改善 timing 的机制是什么？  
   答：复制寄存器降低单个寄存器 fanout 和输出负载，改善 transition 和 path delay。

4. path group 的作用是什么？  
   答：把不同起点/终点路径分类，让工具按工程重点优化，而不是只盯默认 group 中的最差路径。

## AI+IC 连接
NPU datapath 中大量乘加、比较、移位、广播控制、pipeline stage 都会触发本讲技术。优化时必须问清楚：这是算术结构重写、层次边界改变、寄存器复制，还是 retiming？每一种都会影响 PPA，也会影响后续形式验证、DFT、后端 floorplan 和调试可观测性。
