## 本章知识全景图

### 1. 一眼看懂这讲在讲什么

- 本章主题：把实训 SoC 项目从“模块清单”拆成前端 RTL 工程任务：系统结构、工艺电压、IP 取舍、性能功耗、memory、寄存器、中断和外设接口。

## 1. 实训项目是一颗小型 SoC

本章的第一句话就把任务边界定住：项目不是单个模块，而是一颗包含 32-bit CPU、memory、DMA 和多种外设接口的小型 SoC。

![项目需求入口](<./screenshots/任务030_实训项目介绍1/soc_overview_80s.jpg>)

视觉核验：视频 00:00-02:00，画面展示 SoC 项目入口；读者应先找 CPU，再看 memory、DMA、外设如何通过 AMBA 总线被访问。

这张图的读法不是背外设名字，而是找“谁控制谁、数据从哪里到哪里、事件怎么通知”。CPU 是调度者，总线是道路，memory 是仓库，DMA 是搬运工，外设是对外窗口，中断是门铃。只看见 SD、USB、SPI、GPIO 这些名词，还没有听懂项目；能把它们连成一次可追踪事务，才进入前端工程视角。

CPU 通过总线做两类动作：

- 配置外设寄存器：例如设置 SPI 模式、Timer 周期、DMA 源地址和长度。
- 读取数据或状态：例如读取外设状态、错误码、接收 FIFO、完成标志。

所以你后面写的每个 IP 都不是孤立逻辑。它至少要回答：

```text
谁访问我？
通过什么总线访问？
地址和寄存器怎么定义？
我什么时候返回 ready/data/error？
我什么时候发中断？
```

这就是从“写模块”进入“做 SoC 前端”的分界线。

## 2. core/IO 电压和工艺决定实现边界

core 电压服务片内标准单元和内部逻辑，IO 电压服务 pad 与外部板级接口。工艺节点、库和电压会反向限制最高频率、面积、功耗和 IO 连接方式。

![core/IO 电压与工艺](<./screenshots/任务030_实训项目介绍1/voltage_core_io_200s.jpg>)

视觉核验：视频 02:00-05:00，画面讲 core 电压、IO 电压和工艺；读者应把它们看成标准单元库、IO cell、时序目标和电平兼容约束。

前端需要关心这些参数，因为：

| 参数 | 对前端的影响 |
|---|---|
| core voltage | 决定标准单元库、速度、功耗和时序模型 |
| IO voltage | 决定 pad、外部接口电平和电平转换需求 |
| process node | 决定面积、功耗、频率、漏电和 NRE 成本 |
| library | 决定综合可选单元、clock gating cell、SRAM macro |

如果外部接口和片内逻辑电压不同，顶层可能需要 level shifter 或专门 IO cell。RTL 不是在真空里运行，它最终必须落到某个工艺、某组库和某套 IO 约束里。

## 3. 工艺选择是成本、性能、功耗和风险的取舍

先进工艺通常提供更高性能和更好能效，但 mask/NRE 成本更高、风险也更大。成熟工艺频率可能低一些，却更便宜、更稳、更适合控制类或低成本芯片。

![工艺成本取舍](<./screenshots/任务030_实训项目介绍1/process_cost_tradeoff_440s.jpg>)

视觉核验：视频 06:00-09:00，画面讨论工艺节点和成本；读者应把工艺选择理解为产品约束，不是节点数字比赛。

![工艺对性能功耗的影响](<./screenshots/任务030_实训项目介绍1/process_performance_power_730s.jpg>)

视觉核验：视频 10:00-13:00，画面把性能、功耗和工艺联系起来；读者应意识到工艺约束会反推流水线、并行度和时钟门控策略。

这两张图不是重复讲“工艺越先进越好”。成本图看商业和制造约束：钱、良率、风险、上市时间；性能功耗图看架构反推：频率上不去时要不要加并行，功耗压不住时要不要加 clock gating，面积过大时要不要复用硬件。工艺节点是边界条件，不是炫技指标。

工程判断链：

```text
目标市场/出货量
  -> 成本预算
  -> 工艺选择
  -> 标准单元库与频率上限
  -> RTL 架构：并行度、流水线、存储访问、低功耗策略
```

例如目标吞吐很高但频率上限有限，就需要增加并行度或流水线；目标功耗很低，就需要减少无效翻转、做 clock gating 或低功耗模式。

## 4. 前端目标来自系统指标，不来自写法偏好

前端工程师写 RTL 前，要先把系统指标拆成可验证目标。

![前端性能目标](<./screenshots/任务030_实训项目介绍1/frontend_performance_target_1100s.jpg>)

视觉核验：视频 16:00-20:00，画面讲前端性能目标；读者应把每个指标落到 RTL、验证、约束或报告。

| 系统指标 | RTL/验证落点 |
|---|---|
| 功能 | 模块接口、状态机、寄存器、数据路径 |
| 性能 | 频率、吞吐、延迟、FIFO 深度、DMA burst |
| 面积 | 位宽、寄存器数量、SRAM/寄存器取舍、IP 形态 |
| 功耗 | clock gating、低功耗模式、空闲逻辑关闭 |
| 接口 | AHB/APB、寄存器协议、ready/error、中断 |
| 交付 | RTL、TB、filelist、SDC、lint/CDC/综合报告 |

这就是为什么项目介绍值得认真做笔记。它给出的不是背景材料，而是后续 RTL 任务的验收来源。

## 5. IP 取舍决定可控性和集成责任

SoC 中的 IP 可以自研，也可以买现成的。自研更可控，外购更快；但外购 IP 可能面积偏大、修改受限、授权成本高，并且需要额外集成模型和约束。

![IP 取舍](<./screenshots/任务030_实训项目介绍1/ip_buy_vs_self_design_1350s.jpg>)

视觉核验：视频 21:00-25:00，画面讨论 IP 自研和购买；读者应判断每种选择带来的修改权限、验证责任和集成风险。

IP 交付形态：

![系统功能清单](<./screenshots/任务030_实训项目介绍1/ip_delivery_forms_1660s.jpg>)

视觉核验：视频 26:00-30:00，画面介绍 IP 交付形式和系统功能；读者应区分 RTL、加密 RTL、netlist、GDS/hard IP。

IP 取舍图回答“责任归谁”，交付形态图回答“你手里到底拿到什么”。Soft IP 像拿到源代码，能改也要负责验证；netlist 像拿到封好的机器，能接线但很难改内部；hard IP 像一块固定尺寸的实体模块，前端主要负责 wrapper、时钟、复位、总线和约束适配。

| 形态 | 能看到什么 | 能否修改 | 前端责任 |
|---|---|---|---|
| Soft IP / RTL | 源码 | 通常可改 | 读代码、集成、验证、综合 |
| 加密 RTL | 工具可读，人难读 | 基本不可改 | 集成、仿真模型、约束 |
| Netlist | 门级结构 | 很难改 | 黑盒/网表集成、时序约束 |
| Hard IP / GDS | 物理版图或 macro | 不能改内部 | wrapper、pad、时钟、电源、时序模型 |

形态越靠近物理实现，内部越不可控；形态越靠近 RTL，前端责任越大。

## 6. 系统功能要转成协作关系

CPU、memory、DMA、Timer/Watchdog、外设接口不是平铺清单，它们通过寄存器、总线、状态和中断协作。

![系统功能与中断](<./screenshots/任务030_实训项目介绍1/interrupt_register_status_2240s.jpg>)

视觉核验：视频 36:00-39:00，画面讲状态寄存器和中断；读者应确认中断只是通知，真实原因要由 CPU 读寄存器判断。

典型角色：

| 模块 | 系统职责 |
|---|---|
| CPU | 配置外设、读状态、处理中断 |
| Memory | 保存指令、数据、boot code |
| DMA | 代替 CPU 搬运大块数据 |
| Timer | 周期计数或定时触发 |
| Watchdog | 软件异常时触发复位 |
| 中断控制 | 汇总事件并通知 CPU |
| 外设接口 | 与片外设备通信 |

中断流程：

```text
外设完成或出错
  -> 置位 status/error
  -> 拉起 interrupt
  -> CPU 进入中断服务
  -> CPU 读 status/error
  -> CPU 清中断或处理错误
```

如果只设计 `irq`，没有 status、mask、clear 和错误保持策略，这个中断接口就不完整。

## 7. memory 单周期读写要区分吞吐和返回时刻

“单周期 memory”不是一句万能描述。前端必须知道地址、读写使能、写数据、读数据分别在哪个时钟边界有效。

![单周期 memory](<./screenshots/任务030_实训项目介绍1/single_cycle_memory_1920s.jpg>)

视觉核验：视频 31:00-35:00，画面讲 memory 单周期访问；读者应分清写入采样、读出有效、读写冲突和总线等待。

必须定义：

- address 何时有效。
- read/write enable 何时有效。
- write data 何时被采样。
- read data 何时返回。
- 同地址同周期读写如何处理。
- memory 后面会推寄存器、SRAM macro 还是外部 flash。

这会影响总线从设备的 `ready`、读数据返回时刻、仿真模型和综合/后端 memory macro。

## 8. 外部接口是片内总线和片外协议的边界

SPI、UART、GPIO、JTAG、SDHost、NorFlash 都是片内 SoC 与片外世界的连接点。片外世界可能不同频、不同宽、不同协议、不同电压。

![外部接口](<./screenshots/任务030_实训项目介绍1/sdhost_norflash_intro_2540s.jpg>)

视觉核验：视频 40:00-43:30，画面讨论 SDHost、NorFlash 等外设；读者应关注数据方向、时钟关系、寄存器控制和错误反馈。

| 接口 | 核心作用 | 设计关注点 |
|---|---|---|
| SPI | 串行同步通信 | CPOL/CPHA、片选、TX/RX FIFO、时钟分频 |
| UART | 串口通信 | 波特率、起止位、校验、FIFO |
| GPIO | 通用输入输出 | 方向控制、输入同步、中断、pinmux |
| JTAG | 调试和测试 | debug、scan、test mode |
| SDHost | 存储卡控制 | 命令、响应、数据块、CRC、DMA |
| NorFlash | 非易失存储 | 异步访问、boot、等待周期、地址数据总线 |

NorFlash 这种异步外设尤其能训练系统思维：片内同步总线必须通过控制器把片外异步时序包装成 CPU 能读写的寄存器/存储访问。

## 9. 从需求句子拆成前端任务单

需求句子不能停留在口号。例如“CPU 配置 SPI，通过 DMA 把 memory 数据发出去”，拆开至少得到：

| 需求片段 | RTL 任务 | 验证任务 | 交付物 |
|---|---|---|---|
| CPU 配置 SPI | APB/AHB slave 寄存器、地址译码、复位值 | 寄存器读写、非法地址、复位值 | register spec、RTL、寄存器测试 |
| DMA 读 memory | DMA master、地址生成、长度计数、bus request | 边界长度、未对齐、bus error | DMA RTL、TB、波形 |
| 写 SPI FIFO | FIFO full/empty/level、backpressure | overflow/underflow、阈值中断 | FIFO RTL、覆盖点 |
| SPI 发数据 | shift register、SCLK、CS、CPOL/CPHA | 协议边界、loopback | SPI RTL、接口时序 |
| 发完通知 CPU | status/done/error、irq、clear 策略 | 清中断竞争、mask、同时事件 | 中断表、验证报告 |

这张表还要继续落到“谁拥有、用什么证明、什么时候算完成”。

| 交付问题 | 合格答案 | 失败信号 |
|---|---|---|
| 谁拥有寄存器定义？ | RTL、软件、验证共用一份 register spec | RTL 地址和软件 header 不一致 |
| 谁拥有总线协议？ | IP slave/master 接口有 ready/error/非法地址行为 | 仿真只测正常读写，不测等待和错误 |
| 谁拥有数据通路？ | DMA/FIFO/SPI 的数据方向、宽度、边界清楚 | 只知道“能发数据”，不知道 full/empty/done 如何反馈 |
| 谁拥有中断语义？ | status、mask、clear、优先级、异常保持都写清 | irq 拉高但 CPU 无法判断原因或清不掉 |
| 谁拥有实现约束？ | 工艺、库、SRAM/Flash/IP 形态进入约束和 handoff | RTL 可仿真，但综合、STA 或 macro 集成卡住 |

项目介绍真正训练的是“从系统句子反推出硬件契约”。你能拆出这张表，才算听懂了项目介绍。

端到端事务可以这样走一遍：CPU 写寄存器配置 SPI 和 DMA，DMA 从 memory 取数，FIFO 用 full/empty 给出背压，SPI shift 把数据推出片外，发送完成后置位 `done/status/error`，中断通知 CPU，CPU 读状态并清中断。任何一环没定义 `ready/error/clear`，系统就不是“差一个小细节”，而是软件无法可靠控制硬件。

实训项目的最小输入清单：

| 输入材料 | 读它为了得到什么 |
|---|---|
| block diagram | 模块边界、主从关系、总线连接 |
| address map | CPU 访问每个寄存器和 memory 的地址 |
| register spec | reset 值、读写属性、status/mask/clear 语义 |
| IP list | 自研/外购、soft/netlist/hard、交付模型 |
| bus protocol | ready、response、error、burst、等待周期 |
| clock/reset plan | 时钟域、复位关系、CDC/RDC 风险 |
| verification plan | 每个模块的输入、输出、覆盖点和 done criteria |

拿不到这些输入，RTL 不是不能写，而是很容易写成“单模块能跑、系统接不上”的孤岛。

## 10. 工程检查表：拿到 SoC 需求先问什么

| 问题 | 为什么重要 |
|---|---|
| 主控是谁？ | 决定谁发起寄存器和 memory 访问 |
| IP 挂在哪条总线？ | 决定协议、地址、ready/error |
| 需要哪些寄存器？ | 决定软件如何控制硬件 |
| 需要哪些中断？ | 决定事件通知和清除策略 |
| 数据通路在哪里？ | 决定 FIFO、DMA、memory 访问 |
| 性能目标是什么？ | 决定频率、并行度、流水线 |
| 使用什么工艺和库？ | 决定 timing、area、power 边界 |
| 哪些 IP 外购？ | 决定模型、约束、黑盒和验证责任 |

## 11. 与 AI+IC 工程的连接

AI 加速器也是 SoC 里的一个或多个 IP。NPU 不只包含 MAC 阵列，还要有寄存器配置、DMA 搬运、片上 SRAM、外部总线、中断、clock/reset、debug 和软件驱动。

把本章方法迁移到 NPU，可以得到：

- CPU 通过 APB/AHB 配置 NPU 寄存器。
- DMA 把模型权重和输入特征图搬到 SRAM。
- NPU 计算完成后置位 status 并发 interrupt。
- 软件读取 done/error，安排下一轮任务。
- 约束、库、SRAM macro 和频率决定 RTL 是否能落地。

所以本章不是“项目背景”，而是 AI+IC 系统设计的入门骨架。

## 复习与自测

1. 为什么实训项目不能只按单个 RTL 模块理解？
   - 答案要点：它是 SoC，模块之间通过总线、寄存器、中断、memory 和软件驱动协作；单个模块功能正确不代表系统可用。

2. core 电压、IO 电压和工艺为什么前端也要关心？
   - 答案要点：它们影响标准单元库、IO cell、电平兼容、时序模型、功耗和后端 handoff。

3. Soft IP、Netlist、Hard IP/GDS 的可修改性有什么区别？
   - 答案要点：Soft IP 通常可读可改；netlist 很难改；hard IP/GDS 只能集成，不能改内部。

4. 外设发中断后，CPU 为什么还要读状态寄存器？
   - 答案要点：中断只表示有事件，状态寄存器说明事件原因、错误类型、完成状态和清除方式。

5. NorFlash 为什么不能简单当成片内同步 memory？
