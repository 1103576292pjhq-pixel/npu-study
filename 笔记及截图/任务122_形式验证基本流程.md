# 任务122：形式验证基本流程

## 本章知识全景图
本节把 Formality 从概念变成流程：启动工具，读 SVF guidance，读 reference，读 implementation，match，verify，debug。每一步都在缩小“综合后是不是还等价”的不确定性。

| 阶段 | 做什么 | 成功信号 | 失败优先查 |
|---|---|---|---|
| Invoking | 启动 `fm_shell`、GUI 或脚本 | log 和 FM_WORK 生成 | 命令、license、工作目录 |
| Guidance | 读入 SVF | DC 变换记录被接受 | SVF 路径、版本、读入顺序 |
| Setup | 设置推荐变量和环境 | 工具按 Synopsys 推荐模式运行 | app var 拼写、变量覆盖 |
| Read reference | 读 RTL golden | reference container 有 top | RTL 路径、top 名 |
| Read implementation | 读 DDC/netlist 和库 | implementation container 完整 | DB/lib、cell unresolved |
| Match | 对齐 compare points | unmatched 很少且可解释 | SVF、命名、层次、优化 |
| Verify | 证明等价 | pass 或可定位 fail | failing cone、black box、约束 |

最短学习路径：先保证运行可追溯，再把 SVF 放在 match 前，随后按 reference / implementation / match / verify 的顺序建立证据链。

## 1. 启动方式要留下证据
Formality 可以交互启动、GUI 启动，也可以脚本启动。脚本方式更接近工程交付：

```sh
fm_shell -f runme.fms | tee runme.log
```

| 生成物 | 作用 |
|---|---|
| command log | 记录执行过的 Formality 命令 |
| formality log | 记录工具输出、warning、error |
| FM_WORK | 保存工具工作数据库和临时文件 |
| session 文件 | 保存/恢复当前会话状态 |

GUI 对新手有价值，因为它能提示漏步骤、提供 context-sensitive help，并把鼠标动作转成 Tcl 记录。但最终流程必须脚本化，否则无法复现。

## 2. Guidance / SVF 是 match 的前置信息
SVF 是 DC 输出给 Formality 的变换记录。它不是功能描述，而是告诉 Formality：综合过程中哪些名字改了、哪些寄存器合并了、哪些 FSM 重编码了、哪些 datapath 被重构了。

SVF 常记录：

- name changes：命名规则转换。
- constant optimization：常量传播和无效逻辑删除。
- datapath transformation：算术结构重构。
- retiming：寄存器跨组合逻辑移动。
- FSM recoding：状态编码变化。
- register banking / merge：寄存器合并或重组。

不用 SVF 的前提很苛刻：设计简单、命名稳定、优化少。真实项目通常不满足，所以 SVF 应在 match 前读入。

可以把 SVF 理解成综合过程的“翻译字典”：RTL 里的 A 名字在网表里变成 B，两个寄存器被合并成一个，FSM 编码从 one-hot 改成 binary，datapath 从普通加法器换成 DesignWare 结构。没有这本字典，Formality 只能靠名字和结构硬猜；猜不出来就是 unmatched，猜错了还可能造成错误 debug。

## 3. Auto setup 降低 DC 到 Formality 的摩擦
`synopsys_auto_setup true` 会启用一组 Synopsys 推荐设置，让 Formality 更适配 DC 产生的网表、SVF、clock gating、scan model 和 HDL 解释方式。

auto setup 只是降低摩擦，不是自动证明正确。它不能替你修错 top、缺库、缺 SVF、读反 reference/implementation，也不能把真实功能差异变成 pass。工程判断仍要回到 log、unmatched、verify result 和 report。

它的作用是减少低级坑，不是替你判断结果。变量仍然要查，warning 仍然要读，最后一次设置仍然会覆盖前面的值。设置 app variable 时优先用 `set_app_var`，因为拼错变量名时更容易暴露。

## 4. 读 reference 和读 implementation 不是同一个动作
| 对象 | 常见输入 | 是否必须读技术库 | 说明 |
|---|---|---|---|
| reference | RTL Verilog/SystemVerilog/VHDL | 纯 RTL 通常不强制 | golden 功能基准 |
| implementation | gate netlist、DDC | 通常必须 | 有 standard cell，需要库功能模型 |

implementation 如果缺 DB/lib，会出现 cell unresolved、unknown module 或 black box 过多。此时不要先判断功能不等价，先修输入环境。

## 5. Basic script 的逻辑骨架
命令细节会随版本和项目变化，但骨架稳定：

```tcl
set_svf ./default.svf
set_app_var synopsys_auto_setup true

read_db ./sc_max.db
read_verilog -r ./rtl/top.v
set_top r:/WORK/top

read_verilog -i ./mapped/top.v
    # 或 read_ddc -i ./mapped/top.ddc
set_top i:/WORK/top

match
verify
report_verification
report_unmatched_points
report_failing_points
report_aborted_points
```

真正要背的是职责，不是拼写：SVF 指导匹配，DB 解释 cell，reference 是 golden，implementation 是被测，match 建对应点，verify 证明等价，report 形成证据。

report 命令是把屏幕上的一闪而过变成可审查证据。`report_verification` 看总体结论，`report_unmatched_points` 看“谁没找到对象”，`report_failing_points` 看“谁找到对象但逻辑不同”，`report_aborted_points` 看“谁还没证明完”。它们像四张分诊单：总检、身份未核验、病灶已定位、检查未完成，不能混在一起读。

```tcl
redirect -tee reports/fm_verify.rpt {
  report_verification
}

redirect -tee reports/fm_unmatched.rpt {
  report_unmatched_points
}

redirect -tee reports/fm_failing.rpt {
  report_failing_points
}

redirect -tee reports/fm_aborted.rpt {
  report_aborted_points
}
```

若项目工具版本不支持完全相同的命令名，也要保留这四类证据：总体结果、unmatched 列表、failing 列表、aborted 列表。只写一句 “verify failed” 不能指导 debug，因为它没有说明失败发生在身份匹配、逻辑证明还是资源/复杂度。

## 6. 常见失败定位表
| 现象 | 更可能的原因 | 先查 |
|---|---|---|
| top 找不到 | 文件未读入、top 名错、container 错 | read log、module 名、set_top |
| unresolved cell | 库没读或版本不对 | DB/lib 路径、search_path |
| unmatched 很多 | SVF 缺失、命名变化、层次变化 | set_svf、change_names、综合日志 |
| verify fail 少量点 | 真功能差异或错误 match | failing compare point 和 logic cone |
| aborted | 复杂度、资源、黑盒策略 | timeout、memory、cut point、black box |

## 7. 可复现流程检查
1. 启动后确认 log、FM_WORK、版本信息。
2. 读 SVF 后确认 guidance 无明显 error。
3. 读库后确认 standard cell 可解析。
4. 读 reference 后确认 top 在 `r` 容器。
5. 读 implementation 后确认 top 在 `i` 容器。
6. match 后先看 unmatched，再看 verify。
7. verify 后保存 report，不把屏幕一闪而过的结论当证据。

## 工程练习

1. 写 Formality 最小 PASS/FAIL。

   合格答案：log 中库、SVF、reference、implementation 都成功读入；top 设置正确；match 后 unmatched 数量为 0 或可解释；verify 结果 pass；`report_verification` 保存到文件。若 unresolved cell、top 找不到、SVF error 或大量 unmatched，不能把 verify 结果当真。

2. 给 aborted 建排查路径。

   合格答案：先查是否有黑盒或 unresolved cell，再查 proof 资源、timeout、cut point、状态空间复杂度；必要时局部 debug failing/aborted compare point。aborted 不是功能不等价，它只是工具没有完成证明。

## 自测与答案
1. 为什么 SVF 要在 match 前读？  
答案：SVF 指导对象对应关系，match 后再读已经错过主要作用。

2. unresolved cell 是功能不等价吗？  
答案：通常不是，优先说明库或输入环境不完整。

3. GUI 的最大学习价值是什么？  
答案：它把流程步骤可视化，并把点击动作转成 Tcl，帮助初学者理解脚本应该怎么写。

4. 为什么要保存 session？  
答案：复杂 debug 可能需要恢复现场，避免每次从头读入所有设计和库。
