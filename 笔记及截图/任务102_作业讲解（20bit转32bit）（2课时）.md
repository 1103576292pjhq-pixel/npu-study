# 任务102：作业讲解（20bit转32bit）（2课时）

## 本章知识全景图

这一讲是一场完整的小型 RTL 实战：把 `clk_x` 域连续输入的 20bit 数据流，转换成 `clk_y` 域连续输出的 32bit 数据流，并用仿真和 Verdi 波形证明转换没有丢数、重排、提前 valid 或尾部错位。

| 知识块 | 要解决的问题 | 直接结论 |
|---|---|---|
| 规格解析 | 20bit 到 32bit 为什么不是简单拼接 | 最小公共窗口是 160bit，8 个输入 beat 对应 5 个输出 beat |
| CDC 边界 | 输出时钟域怎样知道输入域写了多少 | 用 Gray 码/同步计数把输入进度带到输出域，再转回 binary 判断 |
| ready 条件 | 什么时候可以吐出一个 32bit | `已接收 bit 数 - 已输出 bit 数 >= 32`，且不能让初始 0 误触发 |
| 数据切片 | 5 个输出 word 怎么从缓冲中切 | 按 `out_cnt` 选择 `[31:0]`、`[63:32]`、`[95:64]`、`[127:96]`、`[159:128]` 等窗口 |
| bypass/init | 绕过和初始化为什么是状态边界 | bypass 不能污染转换缓存；init/stop 要清计数和 valid |
| 仿真调试 | 为什么 coding 完还不算完成 | 必须看编译日志、波形、输入输出对应关系、尾部和延迟 |

最短学习路径：先把题面翻译成接口语义，再算 8 入 5 出的 160bit 批次，然后写 CDC 计数与 ready，最后用波形验证每个输入 beat 进入了正确的输出 word。

## 1. 先把题面翻译成数据守恒问题

20bit 输入和 32bit 输出的本质是数据守恒：输入流中每一位都要按顺序出现在输出流里，不能因为位宽改变就丢、重、乱。

最小公共窗口：

```text
LCM(20, 32) = 160 bit
8  * 20 bit = 160 bit
5  * 32 bit = 160 bit
```

因此，本题可以按一个 160bit 缓冲窗口来理解：

```text
clk_x 域：每个 i_data_en 写入一个 20bit beat
clk_y 域：只要累计数据足够，就输出一个 32bit beat
8 个输入 beat 全到齐后，正好输出 5 个 32bit beat
```

一个更直观的比喻是：输入侧每次递来一块 20bit 的积木，8 块刚好拼成一根 160bit 长梁；输出侧不是按原来的积木块拿，而是把这根长梁切成 5 段 32bit。只要长梁的拼接端序或切割位置错一格，输出看起来仍然有 5 段，但已经不是原来的数据。

如果不先算 160bit，后面的代码会变成“凭感觉切位”。这种代码通常能通过编译，但波形里会出现第一拍提前输出、某个 32bit 重复、最后一个 32bit 丢失等问题。

## 2. 接口语义决定状态边界

题面里每个信号都要先归到某个时钟域。

| 信号 | 时钟域 | 作用 | 易错点 |
|---|---|---|---|
| `clk_x` | 输入域 | 20bit 输入侧时钟 | 更快，但不要用“更快”代替 CDC 设计 |
| `i_data[19:0]` | `clk_x` | 输入数据 | 只有 `i_data_en` 有效才计入转换 |
| `i_data_en` | `clk_x` | 输入 beat valid | 无效输入不能推进写指针 |
| `i_bypass` | `clk_x` | 绕过转换 | 旁路不能把转换缓存的旧数据带出去 |
| `init` | 控制信号 | 启动/停止转换 | 跨域使用时也要同步或明确时序假设 |
| `clk_y` | 输出域 | 32bit 输出侧时钟 | 输出 valid 必须在此域产生 |
| `o_data[31:0]` | `clk_y` | 输出数据 | 必须与 `o_data_en` 同拍有效 |
| `o_data_en` | `clk_y` | 输出 beat valid | 不能在数据不足时提前拉高 |
| `o_data_state` | `clk_y` | 状态/异常 | 本讲简化，但真实设计要定义 overflow/underflow |

本题没有 ready/backpressure，所以它不是完整流控接口。输入有效时设计必须接住；输出域只能根据内部已有 bit 数决定是否吐数据。

## 3. CDC 不是“打一拍就行”，要同步可比较的进度

输出域要回答“我能不能输出下一个 32bit”，必须知道输入域已经写了多少 20bit。这个进度不能用二进制计数直接跨域。

视频中采用类似异步 FIFO 的思路：

```text
clk_x:
  in_cnt_bin  -> in_cnt_gray

CDC:
  in_cnt_gray -> 两拍同步到 clk_y

clk_y:
  in_cnt_gray_sync -> in_cnt_bin_y
```

![Gray 码与输出域计数](<./screenshots/任务102_作业讲解（20bit转32bit）（2课时）/task102_dense_2040s_00h34m00s.png>)

Gray 码的作用是让相邻计数只变一位，降低跨域采样时读到混合值的风险。同步到 `clk_y` 后再转回 binary，才适合做大小判断。

看这张图时要抓住一点：跨域传过去的不是“原始数据”，而是输入域的进度牌。输出域拿到进度牌后，还要减去自己已经吐出的 32bit 数量，才能判断窗口里是否真的够下一个 32bit；只看两个计数“不相等”并不可靠。

一个概念上正确的 ready 判断是：

```text
received_bits_y = synced_in_cnt_bin * 20
sent_bits_y     = out_cnt_total * 32
available_bits  = received_bits_y - sent_bits_y
can_output      = available_bits >= 32
```

真实 RTL 可以不用乘法实现，但逻辑含义必须等价。不能写成“输入计数不等于输出计数就输出”，因为 20bit 和 32bit 的粒度不同。

## 4. `available_bits >= 32` 要避开初始 0 陷阱

视频后半段波形暴露的核心问题之一，是 ready 判断在初始状态可能误触发。

如果写成某种等价错误：

```text
available_bits >= 0
```

那么 reset 后 `available_bits=0` 也满足条件，输出域可能在没有任何输入数据时就拉高 valid。这种 bug 只看代码很容易忽略，因为表达式看起来“边界也包含”；但波形会直接显示第一组输出过早出现。

正确的判断必须保证至少覆盖下一个完整 32bit：

```text
available_bits >= 32
```

同时还要检查 `init`、bypass、reset 和本批次尾部。宽度转换最怕的不是完全不输出，而是“看起来能输出，但第一拍和最后一拍错”。

## 5. 输出切片要按 5 个 32bit 位置检查

当 160bit 缓冲窗口建立后，输出侧每次用 `out_cnt` 选择一个 32bit 窗口。

![输出切片代码](<./screenshots/任务102_作业讲解（20bit转32bit）（2课时）/task102_dense_3480s_00h58m00s.png>)

概念模型：

```verilog
case (out_cnt)
  3'd0: o_data = buffer[31:0];
  3'd1: o_data = buffer[63:32];
  3'd2: o_data = buffer[95:64];
  3'd3: o_data = buffer[127:96];
  3'd4: o_data = buffer[159:128];
endcase
```

实际代码的 bit range 可能根据拼接方向调整，但必须通过一个可复现检查：

```text
输入：x0 x1 x2 x3 x4 x5 x6 x7   每个 20bit
拼接：{x7,x6,x5,x4,x3,x2,x1,x0} 或约定的相反端序
输出：y0 y1 y2 y3 y4           每个 32bit
要求：{y4,y3,y2,y1,y0} 与输入拼接后的 160bit 完全一致
```

这里要显式规定端序。没有端序约定，仿真输出“看起来有 5 个数”并不代表正确。

## 6. bypass 和 init 会改变数据路径

`i_bypass=1` 时，数据应绕过转换路径；`init` 停止或重新开始时，内部状态必须回到明确边界。

需要清理或隔离的状态包括：

- 输入累计计数。
- 输出累计计数和 `out_cnt`。
- 160bit 缓冲窗口。
- `o_data_en` 和任何 data_ready 寄存器。
- CDC 同步链的有效性假设。

如果这些状态不清，常见波形是：重新 init 后第一组输出混入上一组尾部，或者 bypass 结束后转换路径继续吐旧数据。

本题最常见的三类失败信号是：第一拍提前 `o_data_en`，说明 ready 边界把初始 0 当成可输出；最后一拍缺失或多吐，说明批次尾部计数没有闭合；重新 `init` 后输出旧片段，说明缓存和计数没有被同一个边界清干净。

## 7. Testbench 不必一开始复杂，但必须能证明 8 入 5 出

视频中后半段搭 testbench、filelist、VCS 编译和 Verdi 波形。最低可用 testbench 要覆盖一个完整批次和一个连续批次。

![testbench 与编译入口](<./screenshots/任务102_作业讲解（20bit转32bit）（2课时）/task102_dense_4680s_01h18m00s.png>)

最低测试计划：

1. 生成 `clk_x` 和 `clk_y`，比例接近题面带宽关系。
2. reset/init 后连续发送 8 个 20bit 输入。
3. 记录 5 个 32bit 输出，拼回 160bit 对比。
4. 再连续发送第二组 8 个输入，检查批次边界。
5. 中间拉低 `i_data_en`，检查不会把无效输入计入。
6. 切换 bypass/init，检查旧缓存不会污染新输出。

这比“随机发一些数，看波形差不多”更可靠。宽度转换器的 bug 往往在 batch 边界、valid 边界和尾部。

## 8. Verdi 波形要按四组信号看

波形调试不是把所有信号都拖进去。先抓四组：

| 波形组 | 要证明什么 | 错误现象 |
|---|---|---|
| 输入组 | `i_data_en` 有效时输入计数才推进 | 无效周期也计数，或有效 beat 漏计 |
| CDC 组 | 输出域延迟看到输入进度 | 同步后计数乱跳或永远不变 |
| ready/valid 组 | 数据足够时才 `o_data_en` | 初始就 valid，或最后多吐一拍 |
| 数据组 | 5 个输出拼回 160bit | 输出重复、错位、漏最后一段 |

![Verdi 波形定位](<./screenshots/任务102_作业讲解（20bit转32bit）（2课时）/task102_dense_5280s_01h28m00s.png>)

视频里从 01:28:00 到 01:52:00 的价值就在这里：先发现输出不像预期，再回到 ready、计数、切片条件修代码。RTL 学习不能停在“老师写完了”，而要学会从波形倒推代码条件错在哪里。

![修正后的波形检查](<./screenshots/任务102_作业讲解（20bit转32bit）（2课时）/task102_dense_6600s_01h50m00s.png>)

## 9. 延迟是 CDC 成本，不是天然 bug

这个转换器会有延迟，主要来自两个来源：

- 跨域同步链通常引入两拍左右延迟。
- 输出必须等累计 bit 数够 32bit，不能收到第一个 20bit 就输出。

因此验收时不要把“输出晚几拍”直接判错。真正要检查的是：延迟是否稳定，valid 是否与数据同拍，连续批次是否能保持吞吐，最后一拍是否正确收尾。

## 本章收束与检查

- 20->32 转换的自然批次是 160bit，即 8 入 5 出。
- 输出域判断 ready 时，要用跨域同步后的输入进度。
- Gray 码同步解决的是多 bit 计数跨域采样风险。
- `available_bits >= 32` 是 ready 的核心口径，初始 0 不能误触发。
- 切片必须有端序约定，并用 160bit 拼回验证。
- bypass/init 是状态边界，不处理会污染下一批数据。
- 编译过关只是语法门，Verdi 波形才证明功能闭合。

## 自测题

1. 为什么本题不是“收到 2 个 20bit 就输出 1 个 32bit”？  
   答：2 个 20bit 是 40bit，会多出 8bit；连续流必须按 160bit 最小公共窗口处理，8 个 20bit 正好对应 5 个 32bit。
2. `i_data_en=0` 时输入计数能不能推进？  
   答：不能。否则无效输入会占据 20bit 位置，导致后续所有输出错位。
3. 为什么 ready 判断不能只看输入计数和输出计数是否不同？  
   答：输入单位是 20bit，输出单位是 32bit，计数单位不同；必须换算成 bit 数或等价状态。
4. 看到第一拍 `o_data_en` 提前拉高，应优先查什么？  
   答：查 ready 条件是否把初始 0 当成可输出，查 reset/init 后 valid 是否清零。
5. 怎样验证端序正确？  
   答：用 8 个可区分的 20bit 输入拼成 160bit，再把 5 个 32bit 输出拼回，按约定端序逐 bit 比较。
