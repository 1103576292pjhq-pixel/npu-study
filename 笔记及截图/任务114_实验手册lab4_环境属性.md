## 1. lab4 的核心输入：端口环境表
实验手册给出的表格把端口分成 input ports 和 output ports。学习重点不是照抄表格，而是把表格翻译成命令对象。

![端口环境表](<./screenshots/任务114_实验手册lab4_环境属性/video_dense_03_07m28s.jpg>)

| 端口类型 | 环境条件 | 对应命令 |
|---|---|---|
| input ports | 输入 transition、driving cell 或外部驱动条件 | `set_input_transition`、`set_driving_cell` |
| output ports | 输出 load、max capacitance | `set_load`、`set_max_capacitance` |
| clock | 时钟约束和时钟属性 | `create_clock`、clock 相关命令 |

clock 不应被当成普通 input 统一套 driving cell。实验中如果统一使用 `[all_inputs]`，必须排除 clock。

## 2. 约束文件骨架：先对象集合，再环境属性
推荐写法：

```tcl
reset_design

create_clock -period 3 [get_ports Clk]
set_clock_uncertainty -setup 0.12 [get_clocks Clk]

set ALL_INP_EXC_CLK [remove_from_collection [all_inputs] [get_ports Clk]]
set OUTPUTS [all_outputs]

set_input_transition 0.12 $ALL_INP_EXC_CLK
set_driving_cell -lib_cell FD1 $ALL_INP_EXC_CLK
set_load 0.05 $OUTPUTS
set_max_capacitance 0.2 $OUTPUTS
```

对象集合要先写清楚。很多 lab 错误不是命令不会写，而是对象选错：clock 被当成 data input，output 集合为空，或者端口名和 RTL 顶层不一致。

## 3. 执行 flow：source 成功只是第一步
视频中 DC 执行阶段显示大量命令输出。这里的关键是确认约束文件已经被读入当前 design。

![DC 执行输出](<./screenshots/任务114_实验手册lab4_环境属性/video_dense_06_14m57s.jpg>)

典型流程：

```tcl
read_verilog MY_DESIGN.v
current_design MY_DESIGN
link
check_design
source MY_DESIGN.con
check_timing
```

如果 `current_design` 不对，约束可能 source 到错误对象；如果 `link` 失败，port/cell 对象也可能不完整。不要只看最后有没有回到 prompt。

视频 17:27-24:56 是编辑约束文件的关键段。

![编辑环境属性 1](<./screenshots/任务114_实验手册lab4_环境属性/video_dense_07_17m27s.jpg>)

写完后要能回答：

| 命令 | 在哪里验证 |
|---|---|
| `set_input_transition` | `report_port -verbose` 的 input transition |
| `set_driving_cell` | port drive / input driving 信息 |
| `set_load` | output port load 信息 |
| `set_max_capacitance` | `report_constraint` 或 DRC violation |

## 5. 报告检查：lab4 的完成点在 report，不在 compile
如果报告中没有属性，说明 lab 没完成。视频最后展示了报告输出，这才是环境属性是否生效的证据。

![report 输出 1](<./screenshots/任务114_实验手册lab4_环境属性/video_dense_11_27m26s.jpg>)

![report 输出 2](<./screenshots/任务114_实验手册lab4_环境属性/video_dense_12_29m55s.jpg>)

检查顺序：

1. `report_port -verbose`：端口属性是否出现。
2. `report_constraint -all_violators`：max capacitance、transition 等是否有 violation。
3. `report_timing`：delay 是否在新的 load/transition 条件下计算。

如果 output load 没有出现在报告中，后续 timing 结果不能信；如果 max capacitance violation 存在但没有解释，说明电气约束没有闭环。

## 6. 返工路径
| 问题 | 先查什么 |
|---|---|
| source 报端口找不到 | RTL 顶层端口名、`current_design`、`link` |
| clock 被普通 input 属性覆盖 | `$ALL_INP_EXC_CLK` 是否正确排除 clock |
| output load 未生效 | `$OUTPUTS` 是否为空、命令是否在 source 后执行 |
| max cap violation | 负载预算是否过大、驱动是否太弱、是否需要 buffer/更强 cell |
| timing 结果和预期不一致 | transition/load 是否改变了 cell delay 查表条件 |

## 工程练习

1. 给 lab4 写最小验收清单。

   合格答案：`source` 无对象找不到；`report_port -verbose` 能看到 input transition、driving cell 或 output load；`report_constraint -all_violators` 中 max cap/transition violation 可解释；`report_timing` 的 cell delay 在新环境下重算；clock 未被普通 data input 属性误覆盖。

2. 判断“报告没有 load”的失败路径。

   合格答案：先查 `$OUTPUTS` 集合是否为空，再查端口名与 RTL 顶层是否一致，再查命令是否在 `current_design/link` 后执行，最后查是否被后续 reset 或 source 覆盖。

## 复习与自测
1. lab4 为什么必须看 `report_port -verbose`？  
   答：它能证明 input transition、driving cell、load 等属性是否真正施加到端口。

2. clock 为什么不能直接混在普通 input 集合里？  
   答：clock 有专门的时钟语义和 clock network 约束，不能按普通 data input 的 driving/transition 处理。

3. 如果 source 成功但报告没有 load，说明什么？  
   答：可能 output 集合为空、对象匹配错误，或命令没有作用到当前 design。

## AI+IC 连接
AI 芯片 block 的早期综合经常没有完整物理信息，lab4 这套流程可以把负载、边沿和驱动先用保守环境建模写入 SDC。对 NPU 的广播控制、SRAM 接口、NoC 输入输出，如果不做环境属性验证，后端 timing 和 DRC 风险会被推迟到更昂贵的阶段才暴露。
