## 1. JTAG 是 CPU 调试入口，不是普通外设

JTAG/debug 让外部调试器控制 CPU：设置断点、单步执行、查看寄存器和内存。它直接服务软件 bring-up 和芯片调试。

![SoC 架构图](<./screenshots/任务031_实训项目介绍2/soc_architecture_jtag_70s.jpg>)

视觉核验：视频 00:00-04:00，画面承担“定位调试入口”的教学职责。看图要点：JTAG/debug 路径不是普通 APB 外设，而是外部调试器进入 CPU、寄存器和 memory 的控制通道；要同时看 CPU、debug block、pad、clock/reset 和 test mode 是否连成闭环。如果看不懂这张图，会把 bring-up 失败误判成软件问题，漏掉 debug clock/reset、pad mux 或 test mode 抢占这类顶层集成 bug。

前端要关心：

- debug 模式如何进入。
- CPU halt/resume/single-step 信号如何连接。
- JTAG pad、test mode、scan/DFT 是否共享路径。
- debug clock/reset 是否与主系统有跨域关系。
- bring-up 时软件如何通过 GDB 观察问题。

JTAG 的存在说明芯片交付不是“RTL 仿真过了”就完。软件调试、板级验证和量产测试都要提前在顶层架构中预留路径。

一个有用比喻：JTAG 像芯片内部的“维修通道”，不是给普通业务流量走的主路；正常软件从 boot path 进入系统，调试器则通过这条维修通道暂停 CPU、查看现场、改寄存器。这个比喻的边界也要记住：维修通道仍然受 clock/reset、pad、test mode 约束，不是绕开所有硬件问题的万能入口。

## 2. USB PHY/PCS 暴露数字和模拟边界

USB 不是纯 RTL 外设。协议和控制可以是数字逻辑，真正把片内信号送到片外高速差分线的是 PHY，PCS 负责协议层与物理层之间的编码和转换。

![USB PHY/PCS](<./screenshots/任务031_实训项目介绍2/usb_phy_pcs_400s.jpg>)

视觉核验：视频 06:00-10:00，画面承担“划清数字前端和混合信号 IP 边界”的教学职责。看图要点：数字控制/寄存器/FIFO 通常由 RTL 负责，PCS 负责数字编码和速率/宽度适配，PHY/pad 负责真实电气收发；同时检查 PHY 的 clock、reset、power、test pin 和仿真模型。如果看不懂，会把 PHY 当成普通 Verilog 模块，后续在仿真模型、约束、pad 连接、DFT 测试口上漏项。

| 层次 | 主要职责 | 前端接口关注 |
|---|---|---|
| 数字控制/协议层 | 包处理、寄存器、状态机、FIFO | RTL、寄存器、验证 |
| PCS | 编码、数据宽度/速率转换 | 接口时钟、复位、控制状态 |
| PHY | 高速模拟/混合信号收发 | hard IP、pad、电源、模型 |
| Pad/IO | 片外电气连接 | IO cell、ESD、pinmux、封装 |

前端不一定设计 PHY，但要知道它是 hard/mixed-signal IP：集成时要有模型、wrapper、clock/reset、power、test mode 和约束。

## 3. master/slave 决定谁能主动发起访问

在总线系统中，master 主动发起读写，slave 被选中后响应。CPU 是典型 master；大多数外设是 slave；DMA 同时具有两种角色。

![master/slave 与 DMA](<./screenshots/任务031_实训项目介绍2/master_slave_dma_750s.jpg>)

视觉核验：视频 12:00-16:00，画面承担“区分总线主动方和响应方”的教学职责。看图要点：CPU 配置 DMA 寄存器时，DMA 是被地址选中的 slave；DMA 开始搬运后，它自己发地址和读写控制，变成 master。如果看不懂，会在 RTL 接口里漏掉 DMA master 端口、仲裁请求或错误响应处理，只把 DMA 当成一组寄存器。

| 角色 | 行为 |
|---|---|
| master | 发起地址、控制、读写方向和传输请求 |
| slave | 响应访问，返回 data/ready/error |
| DMA 配置阶段 | CPU 写 DMA 寄存器，DMA 像 slave |
| DMA 搬运阶段 | DMA 自己读写 memory/外设，DMA 像 master |

DMA 的价值是减少 CPU 搬数据负担。CPU 只写源地址、目的地址、长度和 start，后续读写总线由 DMA 自动完成。

可复现的角色追踪方法：拿任意 DMA 场景写两列清单，左列写“CPU 写了哪些寄存器”，右列写“DMA 随后主动访问了哪些地址”。左列出现的是 slave 行为，右列出现的是 master 行为；如果两列混在一起，说明还没有建立正确的总线角色模型。

## 4. SPI + DMA + FIFO 是生产者/消费者系统

SPI 串行发送速度和片内总线写入速度通常不同。FIFO 的任务是解耦这两种节奏。

![DMA、SPI 与 FIFO](<./screenshots/任务031_实训项目介绍2/dma_spi_fifo_pingpong_1000s.jpg>)

视觉核验：视频 16:00-21:00，画面承担“把数据搬运链路画成生产者/消费者系统”的教学职责。看图要点：确认 DMA/CPU 谁写 FIFO，SPI 谁读 FIFO，FIFO level/full/empty 如何反馈，ping-pong buffer 何时切换，done/error/irq 由谁产生。如果看不懂，会只看到模块名，看不到流控条件，后续容易写出满了继续写、空了继续读、切换点丢一拍的设计。

典型数据流：

```text
CPU 配置 DMA 和 SPI
  -> DMA 从 memory 读数据
  -> DMA 写入 SPI TX FIFO
  -> SPI 从 FIFO 取数据并串行发送
  -> FIFO level/full/empty/done/error 反馈给状态寄存器或中断
```

ping-pong FIFO 的直觉：

- SPI 正在消费 FIFO0。
- DMA 同时填 FIFO1。
- FIFO0 空后切换到 FIFO1。
- 状态或中断通知下一块数据准备。

这个结构不是为了复杂，而是为了隐藏速率差：总线/DMA 批量写入快，SPI 串行输出慢。

比喻要落在机制上：FIFO 像装配线中间的料仓，DMA 是上料机，SPI 是慢速出料口。料仓的价值不是“存东西”这四个字，而是把上料速度和出料速度解耦；料仓没有 full/empty/level，就等于生产线没有库存表，出了断料或溢料也无法定位责任方。

## 5. overflow / underflow 是速率不匹配的症状

FIFO 错误不是抽象名词，而是生产者和消费者节奏失配。

![FIFO overflow/underflow](<./screenshots/任务031_实训项目介绍2/fifo_overflow_underflow_1270s.jpg>)

视觉核验：视频 21:00-24:00，画面承担“把 FIFO 错误变成可验证失败信号”的教学职责。看图要点：overflow 对应 full 后仍写，underflow 对应 empty 后仍读；要同时看状态位、中断、数据保持/丢弃策略和恢复方式。如果看不懂，会只在正常吞吐场景里验证 FIFO，漏掉真正能暴露流控 bug 的负向测试。

| 问题 | 含义 | 常见原因 | 验证重点 |
|---|---|---|---|
| overflow | 满了还写 | DMA/producer 过快、没看 full | full 时写请求、错误状态、中断 |
| underflow | 空了还读 | SPI/consumer 过快、没看 empty | empty 时读请求、发送暂停、错误状态 |

硬件需要提供 full/empty/level/status/interrupt，软件需要知道何时补数据、何时处理异常。FIFO 没有清楚的状态寄存器，系统调试会非常痛苦。

DMA/FIFO 验证不能只跑“刚好不出错”的顺流场景，还要故意制造速率不匹配。

| 验证场景 | 刺激方式 | 期望结果 |
|---|---|---|
| FIFO 正常流动 | DMA 填充速度略快于 SPI 消费速度 | level 在安全范围内变化，不丢数据 |
| overflow 防护 | FIFO full 时继续给写请求 | 阻塞写入或置位 overflow，数据一致性不被破坏 |
| underflow 防护 | FIFO empty 时 SPI 继续取数 | 停止发送、填充默认值或置位 underflow，行为必须有规格 |
| ping-pong 切换 | FIFO0 消费、FIFO1 填充后切换 | 切换点不重复、不漏一拍、不乱序 |
| 中断/状态 | level 到阈值、done、error 同时发生 | status 可读、irq 可清、优先级明确 |

## 6. memory map 是软硬件共同地图

memory map 定义 CPU/DMA 访问某个地址时落到哪个 IP、哪个寄存器、什么权限、什么复位值。它是软件、RTL、验证共同依赖的单一地图。

![memory map 表](<./screenshots/任务031_实训项目介绍2/memory_map_table_1500s.jpg>)

视觉核验：视频 25:00-28:00，画面承担“把地址空间变成软硬件共同契约”的教学职责。看图要点：逐行检查 base address、size、offset、读写权限、复位值、reserved 区域和非法访问响应；同一地址必须在 RTL decoder、软件 header、验证模型里指向同一个对象。如果看不懂，会出现软件写对了寄存器名却打到错误地址、验证模型覆盖旧地址、decoder 命中冲突等问题。

![memory map 讨论](<./screenshots/任务031_实训项目介绍2/memory_map_1700s.jpg>)

视觉核验：视频 28:00-31:00，画面承担“检查 memory map 多份镜像一致性”的教学职责。看图要点：从一个 CPU 访问地址反推 decoder 命中哪个 slave、寄存器偏移是多少、软件宏和验证 sequence 是否使用同一数值。如果看不懂，会把地址表当文档附件，而不是可以生成 RTL、driver、UVM RAL 和测试常量的事实源。

三份镜像必须一致：

| 镜像 | 载体 | 不一致后果 |
|---|---|---|
| RTL | address decoder、register file、bus slave | CPU 访问落到错误 IP/寄存器 |
| 软件 | C header、driver、boot code | 软件写了错误地址 |
| 验证 | sequence、register model、scoreboard | 测试覆盖的是旧地图 |

成熟项目最好从一份 register/memory map 源生成 RTL 参数、软件 header、验证模型和文档，避免手写多份。

memory map 可以理解成 SoC 的门牌系统：master 手里只有地址，decoder 按门牌把访问送到对应 IP。门牌写错不是“文档小问题”，而是快递直接送错楼；在芯片里表现为写寄存器无效、读回默认值异常、非法地址没有 error 或 CPU 卡死。

## 7. boot mode 决定 CPU 从哪里取第一条指令

boot mode 回答 reset 释放后 CPU 的第一条指令来自哪里：内部 ROM、内部 flash、外部 NorFlash、JTAG/debug 或其他 boot source。

![boot mode 真值表](<./screenshots/任务031_实训项目介绍2/boot_mode_truth_table_1860s.jpg>)

视觉核验：视频 31:00-33:00，画面承担“定义 reset 后第一条指令来源”的教学职责。看图要点：检查 boot mode 选择信号、reset 默认值、采样时刻、优先级、非法组合和 debug/test boot 是否覆盖正常 boot。如果看不懂，会把“CPU 不启动”笼统归因到程序错，漏掉第一拍取指路径、ROM/Flash 映射或 boot strap 采样不稳定。

关键约束：

- boot 选择必须在 reset 释放前稳定。
- 非法组合要有定义行为。
- boot source 会影响地址映射和总线路径。
- debug/test boot 不能破坏正常 function mode。

boot mode 错了，CPU 不是“跑错一点”，而是可能第一条指令就取不到。

## 8. clock/PLL/divider 定义系统节奏

SoC 通常不是单时钟系统。外部晶振进入芯片后，可能经过 PLL、bypass、divider，再分发给 CPU、bus、外设和 debug/test 逻辑。

![clock 结构](<./screenshots/任务031_实训项目介绍2/clock_structure_2020s.jpg>)

视觉核验：视频 33:00-35:00，画面承担“建立系统时钟树地图”的教学职责。看图要点：定位外部 clock、PLL、bypass、divider、clock gate、CPU/bus/外设/debug domain，并标出 reset release 属于哪个时钟域。如果看不懂，会在 CDC/RDC、SDC generated clock、低功耗关钟和 bring-up 频率配置上漏检查。

![clock/PLL/divider](<./screenshots/任务031_实训项目介绍2/clock_pll_path_2100s.jpg>)

视觉核验：视频 35:00-37:00，画面承担“说明时钟模式会改变系统节奏”的教学职责。看图要点：分清 PLL lock 前后、bypass 模式、divider 配置、低功耗关钟和各 domain 的同步释放条件。如果看不懂，会写出仿真中能跑、上板后因 PLL 未锁定或 reset 跨域释放错误而随机失败的系统。

要问：

- CPU、bus、外设分别用哪个 clock？
- PLL bypass 时系统频率是多少？
- reset release 是否同步到各 domain？
- clock gate 后的 generated/gated clock 是否进入 CDC/SDC 约束？
- 低功耗模式会关闭哪些 clock？

clock 结构直接影响 CDC/RDC、综合约束、STA 和软件 bring-up。

## 9. pinmux/test mode 是顶层集成的高风险点

芯片 pad 数量有限，同一 pad 在 function mode、scan/test mode、analog/phy test、flash boot 等模式下可能连接不同内部信号。

![function/test mode](<./screenshots/任务031_实训项目介绍2/pinmux_function_testmode_2530s.jpg>)

视觉核验：视频 38:00-42:00，画面承担“暴露 pad 复用和测试模式优先级”的教学职责。看图要点：每个 pad 在 function/test/debug/boot/analog test 下由谁驱动，reset 默认接哪一路，output enable 是否互斥，输入是否跨域同步。如果看不懂，会在板级看到“引脚没反应”，但波形里只查外设内部，不查 pad mux 和 test mode 覆盖。

![总线和接口标准](<./screenshots/任务031_实训项目介绍2/bus_interface_standards_1380s.jpg>)

视觉核验：视频 23:00-25:00，画面承担“按层次区分接口标准”的教学职责。看图要点：片内总线负责 master/slave 事务，外设接口负责片外协议，调试/测试接口负责 bring-up 和量产路径；同一模块可能同时接多个层次接口。如果看不懂，会把 SPI/UART/USB、AHB/APB、JTAG/scan 混成一类，导致架构图和顶层端口表无法对齐。

pinmux 检查项：

| 检查点 | 风险 |
|---|---|
| reset 默认模式 | 上电后 pad 接错功能 |
| test mode 优先级 | 测试信号覆盖正常功能 |
| function mode 选择 | 软件配置后 pad 未切换 |
| 输入同步 | GPIO/外部输入跨域 |
| 输出 enable | 多个功能同时驱动 pad |

pinmux 错误常常不是仿真第一眼能发现的 bug，却会在板级 bring-up 时直接变成“引脚没反应”。

## 10. library、SRAM macro 和 FPGA prototype 进入交付链

大容量 memory 不会总是综合成寄存器阵列，真实 ASIC 常用 SRAM macro。项目列出 library/SRAM，是在告诉前端后续要处理 wrapper、black box、时序模型、test pin 和约束。

![library 与 SRAM 列表](<./screenshots/任务031_实训项目介绍2/library_sram_list_2840s.jpg>)

视觉核验：视频 46:00-49:00，画面承担“把抽象 memory 落到真实工艺资源”的教学职责。看图要点：SRAM macro 的宽度、深度、端口数、byte enable、test pin、时序模型、black box、LEF/lib/db 和综合/STA 约束是否齐全。如果看不懂，会把大 memory 写成寄存器阵列，或在综合/STA/DFT 阶段才发现 macro wrapper 与库文件不匹配。

FPGA prototype 用来尽早跑软件和系统交互，但它不能替代 ASIC signoff。

![FPGA 原型](<./screenshots/任务031_实训项目介绍2/fpga_prototype_3140s.jpg>)

## 11. 系统契约交付矩阵

| 契约 | RTL/集成落点 | 验证口径 | 交付物 |
|---|---|---|---|
| memory map | decoder、register file、reserved 响应 | 地址命中、越界、权限、复位值 | register spec、software header、验证常量 |
| DMA/FIFO | DMA master、FIFO、阈值、中断、错误状态 | burst/边界、full/empty、overflow/underflow | RTL、TB、波形、覆盖点 |
| boot mode | reset 后取指地址、ROM/Flash 映射 | 每种 boot 组合、非法组合、reset 稳定 | boot 表、顶层 mux、bring-up checklist |
| clock/reset | PLL/bypass/divider、domain 划分 | CDC/RDC、reset sequence、低功耗模式 | clock/reset spec、SDC、CDC/RDC 报告 |
| pinmux/test mode | pad mux、mode priority、test enable | 默认值、切换、误覆盖 | pinmux 表、DFT/test mode 表 |
| library/macro | SRAM、PLL、PHY、pad、clock gating cell | 模型可用、black box、约束检查 | library 清单、macro wrapper、handoff 包 |

SoC 集成的本质是把功能变成多方一致的契约。只要地址、clock、reset、mode、macro 有一项多源不一致，后续软件、验证或后端都会踩坑。

集成调试时先看失败信号，再反推契约缺口：

| 失败信号 | 优先排查 | 常见根因 |
|---|---|---|
| GDB 连不上或 CPU halt 无效 | JTAG pad、debug clock/reset、test mode | debug 路径被 pinmux/test mode 覆盖 |
| DMA 配置后不搬运 | memory map、DMA status、bus master 权限 | base 地址错、start/busy 语义错、仲裁未接通 |
| SPI 数据断续 | FIFO level、DMA burst、SPI 时钟分频 | producer/consumer 速率估错或阈值中断没接好 |
| reset 后不启动 | boot mode、取指地址、ROM/Flash 映射 | boot 选择不稳定或 reset 默认值错误 |
| 某些外设引脚无响应 | pinmux 默认值、output enable、pad 复用 | function/test mode 优先级错 |
| 综合或 STA 卡住 | SRAM macro、PLL/PHY model、library | wrapper、black box、时序模型或约束缺失 |

## 12. 可复现流程：从项目介绍抽出一张系统契约表

不要把本讲当成“老师展示项目 PPT”。更稳的复现方法是把每张架构图都转成可检查契约：

```text
1. 选对象：例如 DMA、SPI、SRAM、boot ROM、JTAG、PLL、pinmux。
2. 写输入：地址、clock/reset、mode、配置寄存器、数据流入口。
3. 写输出：read data、write side effect、irq/status、pad 输出、debug 状态。
4. 写状态变化：idle/busy/done/error、FIFO level、boot source、PLL lock、mode 切换。
5. 写失败信号：访问无响应、overflow/underflow、CPU 不启动、pad 无输出、CDC/STA 报错。
6. 写工程落点：RTL 端口、register spec、testbench 激励、断言、软件 driver、handoff 文件。
```

这 6 步能把“项目介绍”变成后续实训的任务清单。若某个对象写不出输入、输出和失败信号，它在项目里还只是名词，不是可实现、可验证、可调试的设计对象。

## 13. 与 AI+IC 工程的连接

NPU/AI 芯片项目同样需要这些契约：

- NPU 寄存器属于 memory map。
- DMA/FIFO 负责权重、激活、输出搬运。
- boot/driver 决定推理任务如何启动。
- clock/PLL/divider 决定计算阵列和总线频率。
- pinmux/test mode 决定调试、DFT、外设复用。
- SRAM macro 决定片上 buffer 的真实实现。
- FPGA prototype 帮助提前跑软件和模型搬运流程。

所以本章是从“知道 SoC 有哪些模块”进入“能维护系统一致性”的关键桥。

## 复习与自测

1. DMA 为什么既可能是 slave，又可能是 master？
   - 答案要点：CPU 配置 DMA 寄存器时 DMA 响应访问，是 slave；DMA 搬运数据时主动发起 memory/外设读写，是 master。

2. FIFO overflow 和 underflow 分别说明什么？
   - 答案要点：overflow 是满了还写，producer 太快或没检查 full；underflow 是空了还读，consumer 太快或没检查 empty。

3. 为什么 memory map 变更必须同步 RTL、软件和验证？
   - 答案要点：RTL decoder、软件 header、验证模型都依赖同一地址定义；任一处不一致都会导致访问错位或测试失真。

4. boot mode 选择为什么必须在 reset 释放前稳定？
   - 答案要点：CPU reset 后马上取第一条指令，boot source 不稳定会导致取指路径错误。

5. FPGA prototype 能验证什么，不能替代什么？
   - 答案要点：能验证软件 bring-up、寄存器/总线/系统交互；不能替代 ASIC 综合、STA、CDC、DFT、后端 signoff。

6. pinmux 设计最容易出什么系统级错误？
   - 答案要点：reset 默认功能错、test mode 覆盖 function mode、多个功能同时驱动 pad、输入跨域未同步、软件配置和硬件 mux 不一致。
