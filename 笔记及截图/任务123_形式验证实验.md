# 任务123：形式验证实验

## 本章知识全景图
本节把 Formality 流程放进真实 shell：读 setup、读库、读 SVF、读 reference、读 implementation、match、verify、看 report。学习目标不是背命令，而是知道每条命令失败时该查哪里。

| 实验环节 | 关键动作 | 正确理解 |
|---|---|---|
| common setup | 设置路径、库、top、变量 | 所有后续读文件都依赖它 |
| `set_app_var` | 设置工具应用变量 | 比普通 `set` 更容易暴露拼写错误 |
| read DB | 读标准单元库 | implementation gate cell 需要功能模型 |
| read SVF | 读综合变换记录 | 帮助 match 处理重命名、合并、重编码 |
| read reference | 读 RTL golden | 建立功能基准 |
| read implementation | 读 DDC/gate netlist | 建立被检查实现 |
| match / verify | 建对应点并证明等价 | 输出 pass/fail/unmatched/aborted |

最短学习路径：先看 setup 把环境装好，再看 log 证明每个输入被工具接受，最后根据 match/verify/report 判断实验是否通过。

| 截图 | 看图要点 | 漏看后果 |
|---|---|---|

## 1. 先读 common setup，因为它决定整个实验是否可信
setup 文件通常集中定义设计路径、库路径、工作目录、top 名、SVF 路径、目标库等。后面所有 `read_verilog`、`read_db`、`set_svf` 都依赖这些变量。

| setup 项 | 作用 | 错误信号 |
|---|---|---|
| design path | 找 RTL、netlist、DDC、SVF | file not found |
| library path | 找 DB/lib | unresolved cell |
| top name | 指定比较对象 | top not found 或比错模块 |
| work dir | 保存数据库和 log | 无法复现 debug 现场 |
| SVF path | 提供综合变换记录 | unmatched 激增 |

视频中提到 gvim 的 `gf` 和 `Ctrl-O`，本质是脚本阅读方法：看到路径不要只读文字，要跳到真实文件确认它存在。

## 2. `set_app_var` 的意义是防止静默错误
普通 Tcl `set` 可以创建任意变量。你把 `search_path` 拼成 `serach_path`，它可能只会新建一个没用的变量，脚本继续跑，后面才报找不到库。

`set_app_var` 面向工具应用变量，拼错时更容易给出错误或警告。形式验证实验里最浪费时间的不是复杂证明，而是路径、库、变量名、top 名这些输入错误。

## 3. 实验核心命令链
可以把脚本压缩成七类动作：

实验入口最好从一条可留痕命令开始：

```sh
fm_shell -f fm_run.tcl | tee logs/fm.log
```

这条命令同时满足两个要求：`fm_run.tcl` 固定实验动作，`logs/fm.log` 保存工具输出。没有 log 的实验像没有监控录像的实验室事故，结果对了也难复盘，结果错了更难定位。

```tcl
    # 1. 环境
set_app_var search_path $DESIGN_PATH
set_app_var synopsys_auto_setup true

    # 2. 库
read_db $TARGET_LIBRARY

    # 3. guidance
set_svf ./default.svf

    # 4. reference
read_verilog -r ./rtl/top.v
set_top r:/WORK/top

    # 5. implementation
read_ddc -i ./mapped/top.ddc
    # 或 read_verilog -i ./mapped/top.v
set_top i:/WORK/top

    # 6. compare
match
verify

    # 7. evidence
redirect -tee reports/fm_verify.rpt {
  report_verification
}

redirect -tee reports/fm_unmatched.rpt {
  report_unmatched_points
}

redirect -tee reports/fm_failing.rpt {
  report_failing_points
}

redirect -tee reports/fm_aborted.rpt {
  report_aborted_points
}
```

命令名字可能因版本不同略有变化，但职责不变。库解释 cell，SVF 解释综合变换，reference 提供 golden，implementation 提供被测设计，match/verify/report 给出可审查结果。

## 4. 看 log 要看“输入是否真的进入工具”
实验中大量终端输出不是噪声。它告诉你 DB 是否读入、SVF 是否接受、RTL 是否解析、DDC/netlist 是否进入 implementation container、top 是否设对。

| log 现象 | 判断 |
|---|---|
| library loaded / cell count 正常 | 标准单元库可用 |
| SVF accepted 或 guidance 信息出现 | 综合变换指导已进入 |
| current container / top 显示正确 | reference 或 implementation 目标正确 |
| unresolved / unknown module | 输入库或路径不完整 |
| warning 可解释且不影响对象 | 可记录后继续 |
| error 中断读入 | 不允许继续把 verify 结论当真 |

## 5. DDC 和 gate Verilog 都能作为 implementation，但检查点不同
DDC 保留 Synopsys 数据库信息，适合同生态；gate Verilog 更透明，适合跨工具和审查。DDC 读入失败时先查版本和路径；gate Verilog 读入失败时先查标准单元库、网表语法、特殊命名和 assign 清洁。

这和任务120 直接衔接：DC 输出阶段如果没有处理 multiple port net、change_names、SDC/netlist 一致性，Formality 实验阶段就会遇到对象找不到或匹配困难。

## 6. match/verify/report 的结果解释
| 结果 | 含义 | 下一步 |
|---|---|---|
| pass | 已匹配点被证明等价 | 保存 report，作为综合交付证据 |
| unmatched | 对应点没建立 | 查 SVF、命名、层次、top、优化变换 |
| fail | 对应点功能不等价 | 查 failing compare point 前的 logic cone |
| aborted | 工具没能完成证明 | 查资源、黑盒、cut point、复杂度 |

视频中的 schematic/debug 视图说明：fail 后要看 reference cone 和 implementation cone 的局部差异，而不是从整个设计头文件开始乱翻。

分诊顺序要固定，否则 debug 会像拿着手电在雾里乱照：

1. 先看 `reports/fm_unmatched.rpt`。如果 unmatched 很多，优先查 SVF、top、命名、层次和库，不要进入功能推理。
2. unmatched 可解释后，再看 `reports/fm_verify.rpt` 的总体结果。
3. 如果有 failing points，打开 `reports/fm_failing.rpt`，按 failing compare point 回溯 reference cone 和 implementation cone。
4. 如果有 aborted points，打开 `reports/fm_aborted.rpt`，查 proof 资源、black box、cut point、状态空间复杂度，不把 aborted 当成功，也不把它直接当功能 bug。
5. 任何 report 结论都要回到 `logs/fm.log` 查输入链是否完整：库、SVF、reference、implementation、top、match 命令都必须真实执行过。

| 报告文件 | 读法 | 常见修复方向 |
|---|---|---|
| `logs/fm.log` | 输入是否真的进入工具 | 修路径、库、top、脚本变量 |
| `reports/fm_unmatched.rpt` | 哪些点没有建立对应关系 | 补 SVF、修命名、检查层次/black box |
| `reports/fm_failing.rpt` | 哪些已匹配点逻辑不等价 | 沿 cone 查综合优化、ECO、RTL 差异 |
| `reports/fm_aborted.rpt` | 哪些点证明未完成 | 调资源、cut point、black box 或拆分证明 |
| `reports/fm_verify.rpt` | 最终总结果 | 归档为交付证据或进入 debug |

## 7. 实验复现检查表
1. setup 文件里的路径能跳转到真实文件。
2. `set_app_var` 没有未知变量或拼写错误。
3. 标准单元 DB 成功读入。
4. SVF 成功读入且无关键 error。
5. reference top 与 implementation top 都设对。
6. match 后 unmatched 数量可解释。
7. verify 后 report 保存，pass/fail/aborted 分类清楚。

## 工程练习

1. 给实验 log 做检查清单。

   合格答案：确认 `set_app_var` 没有未知变量；DB/lib 读入成功；SVF accepted；reference RTL 顶层存在；implementation DDC 或 gate netlist 顶层存在；match/verify/report 命令实际执行；report 文件被保存。任何输入失败都要先修输入，不要跳到功能结论。

2. 解释 gate Verilog 和 DDC 两种 implementation 的取舍。

   合格答案：DDC 保存 Synopsys 内部信息，读入快、匹配通常更顺；gate Verilog 更通用、更适合跨工具审查，但依赖标准单元库和命名清理。两者都要和 DC 输出同版，否则形式验证会把版本漂移误当设计差异。

## 自测与答案
1. 为什么 setup 文件比后面的 verify 命令更先检查？  
答案：setup 决定路径、库、SVF、top 和变量；输入错了，verify 结论没有可信度。

2. `set_app_var` 相比 `set` 的主要优势是什么？  
答案：设置工具变量时更容易发现拼写错误，减少静默错误。

3. implementation 读入报 unresolved cell，先查什么？  
答案：标准单元库/DB 是否读入、版本是否匹配、search path 是否正确。

4. verify fail 后应该先看哪里？  
答案：先看 failing compare point、match 是否正确、reference cone 与 implementation cone 的局部差异。
