# 任务121：形式验证基本概念

## 本章知识全景图
形式验证在本课程中主要指形式等价检查：证明综合/实现后的 implementation design 与已经验证过的 reference design 功能一致。它不是证明需求正确，而是证明综合没有把设计改坏。

| 概念 | 一句话定义 | 关键边界 |
|---|---|---|
| Reference design | 作为 golden 的设计，通常是已仿真的 RTL | 它必须先被认为功能正确 |
| Implementation design | 综合或物理实现后的设计 | 它是被检查对象 |
| Container | Formality 存放设计、库和数据库的容器 | 默认 reference 为 `r`，implementation 为 `i` |
| Compare point | register/latch、black box、primary output 等比较边界 | 工具在这些点上判断两边是否一致 |
| Logic cone | 驱动 compare point 的组合逻辑锥 | 等价证明的局部对象 |
| Match | 把两边对应点配对 | 解决“谁和谁比” |
| Verify | 对 matched 点做等价证明 | 解决“比出来是否一样” |

最短学习路径：先分清 reference 和 implementation，再用 compare point / logic cone 理解工具如何拆设计，最后区分 match 失败和 verify 失败。

## 视觉核对清单

形式验证的图要按“法庭审案”理解：reference 是原始合同，implementation 是被告版本，compare point 是审理节点，logic cone 是证据范围，match 是确认双方身份，verify 是判定证据是否一致。这个比喻的边界是：它只能审“两个版本是否等价”，不能证明合同本身写得对。

| 截图 | 看图要点 | 漏看后果 |
|---|---|---|
| Formality 基本术语 | reference、implementation、container 不可混 | 把两套设计读反或放错容器 |
| logic cone 与 compare point | 工具围绕比较点切 cone 做证明 | fail 后从全设计乱翻 |
| matching 与 verification cycle | match 和 verify 是两种失败 | unmatched 被误判成功能 bug |

## 1. 形式等价检查的第一前提：reference 是可信答案
Formality 假设 reference design 功能正确，然后检查 implementation 是否与它等价。reference 通常来自 RTL，因为 RTL 已经过仿真、review 或功能验证。

这带来一个重要边界：形式等价不能证明 RTL 符合需求。它只能证明综合后的门级实现没有偏离 RTL。功能验证回答“RTL 是否做对事”；形式等价回答“实现是否仍然是那个 RTL”。

| 验证类型 | 回答的问题 | 不能回答什么 |
|---|---|---|
| 功能仿真/UVM | RTL 是否满足场景和协议 | 综合有没有改坏结构 |
| 形式等价 | implementation 是否等价于 reference | reference 是否符合产品需求 |
| STA | 时序是否满足约束 | 功能是否等价 |

## 2. Container 让两套设计共存而不混淆
Formality 同时读入 reference 和 implementation，还要读标准单元库、设计库和内部数据库。Container 就是这些对象的组织边界。

| Container | 装入内容 | 常见来源 |
|---|---|---|
| Reference container `r` | golden RTL、必要库、top 信息 | Verilog/SystemVerilog/VHDL |
| Implementation container `i` | gate netlist/DDC、标准单元库、top 信息 | DC 输出、后端输出 |

implementation 不能只读 Verilog 网表，还要读标准单元库。因为网表里有 `AND2_X1`、`DFF_X1` 等 cell，工具必须知道这些 cell 的逻辑功能，才能和 RTL 表达式比较。

## 3. 最小工具入口：先把两套设计装进容器
本节是概念课，但这些概念不能只停在名词上。Formality 的最小入口就是把 reference、implementation、library 和 top 放到正确容器里，再让工具建立对应关系。

```sh
fm_shell -f fm_min.tcl | tee logs/fm_min.log
```

```tcl
set_app_var synopsys_auto_setup true
set_svf out/TOP_NAME.svf

read_db lib/sc_max.db

read_verilog -r rtl/TOP_NAME.v
set_top r:/WORK/TOP_NAME

read_verilog -i out/TOP_NAME.gv
    # 或 read_ddc -i out/TOP_NAME.ddc
set_top i:/WORK/TOP_NAME

match
report_unmatched_points
```

这段最小入口的目的不是完成全部证明，而是确认“谁和谁比”已经成立。输入是 RTL、网表或 DDC、标准单元库、SVF 和 top 名；输出是 log、容器里的 top、matched/unmatched 结果。PASS 信号是 reference top 和 implementation top 都存在、standard cell 可解析、unmatched 数量为 0 或可解释。FAIL 信号是 top not found、unresolved cell、SVF 读入错误或 unmatched 激增。

可以把 container 理解成两个证物箱：reference 箱放原始合同，implementation 箱放施工后的实物记录，library 是零件说明书，SVF 是改名和重构的翻译索引。证物没装对时，后面的 verify 就像拿错合同去审案，结论再漂亮也不可信。

## 4. Compare point 是形式验证的切分点
大设计不能直接当作一个巨大真值表暴力比较。Formality 会围绕 compare point 切分逻辑。

常见 compare point：

- register 或 latch：时序边界天然把组合逻辑切开。
- black box：内部不展开，只比较边界。
- primary output：最终可观察输出必须一致。

驱动某个 compare point 的组合逻辑叫 logic cone。形式验证要证明：在同样输入和状态下，reference 的 logic cone 与 implementation 的 logic cone 在对应 compare point 上输出一致。

## 5. Match 和 verify 是两个阶段
Match 解决对应关系，verify 解决等价证明。很多初学者看到失败就以为功能不等价，其实常见第一类失败是匹配失败。

| 阶段/结果 | 问题 | 常见原因 | 第一反应 |
|---|---|---|---|
| matched | reference 的点已经找到 implementation 对应点 | SVF、命名、层次和 top 都基本可用 | 进入 verify，看是否等价 |
| unmatched | reference 或 implementation 中有点没有对应上 | 名字变化、寄存器合并、层次变化、SVF 缺失、top 读错 | 先修匹配，不急着改 RTL |
| failing | 已匹配点无法证明等价或确实不等价 | 真功能差异、错误 match、错误约束、black box 建模问题 | 看 failing compare point 和两边 logic cone |
| aborted | 工具没有完成证明 | 状态空间过大、资源不足、cut point/black box 策略不当 | 调 proof 策略或缩小问题，不把它等同于 fail |

综合会做重命名、常量传播、寄存器合并、retiming、FSM recoding。名字已经变了，单靠端口名或寄存器名不一定能配上，所以后续流程必须依赖 SVF guidance。

## 6. Logic cone 帮你定位失败位置
如果 verify fail，不要盲目翻整个网表。先看 failing compare point，再沿它的 reference cone 和 implementation cone 回溯。截图中的 debug cycle 就是在展示：reference cone 和 implementation cone 某个局部逻辑不同，导致 compare point 输出不一致。

定位顺序：

1. fail 的 compare point 是 register、black box 还是 output。
2. 这个点是否 match 正确。
3. 两边 cone 的输入边界是否一致。
4. 差异是综合优化可解释，还是 implementation 真改变了功能。
5. 如果是可解释优化，检查 SVF 是否记录；如果是不可解释差异，回到综合或 RTL/ECO 源头。

failing cone 的排查不要像在一座城市里挨家敲门，而要像沿着断电的街区找变电箱：先从熄灯的 compare point 往回走，只查真正驱动它的局部网络。最小清单如下：

| 检查点 | 要问的问题 | 可能结论 |
|---|---|---|
| compare point 类型 | 是寄存器、输出还是 black box 边界 | 决定回溯深度和是否需要展开模块 |
| match 来源 | 这个对应关系是名字匹配、结构匹配还是 SVF guidance | 错误 match 会制造假 fail |
| cone 输入边界 | 两边 cone 的 primary input、state、black box 边界是否一致 | 输入不一致时不能直接判功能差异 |
| 逻辑差异 | reference cone 与 implementation cone 在哪一层开始不同 | 定位到综合优化、ECO 或 RTL 变更 |
| 约束/黑盒 | 是否有未建模 cell、x-state、clock gating、memory black box | 建模错误会伪装成等价失败 |

这张表的价值在于防止“看到 fail 就全局翻网表”。Formality 的 debug 视图已经把火警位置圈到一个楼层，读者应该顺着 cone 找烟源，而不是把整栋楼拆开。

## 工程练习

1. 区分 match fail 和 verify fail 的排查。

   合格答案：match fail 先查 SVF、命名、层次、top、black box 和优化变换；verify fail 先查 failing compare point、logic cone、输入约束、错误 match 或真实功能差异。不要看到 fail 就直接改 RTL。

2. 说明形式验证的边界。

   合格答案：形式等价证明 implementation 和 reference 一致；它不能证明 reference 满足需求，也不能替代仿真、断言或规格审查。它像复印件比对，不负责判断原稿内容是否正确。

## 7. 与 AI+IC 工程的连接
NPU/AI 加速器中常见宽数据通路、状态机控制、SRAM black box、clock gating、pipeline retiming。它们都会增加 match 和 verify 难度。形式等价不是可选装饰，而是保证综合后 MAC 阵列、DMA、控制 FSM、总线接口仍与 RTL 一致的交付门。

## 自测与答案
1. 形式等价能证明需求正确吗？  
答案：不能。它证明 implementation 等价于 reference，reference 是否满足需求由功能验证和规格审查保证。

2. compare point 常见三类是什么？  
答案：register/latch、black box 边界、primary output。

3. logic cone 是什么？  
答案：驱动某个 compare point 的组合逻辑区域，是工具局部证明等价的对象。

4. match fail 和 verify fail 区别是什么？  
答案：match fail 是对应关系没建立或建立错；verify fail 是对应点建立后两边逻辑无法证明等价或确实不等价。
