# 任务06：gvim 文本编辑工具

## 本章知识全景图

### 1. 一眼看懂这讲在讲什么

gvim 的核心不是“很多快捷键”，而是把文本编辑拆成三层：输入文字、用命令操纵文字、用底行命令处理文件和批量变换。数字前端工程师每天要改 RTL、filelist、约束脚本、仿真脚本和日志定位；如果只会鼠标编辑，面对端口列表、重复声明、批量替换和差异审查时会很慢，也很容易漏改。

核心概念：命令模式、插入模式、底行模式、motion、复制/粘贴、列编辑、搜索、替换、分屏、tab、`gvimdiff`。

逻辑主线：

- 先理解 gvim 为什么必须分模式。
- 再把移动、删除、复制、粘贴、替换变成可组合动作。
- 然后掌握可视块模式，解决 RTL 中常见的列式编辑。
- 接着学习搜索、底行命令、分屏和 tab，支撑多文件阅读。
- 最后用 `gvimdiff` 建立修改后的自审闭环。

### 2. 概念地图

| 能力层 | 具体命令 | 解决的问题 | 失败信号 |
|---|---|---|---|
| 模式切换 | `i`、`a`、`o`、`Esc`、`:` | 区分输入、命令、文件操作 | 敲字母不进文件，或命令被写进文本 |
| 基础编辑 | `x`、`dd`、`yy`、`p`、`u` | 单字符、单行、局部文本修改 | 改多了但不知道如何撤销 |
| 块编辑 | `Ctrl-v`、`I`、`A`、`d`、`y` | 批量处理端口/对齐/列 | 对齐了文本却改错方向或位宽 |
| 搜索定位 | `/pattern`、`n`、`N` | 找信号、模块、always、case | 搜到关键字但没理解语义 |
| 多文件审查 | `:vsp`、`:tabnew`、`gvimdiff` | 对照文件、查看差异 | 修改后没有差异审查 |

### 3. 最短学习路径

1. 打开一个可丢弃练习文件。
2. 在三种模式之间来回切换，直到不混乱。
3. 练熟最小编辑闭环：插入、删除、撤销、复制、粘贴、保存、放弃。
4. 用 `Ctrl-v` 做列操作，理解“文本列”和“RTL 语义”不是一回事。
5. 用 `/` 搜索结构关键字，再用分屏或 tab 对照文件。
6. 修改后用 `gvimdiff` 看差异，而不是凭印象说“应该改对了”。

gvim 可以理解成一台带档位的编辑机器：命令模式是操作档，插入模式是输入档，底行模式是文件和批处理档。新手最常见的问题不是“不聪明”，而是挂错档还猛踩油门：想输入时还在命令模式，想保存时还在插入模式。

## 1. 三种模式：gvim 的效率来自“输入”和“操作”分离

gvim 刚打开文件时处于命令模式，这时键盘输入不会直接变成文本，而是被解释成编辑动作。只有进入插入模式后，键盘才真正写入文件；底行模式负责保存、退出、跳转、设置、替换和批处理。

视觉验证：02:24-04:57，画面讲解 `gvim file` 打开文件，以及命令模式、输入模式、底行模式的分工。

![三种模式概览](<./screenshots/任务006_gvim文本编辑工具/01_open_gvim_file_02m24s.jpg>)

这张图要看模式分工，而不是背 `.vimrc` 每一行。左侧命令打开文件，中间配置影响编辑体验，右侧展示编辑状态；三者共同说明 gvim 不是普通记事本。

| 模式 | 进入方式 | 主要用途 | 退出/切换 |
|---|---|---|---|
| 命令模式 | 打开文件默认进入，或按 `Esc` | 移动、删除、复制、粘贴、撤销、进入其他模式 | `i/a/o` 进插入，`:` 进底行 |
| 插入模式 | `i`、`a`、`o`、`I`、`A`、`O` | 输入代码和文字 | `Esc` |
| 底行模式 | 命令模式下按 `:` | 保存、退出、替换、分屏、设置 | 回车执行，或 `Esc` 取消 |

最常见的新手错误是“模式错了”。如果你按字母没有写进文件，先看左下角是否是插入模式；如果你把 `:wq` 直接写进正文，说明你还在插入模式，没有先按 `Esc`。

## 2. 打开文件：不存在会新建，所以必须先确认路径

`gvim test_rtl.v` 如果目标文件不存在，会打开一个空缓冲区；只有保存后才真正生成文件。这个特性很方便，也很危险，因为路径错时你会以为打开了原文件，实际上是在错误目录里新建了空文件。

视觉验证：09:08-10:33，画面演示在 test 目录下用 gvim 打开一个不存在的 `.v` 文件，gvim 自动进入新文件编辑状态。

本节不重复使用同一张配置截图，重点转成操作判断：打开空白缓冲区时先问“我是在新建文件，还是路径错了”。这一步靠 `pwd`、`ls` 证明，不靠肉眼觉得文件名对。

打开前的安全动作：

```bash
pwd
ls test_rtl.v
gvim test_rtl.v &
```

如果 `ls` 报不存在，先决定这是不是你想要的新文件。RTL 工程中同名文件可能出现在不同目录；路径错时保存一个空文件，会让后续 filelist 或仿真报出更难定位的问题。

## 3. 插入、删除、撤销：最小编辑闭环要能复原

插入命令的差别在于插入位置。`i` 在光标前插入，`a` 在光标后追加，`o` 在下一行新开一行，`O` 在上一行新开一行。它们都进入插入模式，写完后必须按 `Esc` 回到命令模式。

视觉验证：10:33-13:58，画面演示进入插入模式、输入文本、回到命令模式、移动光标和替换字符。

![插入与删除状态](<./screenshots/任务006_gvim文本编辑工具/04_verilog_inputs_28m05s.jpg>)

这张图要看光标所在行、左下角状态和文本变化。练习时每一步都要能说出“我刚才改变了哪个字符或哪一行”，否则后面用撤销也不知道撤回了什么。

常用闭环：

```vim
i      " 当前光标前插入
a      " 当前光标后追加
o      " 下一行新开一行并插入
Esc    " 回命令模式
x      " 删除当前字符
dw     " 删除一个单词
dd     " 删除当前行
u      " 撤销
Ctrl-r " 重做
```

练习口径：每做一步都要能说出“我现在在哪种模式、命令作用范围是什么、屏幕结果是什么、如何撤回”。如果不能撤回，就不要继续叠加更多修改。

## 4. 复制粘贴：数字前端常按“单词、行、块”三种粒度复制

复制不是越大越快。RTL 里复制端口声明适合行粒度，复制信号名适合单词粒度，复制对齐列适合块粒度；粒度错了，最容易带入多余逗号、漏掉位宽或破坏缩进。

视觉验证：07:13-12:03，画面列出 `yw`、`y$`、`yy`、`nyy`、`p`、`P`，并演示复制多行和粘贴。

![复制粘贴命令](<./screenshots/任务006_gvim文本编辑工具/02_copy_paste_commands_07m13s.jpg>)

这张图要看复制粒度：单词、行、n 行、光标前后粘贴。RTL 编辑里粒度像手术刀大小，刀太大容易带走逗号、注释和位宽，刀太小又容易漏掉成组声明。

| 命令 | 含义 | 典型 RTL 用法 |
|---|---|---|
| `yw` | 复制一个单词 | 复制信号名 |
| `y$` | 复制到行尾 | 复制表达式尾部 |
| `yy` | 复制当前行 | 复制端口声明或 assign |
| `nyy` | 复制 n 行 | 复制一组连续声明 |
| `p` | 粘贴到后面 | 在下一行插入复制内容 |
| `P` | 粘贴到前面 | 在当前行前插入内容 |

结果检查：粘贴端口后必须检查方向、位宽、逗号、分号、注释和命名一致性。文本复制成功不等于硬件接口正确。

## 5. 可视块模式：适合列式修改，但不能替代语义判断

`Ctrl-v` 进入 visual block，可选择一块列区域，然后对这块区域执行删除、复制、替换、批量插入。RTL 的端口声明、信号列表、对齐缩进经常呈列状排列，所以块选择很有用。

视觉验证：12:03-16:40，画面演示进入 visual block、选择列、复制列、粘贴到其他位置，并说明选择后接 `d`、`y`、`r` 等命令。

![可视块选择](<./screenshots/任务006_gvim文本编辑工具/03_gvim_select_block_12m03s.jpg>)

这张图只看矩形选择区。可视块像拿尺子裁一列纸，裁得很整齐不代表内容语义正确；端口方向、位宽和信号角色仍要逐项检查。

基本流程：

```vim
Ctrl-v     " 进入可视块模式
j/k/h/l    " 扩展选择区域
y          " 复制块
d          " 删除块
r<char>    " 用单字符替换块
I<text>Esc " 在每行块前批量插入
A<text>Esc " 在每行块后批量追加
```

典型风险：你可以很快把多行都加上 `output`，但其中某些信号可能本来应该是 `input`。块选择只保证文本列被处理，不保证硬件语义正确；所以批量编辑后要按信号角色复查。

## 6. 搜索和底行命令：定位结构，不等于理解结构

搜索命令 `/pattern` 用来快速定位文本，`n` 跳到下一个匹配，`N` 跳到上一个匹配。对 RTL 文件来说，常搜的不是随便一个单词，而是结构入口。

视觉验证：36:09，画面在代码中搜索 `/out`，定位输出声明段。

![搜索 output](<./screenshots/任务006_gvim文本编辑工具/05_output_search_36m09s.jpg>)

这张图要看搜索命中只是定位，不是理解。命中 `output` 后，下一步应该看驱动逻辑、位宽和 testbench 观察点，而不是停在“我找到了”。

常用搜索：

```vim
/module
/input
/output
/always
/case
/assign
```

搜索只是定位工具。搜到 `output` 只能说明你到了输出声明附近，不能说明你已经理解输出含义。真正阅读接口时还要看位宽、注释、驱动逻辑、testbench 是否观察这个输出。

底行模式负责文件级动作：

```vim
:w      " 保存
:q      " 退出
:wq     " 保存并退出
:q!     " 放弃修改退出
:set nu " 显示行号
```

如果你正在插入模式，先按 `Esc`，再输入底行命令。把 `:wq` 写进文件里，是模式没有切回来的典型信号。

## 7. 大小写转换和缩写：批量变换必须有命名规则

课程演示了大小写转换和缩写展开。大小写转换看似简单，但在 RTL 命名里有约定：宏、参数常用大写，信号常用小写加下划线，模块名和文件名通常跟团队规范有关。

视觉验证：40:48，画面展示选中后转大写、转小写和大小写切换。

![大小写转换](<./screenshots/任务006_gvim文本编辑工具/06_case_toggle_40m48s.jpg>)

这张图要看改名前后的文本差异。大小写转换像批量喷漆，喷得快但不会判断哪个零件该是什么颜色；宏、参数、信号名的命名规则要由你负责。

常见命令：

```vim
~      " 切换当前字符大小写
gUiw   " 当前单词转大写
guiw   " 当前单词转小写
```

规则：批量改名后必须搜索旧名是否残留。比如把 `DATA_WIDTH` 改成 `ADDR_WIDTH`，只改声明不改使用点，会导致编译或综合报未定义。

## 8. 分屏、tab 和 `gvimdiff`：修改后必须能审查差异

分屏和 tab 解决“同时看多个文件”的问题；`gvimdiff` 解决“修改后到底改了什么”的问题。数字前端工程里，很多错误不是写代码时发生的，而是改完后没有审查差异。

视觉验证：45:47-55:26，画面演示 `:vsp`、tab 打开文件和 `gvimdiff` 比较两个文件。

![分屏和 tab](<./screenshots/任务006_gvim文本编辑工具/07_diff_tab_45m47s.jpg>)

![gvimdiff 文件比较](<./screenshots/任务006_gvim文本编辑工具/08_gvimdiff_files_55m26s.jpg>)

这两张图分工不同：分屏和 tab 解决“同时看”，`gvimdiff` 解决“改了什么”。读者要学会把写代码和审查差异分成两个动作，而不是边改边凭印象判断。

常用命令：

```vim
:vsp other.v
:sp other.v
:tabnew other.v
Ctrl-w h
Ctrl-w l
```

差异比较：

```bash
gvimdiff old_file.v new_file.v
```

审查时不要只看颜色，要问四件事：

- 改动是否只发生在预期位置？
- 有没有误删端口、逗号、分号、位宽？
- 有没有旧信号名残留？
- 修改是否需要同步 testbench、filelist 或约束？

## 9. 最后速记

### 9.1 本章最该记住的结论

- gvim 的三种模式是效率来源，也是新手错误来源；任何异常先检查模式。
- 复制粘贴要按单词、行、块选择粒度，粒度错会制造隐蔽语义错误。
- `Ctrl-v` 列编辑适合 RTL 批量修改，但批量修改后必须按硬件语义复查。
- 搜索命令帮你定位结构，不能代替接口和逻辑理解。
- `gvimdiff` 是修改后的最低成本自审工具。

### 9.2 复现清单

1. 新建 `test_rtl.v`，练习 `i/a/o/Esc`。
2. 写三行文本，练习 `yy`、`3p`、`dd`、`u`。
3. 用 `Ctrl-v` 选择一列，分别试 `y`、`d`、`r`。
4. 用 `/output` 搜索声明段，再用 `n/N` 跳转。
5. 用 `:vsp` 打开另一个文件并用 `Ctrl-w h/l` 切换。
6. 复制一份文件做修改，用 `gvimdiff` 比较差异。

### 9.3 自测题

1. 为什么 gvim 要区分命令模式和插入模式？  
   答案要点：同一组按键在不同模式下承担不同工作；插入模式写文本，命令模式执行移动、删除、复制等操作。

2. `yy` 和 `yw` 应该分别用于什么场景？  
   答案要点：`yy` 复制整行，适合端口声明或 assign；`yw` 复制单词，适合信号名。

3. `Ctrl-v` 批量编辑端口方向后，为什么还要人工检查？  
   答案要点：块编辑只处理文本列，不判断信号语义；可能把本该是 `input` 的信号改成 `output`。

4. 修改完 RTL 后为什么建议用 `gvimdiff`？  
   答案要点：确认改动范围、发现误删误改、检查旧名字残留，是低成本自审。
