## 1. lab3 的目标：不是跑一次 DC，而是完成时序约束闭环
实验目标可以压缩成一条链：

```text
读原理图 -> 识别路径 -> 计算时序预算 -> 写 SDC -> source 到 DC -> 用报告验证
```

lab 文档列出的任务包括提取目标库时间单位、创建约束文件、验证语法、应用约束、验证有效性和完整性。其中真正最重要的是“创建”和“验证”：前者考察你能不能从结构推导约束，后者考察你能不能证明约束不是假约束。

## 2. 先分路径类型，否则约束会漏
图中的路径不是一类。按 startpoint 和 endpoint 可以分成四类：

| 路径 | startpoint | endpoint | 约束方式 | 漏掉后的风险 |
|---|---|---|---|---|
| 输入到寄存器 | input port | register D | `set_input_delay` + clock | 内部输入逻辑可用时间不明确 |
| 寄存器到寄存器 | register Q | register D | `create_clock` | 周期目标缺失 |
| 寄存器到输出 | register Q | output port | `set_output_delay` + clock | 输出后外部预算缺失 |
| 输入到输出 | input port | output port | input/output delay 或 max delay | 纯组合穿越路径可能不被约束 |

这个分类比命令本身更重要。约束文件写得再漂亮，如果图中的路径类型没有覆盖，报告就没有系统意义。

## 3. clock definition：所有 delay 都要相对时钟解释
视频中的 Clock Definition 表格先给出 clock 频率和相关参数。clock 是端口 delay 的参照系，没有 clock，`set_input_delay -clock` 和 `set_output_delay -clock` 都没有可解释的边沿。

![clock definition](<./screenshots/任务112_实验手册lab3_时序分析/video_dense_02_08m14s.jpg>)

约束骨架：

```tcl
reset_design
create_clock -period 3 [get_ports Clk]
set_clock_uncertainty -setup 0.12 [get_clocks Clk]
set_clock_transition 0.18 [get_clocks Clk]
```

如果实验手册给出 clock generator delay、insertion delay 或 clock skew，需要按题目要求折进 latency/uncertainty。不要把 clock 当成普通 input port 一起约束。

## 4. input delay：外部已经花掉的时间
input delay 的计算不是从端口本身开始，而是从外部 launch register 到本模块 input port 的路径开始。

```text
外部 launch clock edge
  -> 外部寄存器 clock-to-Q
  -> 外部组合逻辑 / 走线
  -> 本模块 input port
  -> 本模块内部组合逻辑
  -> 内部 capture register
```

`set_input_delay` 写入的是“到本模块 input port 之前已经用掉的时间”。它越大，留给模块内部输入逻辑的时间越少，约束越紧。

```tcl
set INPUTS [remove_from_collection [all_inputs] [get_ports Clk]]
set_input_delay -max 0.6 -clock [get_clocks Clk] $INPUTS
```

## 5. output delay：输出端之后还必须留给外部的时间
output delay 是 output port 之后外部路径和外部 capture register 需要的预算。它不是本模块内部输出逻辑 delay。

```text
内部 launch register
  -> 本模块内部输出逻辑
  -> output port
  -> 外部走线/组合逻辑
  -> 外部 capture register setup
```

`set_output_delay` 写入的是 output port 后面要预留的时间：

```tcl
set_output_delay -max 0.5 -clock [get_clocks Clk] [get_ports OUT1]
```

如果 output delay 过小，工具会误以为外部压力小，内部输出路径容易虚假通过；如果过大，内部输出逻辑被压得过紧，面积功耗可能上升。

## 6. DC 执行：让约束进入 design database
视频中间大量画面是在 shell、DC GUI 和文本编辑器之间切换。这里要抓住一条主线：先把 design 读入，再把约束 source 进去，再查报告。

![DC shell / GUI 执行环境](<./screenshots/任务112_实验手册lab3_时序分析/video_dense_04_16m28s.jpg>)

典型流程：

```tcl
read_verilog MY_DESIGN.v
current_design MY_DESIGN
link
check_design
source MY_DESIGN.con
check_timing
```

如果前面没有 `current_design` 和 `link`，约束对象可能找不到；如果 `source` 后不检查，脚本看似执行完也可能没有约束到正确端口。

## 7. 写约束文件：每个对象都要能在报告中找到
视频 24:42 之后进入约束编辑。学习重点不是每个字符，而是对象集合要正确。

![编辑约束文件](<./screenshots/任务112_实验手册lab3_时序分析/video_dense_06_24m42s.jpg>)

```tcl
set INPUTS  [remove_from_collection [all_inputs] [get_ports Clk]]
set OUTPUTS [all_outputs]

set_input_delay  -max <input_budget>  -clock [get_clocks Clk] $INPUTS
set_output_delay -max <output_budget> -clock [get_clocks Clk] $OUTPUTS
```

对象集合的常见错误：

- clock 没有从 input 集合中排除。
- 总线端口只约束了一个 bit。
- output delay 写到了 input port。
- `get_ports` 名称和 RTL 顶层端口不一致。

![约束编辑过程](<./screenshots/任务112_实验手册lab3_时序分析/video_dense_08_32m56s.jpg>)

## 8. 报告验证：看属性、看 violation、看路径细节
实验最后要读报告，不是为了截图完成，而是证明三个层面：

| 报告 | 回答的问题 |
|---|---|
| `report_port -verbose` | input/output delay、transition、load 等属性是否写到端口上 |
| `report_constraint -all_violators` | 还有没有违反约束的路径或 DRC |
| `report_timing` | 最差路径的 arrival、required、slack 怎么组成 |

![report 输出](<./screenshots/任务112_实验手册lab3_时序分析/video_dense_11_45m17s.jpg>)

如果 `report_port` 里端口属性为空，说明约束没打上；如果 `report_constraint` 有 unconstrained path，说明完整性不够；如果 `report_timing` 的路径和你预期不同，说明路径分类或约束对象可能错了。

`report_timing` 的数字要按 `arrival / required / slack` 读。input path 中，外部已经消耗的 `input_delay` 会把 data arrival 推晚；output path 中，`output_delay` 会从 clock period 里拿走一部分时间留给下游；reg-to-reg path 则主要看 launch/capture clock、clock uncertainty、cell/net delay。slack 不是一个孤立分数，而是“合同剩余时间”：`slack = required time - arrival time`。

如果纯 input-to-output 组合路径没有被单独考虑，它最容易变成漏约束路径：没有输入寄存器替你定义 launch，也没有输出寄存器替你定义 capture，必须靠 input delay、output delay 和 virtual/real clock 把上下游时序边界补全。

## 工程练习

1. 写 lab3 的最小复现路径。

   合格答案：进入 lab 目录；读库和 RTL；`current_design/link/check_design`；`source MY_DESIGN.con`；执行 `check_timing`；导出 `report_port -verbose`、`report_constraint -all_violators`、`report_timing`；最后把报告中的对象和原理图路径逐项对上。

2. 给 unconstrained endpoint 做排查。

   合格答案：先查端点是否属于某类遗漏路径，再查 `get_ports/get_pins` 集合是否为空，再查 clock 是否创建并传播到该路径，最后查 false path/multicycle 是否误设。不要先改 RTL，因为这是约束覆盖问题。

## 9. 实验完成标准
一个合格的 lab3 结果至少要能给出：

1. 原理图路径分类表。
2. clock 和端口 delay 的手算依据。
3. 可执行 `.con` 文件。
4. `check_timing` 无关键缺失约束。
5. `report_port` 能看到端口约束属性。
6. `report_timing` 能解释最差路径 slack。

## 复习与自测
1. 为什么 lab3 不能从命令开始学？  
   答：命令来自路径结构和预算；不先识别 startpoint/endpoint，就不知道该约束谁。

2. `set_input_delay` 的数值代表端口前还是端口后的时间？  
   答：代表数据到达本模块 input port 前外部已经消耗的时间。

3. `report_port -verbose` 在本 lab 中最重要的用途是什么？  
   答：确认 input/output delay 等属性是否真正施加到端口对象上。

4. 如果 `check_timing` 报 unconstrained endpoint，应该先怀疑什么？  
   答：先怀疑约束对象或路径分类遗漏，而不是马上修改 RTL。

## AI+IC 连接
NPU 子模块综合时，lab3 这套方法就是 block 级 SDC 生成流程。DMA、NoC bridge、SRAM controller、MAC tile 都要先画出接口路径，再分配 input/output budget，最后用报告证明约束进入工具。没有这一步，单个 block 的 timing clean 不能代表芯片集成后可用。
