# 任务106：lab1逻辑综合基本流程

## 本章知识全景图

这一讲不是单纯演示 DC GUI，而是把逻辑综合最小闭环跑通：检查 setup 和库文件，启动 DCG，读入 top 设计，link/check，保存 compile 前 DDC，执行 compile，读取 timing/area/constraint 报告，最后写出结果并保留命令历史。

| 概念层级 | 核心概念 | 前置知识 | 延伸应用 |
|---|---|---|---|
| 环境准备 | `.synopsys_dc.setup`、common setup、DC setup | 隐藏文件、Tcl source | 建立可复用综合环境 |
| 库检查 | logical library、symbol library、TLUPlus | target/link library | 让 DC 同时具备逻辑与物理估计依据 |
| 读设计 | GUI read、`read_verilog`、link design | Verilog top 和 instance | 让 top 进入 DC memory 并解析层次 |
| 综合执行 | `compile_ultra`、log、WNS、violation count | setup/hold 基础 | 判断优化过程是否收敛 |
| 结果输出 | DDC、mapped Verilog、report、history | DC memory | 形成可交接、可复跑的工程结果 |

最短学习路径：先看 setup 文件把哪些变量设好，再用 GUI 跑一遍 read/link/compile/report/write，最后把 GUI 点击对应回命令行脚本。真正要掌握的是每一步的输入、输出、成功信号和失败信号，而不是记住菜单位置。

## 1. Lab 的目标是跑通一条最小综合闭环

逻辑综合 lab 的真正产物不是一张 GUI 截图，而是一条可复现的工程链：输入 RTL、库和约束，经过 DC link/check/compile，输出报告、DDC 和 gate-level netlist。

这条链可以抽象成：

```text
setup -> library check -> read design -> link/check -> source constraints
      -> compile -> report timing/area/constraint -> write result -> save history
```

实际公司 flow 会比 lab 大很多，可能一两百条命令；但骨架仍然是这几块。你看懂 lab，不是为了以后一直点 GUI，而是为了知道自动化脚本中每一段在防哪类错误、产出哪类证据。

失败时按工位定位，而不是凭感觉重跑：

| 失败信号 | 首查工位 | 常见根因 |
|---|---|---|
| 启动后变量为空 | setup | `.synopsys_dc.setup` 没在 CWD，或 source 的 common/DC setup 路径错 |
| `check_tlu_plus_files` fail | library check | tech/tluplus/map 文件不匹配，或物理库路径错 |
| `link` unresolved | read/link | RTL 子模块、IP、DDC 或 macro library 没读入 |
| `check_design` 大量 missing/unconnected | design check | 例化端口不匹配、信号悬空、top 选错 |
| `check_timing` no clock/unconstrained | constraints | SDC 没 source、clock 名错、端口集合为空 |
| `compile` 结束但 WNS/violations 无改善 | compile/QoR | 约束太紧、逻辑太深、库/物理估计不合理 |
| report 文件为空或对象不对 | report/write | current design 错、命令重定向路径错 |

## 2. `.synopsys_dc.setup` 是 DC 启动时的项目级入口

实验第一步是用 `ls -a` 看隐藏文件，因为 `.synopsys_dc.setup` 默认不会被普通 `ls` 显示。DC 启动时会读取安装级、用户级、当前工作目录级 setup，本 lab 重点看当前 CWD 下的项目级 setup。

![setup 文件和变量检查](<./screenshots/任务106_lab1逻辑综合基本流程/task106_dense_0720s_00h12m00s.jpg>)

setup 里通常会 source 两类脚本：

| 文件 | 作用 | 典型内容 |
|---|---|---|
| common setup | 定义跨脚本共用变量 | library 路径、technology file、TLUPlus file |
| DC setup | 把变量应用到 DC | `target_library`、`link_library`、Milkyway library、alias |

本 lab 中的关键对象包括：

- logical technology library file：综合 mapping 和 timing 计算要用的 `.db`。
- symbol library file：GUI schematic 显示符号时要用。
- Milkyway design library：DC 和 ICC/ICC2 可以共用的数据结构，用来存设计与物理相关信息。
- TLUPlus file：用于估算金属线 RC，帮助 topographical 综合更接近后端布局布线。

注释也不是装饰。Tcl 里用分号结束语句，用 `#` 写说明，后续维护者才能知道每条变量设置对应哪类库文件。

## 3. 启动 Design Vision 是为了看懂状态，不是为了依赖鼠标

Design Vision 是 DC 的图形界面。初学阶段用 GUI 的价值在于直观看到 design hierarchy、command log、schematic view 和报告结果；工程阶段则要把这些操作还原成 Tcl 命令。

启动方式：

```sh
design_vision -topo
```

或者先进入命令行：

```sh
dc_shell -topo
```

然后在需要时打开 GUI。

GUI 常见区域可以这样理解：

| 区域 | 工程含义 |
|---|---|
| 顶部菜单 | GUI 对命令的封装，如 read、link、save |
| 左侧设计树 | 当前 DC memory 里的 design hierarchy |
| 中央视图区 | schematic、report、design browser |
| 下方 command/log | 命令执行记录、warning/error、返回结果 |

关键检查可以不用鼠标完成：

```tcl
printvar target_library
printvar link_library
printvar symbol_library
```

如果这些变量和 setup 文件预期一致，说明库环境基本被读进来了。

## 4. 库检查要分清“实验环境限制”和“真实 flow 必须通过”

实验里 `check_library` 可能因为没有安装 library compiler 而失败，这属于教学服务器环境限制；在公司环境中，library compiler/license 通常应该可用，因为库转换和库一致性检查是正常 flow 的一部分。

TLUPlus 检查则要看是否 pass：

```tcl
check_tlu_plus_files
```

![TLUPlus 检查通过](<./screenshots/任务106_lab1逻辑综合基本流程/task106_dense_1200s_00h20m00s.jpg>)

看图要点：TLUPlus 图只回答物理 RC 数据是否能被工具识别，它不证明 RTL 功能正确，也不替代 timing report。

TLUPlus 的作用不是综合逻辑功能，而是让工具在 topographical 模式下估计走线 RC。没有它，DC 很难对线延时、metal 层特性和后端相关性做合理估计。

## 5. 读入 top 后要确认 current design 和 link 状态

读 design 的 GUI 操作最终对应到命令：

```tcl
read_verilog top.v
current_design top
link
```

读入后要检查左侧 hierarchy 是否出现 top，以及右下角 current design 是否是 top。这个确认不是形式主义：后面所有 compile/report 都默认作用在 current design 上，current design 错了，报告就没有工程意义。

![读入设计后的层次树](<./screenshots/任务106_lab1逻辑综合基本流程/task106_dense_1440s_00h24m00s.jpg>)

link design 的成功信号是没有 error、没有 mismatch、没有必须处理的 warning。它的职责是把 top 中的子模块、IP、library reference 解析到 DC memory 或 link library 中。

GUI 点击 `File -> Link Design`，下方 command log 里会出现对应命令；这说明 GUI 不是另一套机制，只是命令的图形化入口。

## 6. compile 前保存 DDC，是为了给后续迭代留起点

在 compile 之前保存一版 DDC：

```tcl
write -format ddc -hierarchy -output unmapped/top.ddc
```

这版 DDC 相当于“已经读完 RTL、link 完层次、还没做最终 mapping/optimization”的快照。后续如果只是改约束、改频率或重跑不同优化策略，可以从这版开始，避免重新读入和解析所有 RTL。

之后再打开 schematic：

![综合前层次和 schematic](<./screenshots/任务106_lab1逻辑综合基本流程/task106_dense_1560s_00h26m00s.jpg>)

看图要点：schematic 图用于确认 top、子模块层次和 reference 都能展开；它是读入/link 成功的视觉证据，不是最终 QoR 证据。

schematic 不是最终交付物，但它能帮助初学者确认三件事：top 层存在、子模块层次存在、library cell/reference 没有明显缺失。

## 7. source 约束和 compile 要一起看 log

source 约束后，工具返回 1 说明脚本执行成功；但执行成功不等于约束完全合理。后续 `check_timing` 和 report 才能判断约束是否真的覆盖到该覆盖的路径。

compile 阶段可以用：

```tcl
compile_ultra
```

或者 lab 中对应的 GUI 操作。compile log 里要关注：

| log 信息 | 含义 | 判断口径 |
|---|---|---|
| library / TLU precheck | 编译前可靠性检查 | 缺库、缺 license、缺物理信息会在这里暴露 |
| global optimization phase | mapping/optimization 迭代 | phase 越多不代表越好，要看 QoR 是否改善 |
| WNS | worst negative slack | 越接近 0 或非负越好 |
| violation count | 违反路径数量 | 数量应随优化减少 |
| return 1 | 命令跑完 | 只说明流程可继续，不保证 QoR 满足 |

![compile log 中的优化阶段](<./screenshots/任务106_lab1逻辑综合基本流程/task106_dense_1920s_00h32m00s.jpg>)

视频里的重点是 WNS 从较差值逐步变小，violation path 数量也减少。这里要建立一个工程判断：compile 的成功不是“命令没崩”，而是 timing/area/power 报告能解释，且 violation 处于你能接受或后续可修的范围。

## 8. QoR 报告至少要看 constraint、timing 和 area

compile 后要读报告，不能只看 GUI 显示“完成”。本 lab 用 alias 简化了命令：

```tcl
rc  ;# report_constraint -all_violators
rt  ;# report_timing
ra  ;# report_area
```

`report_constraint` 告诉你还有哪些违反项，负值代表 violation。`report_timing` 展开最差路径，显示每个 cell/net 的延时、arrival time、required time 和 slack。`report_area` 统计面积、端口数、net 数、cell 数、组合逻辑面积等。

![timing 报告示例](<./screenshots/任务106_lab1逻辑综合基本流程/task106_dense_2040s_00h34m00s.jpg>)

![area 报告示例](<./screenshots/任务106_lab1逻辑综合基本流程/task106_dense_2160s_00h36m00s.jpg>)

这两张报告图不能混读：timing report 回答“哪条路径最危险、slack 如何算出来”，area report 回答“设计规模和 cell 面积分布如何”。后面的 slack histogram 只看坏路径分布是否集中，不能替代最差路径明细。

读 timing report 的最小口径：

1. 先看 slack 是否为负。
2. 再看 path group、startpoint、endpoint 是否符合预期。
3. 然后看 data arrival time 和 required time 的差值。
4. 最后定位延时最大的 cell/net，判断是逻辑太深、负载太大、约束太紧，还是库/路径设置问题。

histogram 适合快速看 violation 分布：

![slack histogram](<./screenshots/任务106_lab1逻辑综合基本流程/task106_dense_2280s_00h38m00s.jpg>)

直方图越靠左越危险，说明 slack 更差的路径更多；但它只能给全局形态，不能替代具体路径分析。

## 9. 保存结果时要区分 DDC、mapped netlist 和命令历史

优化后的 design 首先仍在 DC memory 中，必须写出文件。GUI 中的 save 操作对应命令：

```tcl
write -format ddc -hierarchy -output mapped/top.ddc
write -format verilog -hierarchy -output mapped/top.v
```

保存后可以打开 mapped 结构查看。compile 后的结果可能被 flatten 或优化到更低层，原来的层次名、module 结构不一定完整保留；这是综合优化的一部分，不要拿 RTL 层次直接要求 mapped netlist 完全一样。

![compile 后 schematic](<./screenshots/任务106_lab1逻辑综合基本流程/task106_dense_2400s_00h40m00s.jpg>)

最后还要保留命令历史：

```tcl
history > dc.tcl
```

或者从 command log 中复制本轮命令。命令历史的价值是可复跑：一旦 GUI 误关、实验中断或下一次要改约束重跑，你可以把关键命令整理成脚本，而不是重新手点一遍。

退出前可以释放设计：

```tcl
remove_design -all
exit
```

## 10. 从 GUI 过渡到脚本，是这个 lab 的真正终点

GUI 操作的最终目标不是让你永远依赖 GUI，而是让你看懂每个状态后，把流程转成脚本。

命令行流程可以写成：

```tcl
source .synopsys_dc.setup
read_verilog top.v
current_design top
link
check_design
source top.con
check_timing
write -format ddc -hierarchy -output unmapped/top.ddc
compile_ultra
report_constraint -all_violators
report_timing
report_area
write -format ddc -hierarchy -output mapped/top.ddc
write -format verilog -hierarchy -output mapped/top.v
```

如果工程更复杂，可以改成：

```tcl
define_design_lib work -path ./work
analyze -format verilog {A.v B.v top.v}
elaborate top
current_design top
link
```

如果 RTL 中有 VCS 相关语法或仿真选项，`analyze` 阶段可以加相应 option，让 DC 更好地接受这些语法。核心原则是：读入方式可以变，但 link/check/constraint/compile/report/write 这条闭环不能丢。

## 本章收束与检查

### 本章最该记住的结论

- Lab 1 的目标是跑通综合闭环，不是学会点 GUI。
- `.synopsys_dc.setup` 决定 DC 启动后能否看到正确库、路径和 alias。
- library check 和 TLUPlus check 是综合前的环境闸门。
- read/link 后必须确认 current design 是 top。
- compile 成功要看 WNS、violation count、constraint/timing/area 报告，不只看 return value。
- GUI 操作都能还原成 Tcl 命令；后续工程应该脚本化。

### 复现清单

1. `ls -a` 确认 `.synopsys_dc.setup` 存在。
2. 启动 `design_vision -topo` 或 `dc_shell -topo`。
3. 用 `printvar` 检查 target/link/symbol library。
4. `read_verilog top.v` 后确认 current design。
5. `link`、`check_design`，确认没有必须处理的 error/warning。
6. 保存 compile 前 DDC。
7. `source` 约束，执行 `compile_ultra`。
8. 读取 `report_constraint`、`report_timing`、`report_area`。
9. 写出 mapped DDC、mapped Verilog 和命令历史。

### 自测题

1. 为什么 GUI 点击和 Tcl 脚本不是两套不同 flow？

   答：GUI 点击本质上会在 command log 中执行对应 Tcl 命令；GUI 是命令的可视化入口，真实工程应把关键操作整理成脚本。

2. WNS 从负值变小但仍为负，说明什么？

   答：优化有改善，但最差路径仍未满足 required time。需要继续判断约束是否合理、逻辑是否过深、库和物理估计是否正确，以及是否可留给后端修。

3. 为什么 compile 前后都可以保存 DDC？

   答：compile 前 DDC 便于从已读入、已 link 的状态继续改约束重跑；compile 后 DDC 保存综合后的设计状态，适合同家 Synopsys 后续工具继续读取。
